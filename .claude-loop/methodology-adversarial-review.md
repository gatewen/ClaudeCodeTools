# 「開發設計閉環」方法論 — 對抗驗證後最終評估報告

> 評估基準：跟著這套方法論走，**Claude 產出的架構與代碼**會不會真的變得更高品質、更穩定？還是只產生漂亮的產出物文件、增加 token overhead、形成儀式劇場（theater）？
> 證據基礎：13 個經 3 視角對抗驗證存活的主張 + 11 個被駁回的主張，全部主張附倉庫檔案/行號，本報告獨立復查關鍵證據後撰寫。
> 復查日期：2026-05-30

---

## 1. 總體判斷

**結論：在「設計／認知一致性治理」這個窄域內部分有效，但對「使用者真正要的應用代碼品質」目前是『設計合理、零實證、且帶有結構性自我膨脹傾向』。**

直球說：這套方法論**還沒有任何證據**能回答「跟著走代碼會更高品質」這個核心問題，因為它從未在真實應用代碼上跑過。我獨立復查確認——`git ls-files` 全倉 **零個** `.ts/.py/.go/.rs/.js` 應用源碼（77 .md + 21 .sh + 1 .html + 1 LICENSE），`.claude-loop/artifacts/` 下全部產出物審查對象都是方法論自己的 markdown，**連一個 Phase 2 implementer 產出物都不存在**（`ls artifacts/ | grep P2` 為空），方法論宣稱改善代碼的核心引擎（Phase 2 code-simplifier、Phase 3 語言審查、R-x 語言標記）在所有閉環裡 100% 是 N/A 或從未實例化。方法論自己的文件（learning-log.md:192）也明文承認「T3 大型 5-Phase 實戰樣本 ≥ 1 = ❌」。

但這不是「純儀式劇場、什麼都沒有」的全盤否定。三個區分要誠實講清楚：

1. **它真正被驗證有效的能力，是「文件／設計一致性治理」與「跨來源認知盲點防護」**——這在 markdown 治理上有量化實證（cross-source review 漏看率 50%→67% 的證據是真的），但這個能力 ≠ 它宣稱的「改善應用代碼品質」。兩者之間沒有任何橋接證據。
2. **它最有實證的機制（cross-source review）恰恰證明了閉環自審本身的不足**——真正抓到盲點的是「換一個外部 LLM（Codex）」，不是閉環的五階段儀式。這是承重的反諷。
3. **它有方法論自己記錄在案的結構性膨脹傾向**——「單 LLM architect 每次 review 抓到問題本能是補規格而非縮 scope」（learning-log.md:451），codemap skill 經 5 輪 architect + 3 輪 codex review 仍被判為「偽裝成 prompt skill 的靜態分析子系統」而冷凍。若這套傾向施加到應用代碼上，過度設計風險真實存在。

**淨評價**：這是一套設計用心、認知謙卑、自我審計誠實的方法論。它在防 LLM 的設計前提偏誤與文件矛盾上有真材料。但它的核心商業承諾（代碼品質）目前 0 證據，且 ceremony 成本、單點收斂、補規格膨脹三個結構性問題在最需要把關的時刻（長 session、大任務、急迫情境）反而最脆弱。**部分有效，但有「核心命題未經實證」這個 critical 落差。**

## 2. 經驗證存活的真實優勢

以下是對抗驗證後**確實會改善產出品質**的設計（注意：多數驗證域是「方法論／認知性產出」，非應用代碼）。

### 2.1 cross-source review（R-2 / R-5）是最誠實、最有量化實證的一條規則
- **證據**：learning-log.md:280 single-source 自審漏看率 50%、:319 第二次 67%（平均 58%），且兩次都由不同 LLM（Codex）cross-source 拉回。problem 追蹤 #007 把它升格為「Single-Perspective Self-Review Blind Spot」長期警惕模式，並制度化為 R-2 hard requirement（CLAUDE_TEMPLATE.md:323，我已逐字復查）+ R-5 連續 ≥2 次 needs-attention 強制降級 scope（:326），且 R-1~R-5 明標「任何情境不可 bypass，即使用戶口頭命令跳過」（:320）。
- **為何改善品質**：它從根本上承認「會犯偏誤的 LLM 自己偵測自己的偏誤」無效，強制引入外部視角。對架構決策、根因診斷這類單 LLM 容易自我背書的產出，這是真實的攔截。
- **誠實限縮**：R-2 的文義適用域被明文限定在「方法論修改 + 重大認知性產出」，**不覆蓋一般應用代碼審查**；且其有效性依賴外部資源（另一 LLM 或人類），不是 prompt-skill 可獨立提供的。這是它的優勢也是它的自承極限。

### 2.2 Phase 5 雙向追溯的「反向枚舉」是有意識的反確認偏誤工程
- **證據**：verifier.md:337 明文「正向與反向必須獨立執行、步驟 8 才交叉比對（避免確認偏誤）」；anti_patterns 禁止「先看代碼再找設計來配」「跳過反向分析」；步驟 5-6 先枚舉行為路徑當「分母」再反向標記，無對應者判 [多餘程式碼]/[遺漏設計]。
- **為何改善品質**：反向枚舉理論上能抓「實作了但設計未涵蓋」的死碼／未授權 fallback，這是正向追溯與單測抓不到的類別。獨立性設計（fresh-context task sub-agent）讓它不只是文件對帳。
- **誠實限縮**：這是「設計成立」而非「實效已證」。倉庫內 0 筆反向分析實際抓到死碼的紀錄；唯一運作樣本（P5AB）對象是純文檔變動、自宣「無執行路徑可追蹤」、結果 0 孤兒。對中大型代碼還有 ">15 函式只聚焦改動函式" 的縮減逃生口，恰好把舊死碼排除在外。

### 2.3 設計前提的「事實主張閘門」有真實外部事故血統
- **證據**：architect.md Step 0a 字面證據掃描 + Step 0b 共用值檢測；design-reviewer Step 5c Falsification Check；CLAUDE_TEMPLATE.md Section 12 事實主張閘門。這些源自真實外部專案失敗教訓（reel_core panic、GS/config 誤判，問題追蹤 #001-#005）。
- **為何改善品質**：能攔 LLM 在閱讀真實 config／環境事實時的推理偏誤（如「同一 IP 被 N 方引用 → 不可能私有 → 推論必錯」），這類錯誤前提會污染整個 Phase 1 設計。
- **誠實限縮**：只覆蓋「環境事實前提」（X 是 Y 型斷言），**不覆蓋業務語意正確性**（含稅 vs 未稅、演算法選錯）。純邏輯設計錯誤直接跳過此閘門。

### 2.4 升格學習機制（同類根因 ≥3 次 → 用戶確認 → 長期警惕模式）是真實的反覆犯錯防護
- **證據**：#006（行數預算估算樂觀）、#007（self-review 盲點）都是「升格自 3 筆 learning-log」的真實內部偵測，非外部植入。architect Phase 1 強制兩層教訓查詢。
- **為何改善品質**：把一次性教訓固化成跨閉環的常駐檢查，避免同類盲區反覆發生。這是方法論少數真正「自己在運作中賺到」的機制。
- **誠實限縮**：目前唯二真實升格的 #006/#007 都是「方法論維護類」元問題，非應用代碼缺陷。

## 3. 經驗證確認的缺口與風險（critical → low）

### 🔴 CRITICAL-1：核心命題零實證——從未在任何應用代碼上驗證過
- **存活票數**：3/3（兩個獨立 gap 主張都 3/3 存活）
- **證據**：全倉零應用源碼；所有 24 個閉環產出物審查對象皆方法論 markdown；P3 代碼品質四項檢查（結構安全／依賴方向／語言專屬／R-style）100% N/A；Phase 2 implementer 產出物零存在；方法論自承「T3 大型 5-Phase 實戰樣本 ≥ 1 = ❌」「跨 session/模組/repo 樣本各 ≥ 1 = ❌」。連唯一「dogfooding」也是改 DOGFOODING.md spec 文檔，且 spec 自身「沒跑閉環（self-irony）」。
- **為何影響代碼品質**：使用者問「跟著走代碼會不會更好」，repo 內 0 次閉環跑在代碼上。領域偵測、驗證層級、資源生命週期審查、跨模組資料流追蹤這些「為真實代碼設計」的機制，唯一實證來源是改一個不編譯、不執行、無資源洩漏的 markdown 倉庫。代碼品質效果完全是理論外推，KPI baseline 門檻校準也建立在 100% self-edit 的非代表性樣本上。
- **誠實平衡**：方法論對此 gap 是已知、已記錄、已 gating（v7 啟動條件明列 T3≥1）。這是「未驗證」非「已證偽」，所以是 critical 而非「致命已死」。但對使用者的核心問題，目前拿不到任何支撐證據。

### 🟠 HIGH-1：設計前提錯誤時，閉環會「嚴謹地把錯的事做對」（GIGO 放大器）
- **存活票數**：2/3
- **證據**：閉環核心理念.md:67 方法論自承「自證可以比對設計跟實作有沒有對齊，但沒人質疑設計本身是不是最好的選擇…否則只是正確地做了錯的事」；verifier.md:50「只驗證一致性，不做設計」；code-reviewer 的 by-design 豁免讓「設計刻意取捨」直接跳過審查。
- **為何影響代碼品質**：當 Phase 1 把「含稅金額」誤設計為「未稅」或選錯演算法定為 BC-1，Phase 2-5 越嚴謹，越精確地實作並交叉驗證這個錯誤，產出 5 份高度對齊的產出物，但代碼從根上錯。設計正確性的所有防線（architect Step 0a/0b、design-reviewer Step 5c）都在實作前、無代碼證據可依，且只覆蓋環境事實前提，不覆蓋業務邏輯正確性。唯一緩解（Phase 1b 挑戰式審查）只跑 1 輪、嚴重才回退最多 3 輪。
- **被駁方觀點（公允記錄）**：1 票判 driver 認為方法論有三層前置防禦（事實閘門+反向質疑+Falsification），且「含稅誤設計」恰落在 Step 5c 射程內——但這只對「有環境事實可證偽」的設計成立，純業務語意錯誤仍漏接。

### 🟠 HIGH-2：閉環「獨立性」是 context 隔離，不是模型/框架異質——穩定漏過框架自身編碼的盲區
- **存活票數**：3/3
- **證據**：Phase 1b/3/5 雖開 fresh-context task sub-agent，但仍同一底層 Claude；learning-log.md:283「同 LLM 同 session 自審 0/2，不同 LLM 2/2」；方法論自承「所有子 agent 還是 Claude…不能完全消除同一模型的限制」（閉環核心理念.md:95）。grep code-reviewer/verifier 對「並發/race/時序/效能/cross-source/異質 LLM」命中皆為 0。
- **為何影響代碼品質**：reviewer 清單沒列入的維度（並發、效能、整合時序）會被結構性穩定漏過，因為審查者與被審者共享同一模型的盲區。對「規格沒覆蓋的未知未知」缺乏補位機制。一般代碼審查（Phase 3）不在 R-2 cross-source 強制範圍內，仍是同模型自審。
- **誠實限縮**：對「有 BC-x/EH-x 錨定的缺陷」，拿凍結規格對帳仍有真實異質捕獲力（參照系異質性），不是全面漏接。漏看集中在「規格本身的未知未知」+「一般代碼審查無 cross-source 強制」兩個邊界。代碼層有 Phase 4 強制實際跑測試這道外部 ground truth，並發 bug 若被測試觸發仍會暴露——所以原主張「穩定漏過一半以上」的量化外推被適度削弱（58% 來自無 ground truth 的認知任務，不能直套代碼）。

### 🟠 HIGH-3：可學習性極差 + 補規格膨脹是結構性傾向（人類無法外部稽核）
- **存活票數**：3/3
- **證據**：CLAUDE_TEMPLATE.md 580 行（已復查）含十餘橫切閘門 + 六套 ID 系統，always-read；8 agent 合計 2037 行；learning-log.md:222 自承「Claude 每次都全讀／人類 maintainer 大概率不讀」；codex 對 codemap skill 判「lightweight static-analysis subsystem masquerading as a prompt skill」5+3 輪不收斂 → PAUSE；自評根因「單 LLM architect 自然走向擴張，每次 review 本能是補規格而非縮 scope」（:451）；v6.4.2 source-of-truth marker 三次連續漏改、靜默失敗「沒有 forcing function 暴露問題」。
- **為何影響代碼品質**：(1) 人類無法稽核 → 方法論正確性只能靠 LLM 自洽，缺乏外部 forcing function（三次靜默漏改即症候）；(2) 補規格慣性若施加到應用代碼，會產生過度抽象／過早建構的架構（codemap 是活體案例：方法論驅動的設計過程本身產出 over-engineering）。R-5 是事後補的護欄，其存在本身即承認膨脹是常態傾向。
- **誠實限縮**：方法論有微小任務逃生閥（<50 行單檔直通）+ 顯式 Trade-off 宣告 + 不適用情境聲明，高負荷只落在中大型任務；「人類不讀」部分是設計取捨（LLM 全讀執行、人類只觸發）而非純缺陷。

### 🟠 HIGH-4：可信度與學習進化兩條命脈收斂到 verifier 單一 agent，且資源壓力下第一個被犧牲
- **存活票數**：2/3
- **證據**：verifier.md 單檔 396 行承載 step 0~10 約 14 個職責；CLAUDE_TEMPLATE.md:197-198 全域降級規則「子 agent 第二次失敗 → 主 agent 自審」；配額降級優先序第 1 順位 = 「P5 Part AB → 主 agent 自審（省最多 token）」；#007 證明 single-source 自審漏看率 50-67%。
- **為何影響代碼品質**：在最需要把關的長 session／大任務後段（配額耗盡時），最重的閉合保證自動降級為 single-source 自審——架構在「最該硬」時反而最軟。
- **被駁方觀點（公允記錄·此點較弱）**：1 票判 false。關鍵反證：(a) 學習進化的決策權不在 verifier（精簡閉環無 verifier sub-agent，升格寫入由主 agent 用戶確認後執行）；(b) P3 品質審查明標「⛔ 不可降級（100% 攔截率）」，是降級序列裡**最後**才犧牲的，代碼層攔截受架構保護；(c) 降級有標記非靜默，:456 在配額 70% 即主動告警。代碼缺陷攔截不經過 verifier，所以「代碼品質隨資源反向衰減」對代碼層不成立——爆炸半徑落在一致性稽核與 meta-learning 的儀式層。**綜合：結構單點為真，但對代碼品質的直接傷害有限。**

### 🟡 MEDIUM-1：並發/race/時序缺陷結構性漏接（語言中立層空）
- **存活票數**：2/3（含 1 票駁回，嚴重度共識下調至 medium）
- **證據**：agent 庫並發只出現在 Phase 1 設計提問清單；code-reviewer 結構安全只查資源生命週期/錯誤靜默/非法狀態三項靜態屬性；tester 是 per-BC-x 三測試的單元測試思維；verifier 無並發追蹤項。
- **為何影響代碼品質**：兩 handler 並發寫同 map、check-then-act 競態、async 初始化順序這類 bug 在 BC-x 功能測試下全 PASS，閉環綠燈放行。
- **重要削弱**：語言指南層有實質補洞——go.md 有強制 `go test -race`（已復查確認 line 224）+ 競態條件 high 審查項，rust.md 有死鎖/鎖順序 high。但 (a) 條件性部署（setup.sh 偵測才裝）、(b) 僅 Go 有強制 race tooling、(c) Python/TS/C# 的應用層邏輯競態無偵測器、(d) 無強制誘發並發的測試設計。對 Go/Rust 後端不成立「完全漏接」，故下調 medium。

### 🟡 MEDIUM-2：中游認知機制是純 prose，無機械強制、無可觀測證據（declarative theater）
- **存活票數**：3/3（嚴重度共識在 medium~high 間）
- **證據**：6 個 hook 無一驗證認知閘門是否觸發（grep「事實主張/push/質疑/cognit」於 hooks/ 零命中）；Section 12 觸發需 LLM 先承認自己在斷言（但確認偏誤本質正是不自覺在斷言）；Karpathy Q1「需要 push back 嗎」是自問式無輸出契約。
- **為何影響代碼品質**：這些機制在「急/用戶說直接做」的壓力情境下最容易被靜默略過——而那正是偏誤最危險的時刻。且留下證據表格反而製造「已驗證」假信心（learning-log.md:314「風險表反而讓人認為已 cover，實際 67% 漏看的還在」）。
- **誠實平衡**：唯一有 artifact 契約的是 verifier Step 9c（寫入 P5-fact-claims.md），且有跨 agent 下游重建鏈（design-reviewer 5c → verifier 9c 從 artifact 而非自承重建）對環境事實子場景提供事後攔截；R-1/R-2/R-5 是針對壓力情境的成文反制（雖仍是 prose）。故非全裸奔，但 push back/Karpathy 自檢確實無留痕、無缺席偵測。

### 🟡 MEDIUM-3：精簡閉環名實不符 + ceremony 成本對小任務 ROI 為負
- **存活票數**：3/3（嚴重度共識 medium）
- **證據**：「單一函式·1-3 檔·<300 行」中型任務仍強制 ≥3 次獨立 sub-agent 委派（design-reviewer + code-simplifier + code-reviewer，皆 type:task）；CLAUDE_TEMPLATE.md:459「每個委派 ~5K-30K token」→ 一個 200 行函式可能燒 15K-90K token 在審查上；CLAUDE_TEMPLATE.md:8-10 自承「中型 +30% / 大型 +50-80% 時間」。dogfooding T2 精簡六步實測「0 high / 3 medium」——重流程在實際中型任務攔到 0 個 high。

## 4. 被駁回的迷思（對抗驗證後不成立）

誠實點出這些「聽起來像優勢、實則站不住」的主張：

### 4.1 ❌「BC-x→R-x 編號追溯閉合是架構級防呆、能真正提升代碼品質」（1/3）
機制設計（獨立性、延遲交叉比對、反確認偏誤）為真，但「提升代碼品質」是未證影響：反向枚舉從未對真實代碼運作過，唯一樣本退化為「grep 哪個文檔行對映哪個 BC-x」的行對行文件對帳；0-for-N 實證紀錄；本 repo 最關鍵的「設計聲稱-檔案不符」缺陷是 codex 外部 review 抓的，自家雙向追溯放行了同一批產出。**自證一致 ≠ 代碼正確**——這正是迷思核心。

### 4.2 ❌「閉環自審/獨立 sub-agent 有量化證據改善代碼品質」（0/3 與 1/3）
量化數字（50-67% 漏看率、2/2 捕獲）全部來自**審查方法論文檔本身**，零應用代碼缺陷。被 Codex 抓的全是 meta-level（跨版本相容、awk parser silent bug、文檔自我矛盾）。把 meta 層證據貼到 code 層結論是範疇偷換。而且真正捕獲的是「換一個外部 LLM」，不是閉環五階段儀式——歸因偷渡。

### 4.3 ❌「Phase 5 是死碼/未設計 fallback 的有效偵測器」（1/3）
分母由同一 LLM 從同一份代碼讀出 → 循環依賴，漏看的路徑根本進不了枚舉表；>15 函式 scoping 正好切掉最該偵測的舊死碼；二元判定 + 禁善意推測可能誤殺必要的防禦性代碼。單線程邏輯代碼正是 dead-code linter / coverage 工具確定性完勝的場景。

### 4.4 ❌「認知驗證層是自我指涉悖論的 critical 系統盲點」（1/3）
事實為真但 critical framing 是稻草人：方法論明文承認自檢不可靠（:316「閉環不應依賴此機制…是對認知謙卑的承認」）並用 R-2/R-5 把外部來源制度化為不可 bypass 義務——這是已揭露並結構化回應的前提，非掩蓋的盲點。下調為「R-2 觸發層缺機械強制」的 medium 具體缺陷。

### 4.5 ❌「learning-log 近半事件是 ceremony 自我消耗、對 app 代碼零貢獻」（0/3）
數字誇大（實測 39 非 49，且 grep -c 計行非計事件）；#007 系列抓到的是真實 commit 修復（跨專案 marker 污染、upgrade 靜默失敗等真實基礎設施 bug，已 git 驗證）；self-irony 標記是 anti-theater 證據（系統主動標記自身無作用機制並設重評閘門），不是 theater 罪證。行數預算戰爭只存在於本文檔倉庫的特殊 dogfood 語境，不外溢到使用者 app。

### 4.6 ❌「Phase 5 自證是核心 target 錯位、儀式劇場」（1/3）
事實為真（Phase 5 量一致性非正確性），但定性錯誤：方法論在核心理念文件明文標示此邊界（宣稱與實質一致 → 不構成 theater 定義要件）；設計正確性由 Phase 1b 挑戰式審查 + Phase 4 測試承擔，是分層分工非遺漏；Phase 5 抓的「漂移/遺漏/多餘代碼」是真實缺陷類別。

### 4.7 ❌「編號閉合的柔性出口（by-design/間接覆蓋）使 100% 對映率灌水」（1/3）
事實大致為真但「無第二來源覆核」被自己引的證據推翻：by-design 由 Phase 3 標記 → Phase 5 verifier 獨立覆核（learning-log.md:45），是兩道 agent；間接覆蓋判定方向是 fail-closed（不確定判 ❌）非柔性放行。唯一實證的 by-design 使用是吸收文件行數超標（非代碼缺陷）。

> **這些迷思的共同教訓**：方法論最容易被誤認為優勢的，是「產出物的嚴謹外觀」。但嚴謹的編號、漂亮的雙向追溯表、密集的證據表格，本身都不是代碼品質——它們是**一致性**與**可追溯性**，與**正確性**正交。把「文件對齊」當「代碼對」是這套方法論最大的認知陷阱，連它自己都在 core 理念裡承認了。

## 5. 優先改進建議

聚焦使用者真正目標：讓 Claude 產出的應用代碼更高品質、更穩定。

### 建議 1（最高優先）：在真實應用代碼上跑至少一個完整 5-Phase 閉環，產出 before/after 缺陷對比
- **做什麼**：拿一個有真實 bug 史的小型應用（含並發、邊界、資源生命週期的 Go/Rust/Python 服務），完整跑一次 T3 大型 5-Phase，記錄「閉環攔下的真實代碼缺陷」vs「裸寫漏掉的」。
- **對代碼品質的增益**：這是唯一能把 CRITICAL-1 從「設計合理但 0 證據」變成「有/無實效」的動作。沒有這一步，方法論對其核心承諾永遠是 untested。建議同時跑「裸寫 + 一次 Codex review」當對照組，才能區分「閉環結構有效」vs「多一個 LLM 看一眼就有效」。

### 建議 2：把 cross-source review（不同模型/人類）擴展到「一般應用代碼審查」的 R-2 觸發域
- **做什麼**：目前 R-2 只強制「方法論修改/重大認知產出」。將「高風險代碼變更」（並發、安全、跨模組契約、無測試覆蓋的關鍵路徑）納入強制 cross-source。
- **對代碼品質的增益**：直接堵 HIGH-2（同模型盲區）。方法論唯一量化證明有效的機制（外部視角 2/2 vs 自審 0/2），目前對使用者最在意的應用代碼根本不觸發。把它接到代碼層是「最高 ROI、已驗證有效」的擴展。

### 建議 3：為並發/race/時序新增一條語言中立的 Phase 3 審查項 + Phase 4 強制並發測試
- **做什麼**：在 code-reviewer 結構安全清單加「共享可變狀態保護 / check-then-act 原子性 / 初始化順序依賴」三問（不依賴語言指南部署）；tester 對含並發 BC-x 強制「誘發並發執行」的測試設計，而非僅單線程 per-BC-x 三測試。
- **對代碼品質的增益**：堵 MEDIUM-1。並發是「最難抓、最貴、漏了最危險」的類別，目前只在 Phase 1 問一句、Go 以外無偵測。後端 API（方法論自標最嚴格）尤其需要。

### 建議 4：給設計正確性加一道「實作後回饋」閘門，打破 GIGO 放大
- **做什麼**：在 Phase 3 或 Phase 5 增加「看到代碼真實行為後，回頭質疑 Phase 1 設計前提是否正確」的步驟（目前 code-reviewer「設計是標準」+ by-design 豁免結構性關閉了這條路）。對業務語意正確性（非僅環境事實）增加一個輕量的「這個 BC-x 真的解決對的問題嗎」檢核。
- **對代碼品質的增益**：堵 HIGH-1。目前設計正確性防線全在實作前、無代碼證據、只覆蓋環境事實。一道實作後回饋能攔下「忠實實作爛設計」這個最隱蔽的失效模式。

### 建議 5：把「補規格慣性」做成可量測的 forcing function，對抗膨脹
- **做什麼**：每次 review 強制記錄「本輪是補規格還是縮 scope」並設比例告警；R-5 之外增加「規格行數/機制數連續增長 N 輪 → 強制提出刪減方案」。為 always-read 主檔的橫切閘門設硬上限。
- **對代碼品質的增益**：堵 HIGH-3。codemap 案證明方法論驅動的設計會自我膨脹到不可收斂。若這套傾向施加到應用架構，會產生過度抽象。一個機械的縮 scope forcing function 直接對抗「補規格本能」。

### 建議 6（成本優化）：給精簡閉環一個 inline-skip 逃生口，降低小任務繞過誘因
- **做什麼**：對「無跨呼叫者語意風險 + 無跨產出物矛盾」的純小函式，允許跳過 code-reviewer 委派（保留 code-simplifier），或提供「用戶確認低風險 → 降為 inline 自審」選項。
- **對代碼品質的增益**：堵 MEDIUM-3 的二階反噬。降低小任務 ROI 為負導致的繞過誘因，保住採用率——被繞過的任務是零把關，比輕量把關更糟。
