## 審查結果

### DR-1 [arch-risk] — design/10 規劃 vs P1 規格分歧未顯式標示

**問題**：

design/10 規劃文件多處（lines 79-80、141、152、196、208-215）明確寫入 **「CLAUDE_TEMPLATE.md migration-notes-v6.3 區塊（≤ 4 行 inline 風格，沿用 v6.2.0 教訓）」**。但 P1 設計規格 Section 5 設計決策表 + Section 1 分層結構聲明**反向決定「不新增」**，理由為「K-07 純新增 examples/ 目錄，無改 CLAUDE_TEMPLATE 結構 → 無 migration 需求」。

設計者改變了上游決定，但：
1. 沒在 P1 explicit 標出「此處與 design/10 lines 79-80 / 208-215 規劃分歧」
2. 沒回去更新 design/10 註記「規劃時保留，實際 P1 改為不做」
3. Phase 5 反向追溯會發現 design/10 listing of changes ≠ 實際 git diff，誤判為「實作漏做」

**影響**：

- **短期**：Phase 5 verifier 反向追溯時，會看到 design/10 寫「migration-notes-v6.3 註記」、實際 git diff 沒有，啟動 forensic 找原因
- **中期**：未來 v7.x major 升級若參考 design/10 為 migration-notes 模板出處，會誤以為 v6.3.0 有此區塊可繼承
- **不影響 v6.3.0 正確性**——設計者的判斷本身可能是對的（純擴充無 breaking 確實不需 migration），但**決定的更新沒有閉環**

**建議修正**：

二擇一（任一即可解除）：

- (a) **P1 Section 5 設計決策表 migration-notes-v6.3 行新增「⚠️ 此決定與 design/10 規劃分歧（design/10 lines 79-80 寫保留 4 行 inline）。理由：規劃時保留為穩健做法，P1 評估後判斷無 migration 需求」**
- (b) **回去 design/10 加一段「2026-04-26 P1 階段更新：migration-notes-v6.3 區塊改為不新增（理由詳見 P1 Section 5）」**——如此 design/10 不再為過時規劃

推薦 (a)：design 歷史檔案不該事後改寫（v5.x 慣例「設計歷史文檔僅供參考」），由 P1 explicit 標分歧較符合本 repo 設計檔案的不可變性原則。

### DR-2 [arch-risk] — examples/ 與被引用 K-x 機制的依賴反向同步未進入 CLAUDE.md 編輯規範

**問題**：

P1 RISK-2 + design/10 RISK-2 都已正確識別「範例引用 K-04 / K-14 / K-16 → 未來方法論升級需同步更新範例」。但 P1 給出的緩解策略只有：

> 每範例檔末加「最後修訂」+ 版本標注；v7 升級時 explicit 標 examples/ 進依賴影響表

這是**事後依賴 v7 那位設計者記得加**——而 CLAUDE.md 「依賴影響分析」表是 hardcode 在 repo 根的，沒有人主動把 examples/ 加進去就漏掉。

CLAUDE.md 目前依賴影響表 11 行（已含 9 個觸發場景），其中**沒有「K-x 機制（K-04 / K-14 / K-16 etc.）行為變動 → 同步檢查 examples/」這一行**。

**影響**：

- 例如 v7 重構 K-04 push back 觸發條件 5 條白名單時，依賴影響表會引導同步 CLAUDE_TEMPLATE Section 12 + 認知驗證概念檔，但**不會引導去看 examples/01-think-before-coding.md**——而那個範例的「關鍵限制」段落 explicit 寫了「5 條白名單」
- 結果：方法論本體已升級，範例還停在 v6.3.0 寫法，反而誤導讀者（範例還在教舊做法）

**不影響 v6.3.0 當前正確性**——v6.3.0 部署當下範例與本體一致；風險出現在 v7+。但既然 examples/ 是 K-07 主體，現在應該補建這個機制以免未來忘記。

**建議修正**：

在 P1 風險清單 + Phase 2 實作清單加入：

- **修改 CLAUDE.md 「修改前依賴影響分析」表**，新增一行：
  ```
  | CLAUDE_TEMPLATE Section 0 (Karpathy 4 原則) / K-04 / K-14 / K-16 行為變動 | `.claudedocs/examples/01-04-*.md`（對應原則範例同步檢查）|
  ```
- 此修改對 setup.sh / EXPECTED_FILES 無影響，純 CLAUDE.md 字面新增 1 行（不爆預算）
- 列入 BC-K07-7（新建）或合併進 BC-K07-6

### DR-3 [medium] — BC-K07-6 「跨 4 處 v6.3.0」與依賴影響表 5 處不一致

**問題**：

BC-K07-6 驗收條件寫：

> 跨檔同步 grep `v6.3.0` 在 4 處（CLAUDE_TEMPLATE / dev-closed-loop/README / 根 README / .claudedocs/README）各 ≥ 1

但 P1 Section 1 分層結構聲明列出 6 處檔案要動：
1. `.claudedocs/examples/` (新)
2. `.claudedocs/README.md`
3. `dev-closed-loop/README.md`
4. 根 `README.md`
5. `CLAUDE_TEMPLATE.md`
6. `setup.sh`

而 setup.sh 改 12/12 → 17/17 + EXPECTED_FILES 增 5 條目時，**會不會也順手把 setup.sh 內 v6.x 提示字串改 v6.3.0**？目前 grep `v6\.` setup.sh 是空（setup.sh 沒寫死版本），所以**確實是 4 處**。但 BC-K07-6 沒在註解中說明「為什麼是 4 處不是 6 處」（examples 自身不算 + setup.sh 不含版本字串）——等於把判斷邏輯藏在驗收條件中。

**影響**：

- Phase 3 一致性審查時，code-reviewer 看到 BC-K07-6 「4 處」會問「為何不是 5 / 6 處」，需追溯到 P1 才能確認；耗 review 時間
- 若 implementer 為對齊「4」而誤刪 setup.sh 中可能存在的 v6.x 字串（雖然目前無），引入 bug

**建議修正**：

BC-K07-6 描述補一句註解：

> 跨檔同步 grep `v6.3.0` 在 4 處（CLAUDE_TEMPLATE / dev-closed-loop/README / 根 README / .claudedocs/README）各 ≥ 1。**註：examples/ 各檔自身的「最後修訂」標注不計入此 4 處；setup.sh 因不含版本字串故不列。**

### DR-4 [medium] — CLAUDE_TEMPLATE 緩衝 = 5 行剛好踩 #006 硬規則底線

**問題**：

實證 wc -l：CLAUDE_TEMPLATE.md = **540 行**（驗證設計者寫的 540 行屬實 ✅）。

P1 Section 6 行數預算寫上限 545 → 緩衝 = **5 行**（精準等於 #006 預防做法 c「緩衝 ≥ 5 行硬規則」）。

但設計者選的是「增量 = 0」（只改 v6.2.0 → v6.3.0 一行替換）——這個選擇在純文字層面不會增量。**但實作可能微調**：
- 若 implementer 發現 closed-loop 註解處還需加「examples/」一行提示（部署說明）→ +1 行 → 緩衝 4 → **破 #006 硬規則**
- 若 implementer 在 Section 0 末尾加一行「詳見 .claudedocs/examples/ 5 個對照範例」→ +1-2 行 → 緩衝 3-4 → **破 #006 硬規則**

設計者寫「上限 ≤ 545」是把硬規則塞在邊緣——技術上合規，但無錯誤容錯。**v6.0.0 教訓 #2「預算緩衝 ≥ 5 行硬規則」的設計意圖是「實作中即使有微調仍不超預算」，當前緩衝剛好 5 行等於零容錯**。

**影響**：

- 不影響 v6.3.0 當前正確性（增量真的 0）
- 但若 Phase 2 實作過程觸發任何「順便加一行說明」的衝動 → 馬上違規 → 觸發 R-x

**建議修正**：

二擇一（任一即可解除）：

- (a) **P1 Section 6 預算上限放寬至 ≤ 547**（緩衝 7）→ 留實作微調空間，仍遵循 #006 硬規則 + 預留 v6.0.0 教訓 #3「DR 修正傳遞性」緩衝
- (b) **保留 545 但 Phase 2 implementer 步驟新增明確指令「如發現需在 CLAUDE_TEMPLATE 加任何說明性內容，先回 P1 加 BC，不在實作中即興 +1」**

推薦 (a)：成本零（純預算數字調整），收益是 implementer 心理空間。

### DR-5 [low] — BC-K07-3 行數範圍 80-120 內部 prose / code 比例未明示

**問題**：

P1 Section 2 大綱寫「每檔包含具體程式碼範例 + 修正版本各 1-2 個程式碼塊（合計 ~30 行 code 占行數預算）」，所以 80 行檔約 50 行 prose（5 段平均 10 行）；120 行檔約 90 行 prose（5 段平均 18 行）。

下限 80 行對 5 段固定結構 + 程式碼 30 行 + heading 5 行 + 結尾 3 行 = **38 行框架 → 剩 42 行 prose 分 5 段約每段 8 行**——技術上夠但偏緊；上限 120 行則寬鬆。

不影響 BC-K07-3 「80-120 行」grep 範圍檢查的可驗證性，但 implementer 可能在「場景」這種短段（往往 3-5 行就夠）和「修正版本」這種長段（完整 case + 程式碼 + 解釋）的分配上失衡。

**建議修正**：

P1 Section 2 BC-1 新增一行 implementation hint（不變更 BC 驗收條件）：

> **段落分配建議**（非 BC，僅 implementer 參考）：場景 5-10 行 / 錯誤示範 15-25 行（含 code 10-15）/ 原則診斷 10-20 行 / 修正版本 20-30 行（含 code 15-20）/ 關鍵限制 10-20 行 + 結尾 3-5 行 ≈ 80 下限 / 120 上限。

**low 級摘要**：純風格優化，不影響任何 BC / 行數預算 / 部署正確性。
