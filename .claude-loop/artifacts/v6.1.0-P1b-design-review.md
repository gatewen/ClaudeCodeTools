### DR-1 [arch-risk] — CLAUDE_TEMPLATE Section 11.5 編號位置與「執行約束」脈絡的語意錯配

**問題**：

P1 規格 BC-3「位置」寫「**Section 11.5「Dead Code 處理立場」**（位於 Section 11 同類掃描之後、Section 12 事實主張閘門之前）」。

但目前 CLAUDE_TEMPLATE.md 的結構是：
- Section 11 同類掃描（line 224，屬「⚠️ 執行約束」大段）
- Section 12 事實主張閘門（line 228，仍屬「執行約束」段）
- Section 12.5 Push Back 義務（line 253）
- Section 13 質疑熔斷協議（line 281）

「執行約束」section 內的條目都是**最高優先級的 Hook 阻擋式或全域約束規則**（合理性審查、同類掃描、事實主張閘門、Push back、熔斷）——它們是「Claude 行為的硬性約束」。

「Dead Code 處理立場」嚴格說是**程式碼審查與實作期的判斷規則**（Phase 2/3 的指引），把它編入「執行約束」區的 Section 11.5 位置語意上**降級不對等**——它不是全域硬約束，而是領域哲學立場。

**長期風險**：之後若有人要新增「執行約束」級別的硬性規則，會被「11.5 Dead Code」打散編號連續性，且讓讀者誤以為這是與 Section 12 事實主張閘門同等級的硬閘門。

**建議修正方向**：
- 選項 A（推薦）：放到 Phase 2 / Phase 3 的描述附近，或放在「精簡閉環步驟 2」描述附近（line 374 ~ 376），編為「步驟 2 補充」或「品質審查補充」。
- 選項 B：另開一個概念區（如 Section 14「審查立場」），與「執行約束」（行為硬約束）做語意切分。
- 選項 C（保守）：保留 Section 11.5 位置，但在內文開頭明標「本立場為品質審查階段適用，非執行期硬約束」，避開語意誤導。

**為何 arch-risk 不是 high**：本次行為功能正確、不影響流程可運作；屬編號結構長期規劃議題，記錄不阻擋。

### DR-2 [arch-risk] — 連動檔案矩陣（EH-2）未納入 Skill 部署層的 init-claude.md

**問題**：

依本 repo CLAUDE.md「依賴影響分析」表第 7 行：

> **CLAUDE_TEMPLATE.md — 結構變更（section / placeholder 增刪）** → `dev-closed-loop/skill/init-claude.md`

BC-3 在 CLAUDE_TEMPLATE.md **新增 Section 11.5**（structural change，新增 section），按上表規則應同步檢查 `init-claude.md` 部署邏輯（Skill 是否在部署時對 Section 11.5 做 placeholder 替換、版本號驗證、結構驗證）。

P1 EH-2 連動矩陣的 BC-3 行只列「CLAUDE_TEMPLATE + code-reviewer.md」，**漏列 init-claude.md 的潛在影響檢查**。

**現實影響**：
- 若 init-claude.md 部署邏輯中沒有對「Section 11.5」做特殊 placeholder 處理，則新增 section 是純文字添加，不影響部署 → 無實際 bug。
- 但 EH-2 教訓的精神是「**主動 walk 連動矩陣**」，不是「事後發現了再補」。漏列就是 walk 不夠完整。

**建議修正方向**：
- 在 P1 EH-2 矩陣 BC-3 行補一個「Skill 層連動檢查 = no-op（已驗證 init-claude.md 不對 section 11.5 做特殊處理）」的明標。
- 或在步驟 2 實作前主 agent 用 Read 抽查 init-claude.md，確認無 placeholder 引用 Section 11/12 編號或結構錨點。

**為何 arch-risk 不是 high**：實際部署邏輯未受 Section 編號變動影響的可能性高（Skill 邏輯通常依賴 placeholder 名稱而非 section 編號），實際運作不阻擋。但 walk 矩陣完整性的方法論層面是長期合規問題。

### DR-3 [medium] — EH-2「DR 修正傳遞性」walk 範圍只覆蓋連動檔案，未覆蓋預算傳遞

**問題**：

v6.0.0 教訓「DR 修正傳遞性」的原始定義是：「修正一處時 walk **全部 BC list** 看是否需同步調整**其他 BC 的預算/介面**」（P1 Section 0 Line 19 引文）。

P1 EH-2 設計只 walk「**檔案連動矩陣**」（哪些檔案要一起改），沒覆蓋「**預算傳遞**」面向。具體範例：
- 若 BC-1 第 7 問實作時排版佔用 +5 行（非預估的 +1 行），CLAUDE_TEMPLATE 總增量 = 5 + 12 + 2 = 19 行 → 510 + 19 = 529 行 → **觸發 EH-1 medium 區間（525-540）**。
- 此時 BC-1 的偏差會「傳遞」到 BC-3 / BC-5 的整體預算判讀，但 EH-2 沒有 walk 機制提醒主 agent 在實作 BC-1 後重估全體預算。

**建議修正方向**：
- EH-2 補一個「實作梯度 walk 規則」：每完成一個 BC 後，主 agent 用 wc -l 檢查 CLAUDE_TEMPLATE 累積行數，若觸發 EH-1 medium 區間，立即停下重估剩餘 BC 預算。
- 或在 EH-1 補一個「完成每個 BC 後即時行數檢查」步驟，補 EH-2 的不足。

**為何 medium 不是 high**：v6.1.0 預算寬裕（510 → 525 預期增量 15 行，distance to 540 上限 = 30 行），實際觸發 high 的概率低；但教訓延續精神不到位是 medium 級的方法論瑕疵。

### DR-4 [medium] — EH-1 行數預算估算未含「排版自由度寬容區間」

**問題**：

EH-1 預算計算寫「BC-1 步驟 1 自檢 +1 行 / BC-3 Section 11.5 +12 行 / BC-5 步驟 1 補句 +2 行 = +15 行」。

實際排版自由度檢查：
- **BC-1 第 7 問**（CLAUDE_TEMPLATE line 369「設計自檢」段，目前是單行濃縮 6 問）：
  - 若擴在原句尾、不換行 → 實際 +0 行
  - 若換行成 markdown list 形式（每問一行）→ 實際 +6~7 行
  - **真實波動：0~7 行**，估算「+1 行」過度精確
- **BC-3 Section 11.5**（含 markdown fence + heading + 5 條 bullet）：估「+12 行」基本合理
- **BC-5 補句**（短句一行）：估「+2 行」基本合理

**真實預算可能落在 510 + 14 ~ 510 + 22 = 524 ~ 532 行**，部分情境會跨入 medium 區間（525-540）。

**建議修正方向**：
- EH-1 預算計算改為「+15 行（區間 +14 ~ +22）」並明標寬容假設。
- 或在 BC-1 內文增「**排版選擇**：若擴在原句尾追加（不換行）以最小化行數膨脹」一句，引導 implementer 選擇低行數方案。

**為何 medium 不是 high**：上限 540 行仍有寬度，high 觸發概率低；屬精度問題。

### DR-5 [medium] — BC-4「R-style」與 v6.0.0 Section 0 Q3 Surgical 規則的概念重疊

**問題**：

v6.0.0 Section 0 Q3 Surgical（line 36~55 內的橫切自檢層第 3 問）已經規定：「修 bug 不順手 reformat 引號 / 加 type hints」——這條規則的精神是「不主動引入或修改既有風格」。

BC-4 R-style 子類別判定規則：
- **改動引入的不一致** → R-style medium（建議改回）：與 Q3 Surgical 衝突傾向（Q3 鼓勵不動既有風格，R-style 卻說改回）
- **既有已存在的不一致** → 不報告：與 Q3 Surgical 一致

**核心張力**：「改動引入的不一致」與「Q3 Surgical 不順手 reformat」在邊界情境會打架——例如 implementer 順手用了與既有檔案不同的引號風格，照 Q3 應該是「Implementer 不該主動引入新風格」（implementer 端規則），R-style 視角是「Reviewer 應該抓出來建議改回」（reviewer 端規則）。兩條合起來邏輯一致，但**規則歸屬不清**容易讓 agent 誤觸發。

**建議修正方向**：
- BC-4 內文補一句：「R-style 與 Section 0 Q3 Surgical 互補——Q3 從 implementer 端避免引入不一致；R-style 從 reviewer 端反向兜底」。
- 或在 `.claudedocs/concepts/閉環核心理念.md` 加一句概念性說明（順便補 BC-6 Anti-Patterns Summary 對照表內 Q3 行的關聯）。

**為何 medium 不是 high**：規則本身正確、不矛盾；只是兩條規則的職責邊界沒明確分工，長期會出現「reviewer 抓 R-style high 但 implementer 對照 Q3 認為合規」的爭議——但 medium 級先記錄即可。
