# 問題追蹤

## 這份文件是幹嘛的

踩過的坑記在這裡，下次不要再踩。CLAUDE.md 規定 Claude 在中型以上任務設計前掃一次「警惕模式」段，命中的把預防做法納入設計。

兩個區塊：

| 區塊 | 放什麼 | 誰讀 |
|------|--------|------|
| **警惕模式** | 反覆出現、值得每次設計前都提醒一次的模式 | Claude 設計前必掃 |
| **單一事件** | 一次性的 bug 或踩坑，還不確定會不會再發生 | 人偶爾回顧 |

## 怎麼新增

- **單一事件**：發生就記，格式見下方。
- **升格為警惕模式**：同類根因在單一事件或 `.claude-loop/learning-log.md` 出現 ≥ 3 次，且你同意它值得每次都提醒，就搬上來並編號。
- **退場**：某條警惕模式很久沒再命中，覺得它已經不需要每次提醒，直接移到文末「歷史條目」。這是人的判斷，不設機械門檻。

> v6.4 曾為升格與降級設計過 n=10 / m=5 / 2n=20 的機械規則。四個月下來升格兩條、降格零條，機制本身的維護成本高於價值，v8 起改回人判。

## 警惕模式

> 條目內提到的「Phase 1 / Phase 3 / architect / verifier」是 v6、v7 時期的角色名稱，對應到 v8 就是「設計前 / 審查時 / 設計者 / 審查者」。條目保留原文，因為歷史證據不改寫。

### 條目格式

```markdown
#### #XXX · YYYY-MM-DD · 來源 · #tag1 #tag2

- **模式**：一句話描述
- **觸發情境**：什麼時候容易發生，要具體
- **預防做法**：設計時要做什麼，可操作
- **檢測信號**：審查時看什麼
- **歷史證據**：出處或時間戳
```

### 模式記錄

#### #001 · 2026-04-18 · 種子條目（reel_core 案外部來源） · #無驗證宣告 #診斷紀律

- **模式**：絕對負面陳述缺證據（Existence Claim Without Verification）
- **觸發情境**：診斷「A 找不到 B」「X 不存在」「Y 缺失」「Z 為空」類問題時，agent 基於架構推理或直覺下結論，未實際執行 `ls` / `grep` / `find` / `test` 驗證
- **預防做法**：根因敘述中的任何絕對負面陳述（不存在 / 沒有 / 缺 / 找不到 / 為空 / 未呼叫 / 未實作）必須附產生該結論的指令輸出。無證據時須降格為「推論（未驗證）：X 可能不存在。驗證指令：ls X」
- **檢測信號**：審查時掃根因段落，觸發字（不存在/沒有/缺/找不到/為空）出現但同段落無 ls/grep/find/test 指令輸出 → R-x high
- **歷史證據**：種子條目（外部來源 `閉環學習素材-存在性宣告缺證據.md` 2026-04-18）

#### #002 · 2026-04-18 · 種子條目（reel_core 案外部來源） · #routing誤分類 #診斷紀律

- **模式**：存在 vs 路徑 框架錯置（Existence-vs-Routing Mis-framing）
- **觸發情境**：處理「A 讀不到 B」類 bug 時，將 routing 問題（B 在別處存在但 A 找錯位置）誤當作 existence 問題（B 真的不存在），導致修法朝錯方向（補資料 vs 修路徑）
- **預防做法**：根因分析「A 讀不到 B」類 bug 時，必須先用 `find`（或等價全域搜尋）確認 B 是否存在於任何位置。三種分類強制標明：
  - B 在別處存在 → **routing 問題**，修 A 的查找路徑（env var / cwd / config）
  - B 絕對不存在 → **existence 問題**，補資料 / 生成 B
  - B 找得到但讀不了 → **access 問題**，修權限 / 格式 / 版本
- **檢測信號**：設計規格或審查時，同主體同時出現「X 不存在」與「X 存在於 Y」 → 框架錯置嫌疑，要求 reframe 為 routing
- **歷史證據**：種子條目（外部來源 `閉環學習素材-存在性宣告缺證據.md` 2026-04-18，UK 658 reel_core panic 案）

#### #003 · 2026-04-22 · 種子條目（GS 誤判事件外部來源） · #認知性 #確認偏誤 #單線索推論

- **模式**：單線索 → 事實（Single-Source Inference to Asserted Fact）
- **觸發情境**：讀到 config / workflow 中的單一線索（例：某 IP 出現在某 entry），立即斷言為事實（「這個 IP 是 GS」）。一旦假設形成，後續所有證據都往「支持此假設」方向解讀，形成確認偏誤。並把推論寫入 memory 污染未來 session
- **預防做法**：字面證據掃描 + 共用值檢測先於任何推論。任何「X 是 Y」類斷言必須有 ≥ 1 A 級字面證據；共用值 N ≥ 3 時不得斷言為專屬資源。memory 寫入前須標注證據等級，弱證據禁寫入 memory
- **檢測信號**：設計規格中出現「某 X 是某 Y」類斷言但無字面證據 → 審查 high。追溯時比對設計事實引用是否有 A 級證據
- **歷史證據**：種子條目（外部來源 `經驗反思-GS誤判-2026-04-22.md` 2026-04-22，pig_server GS 誤判事件）

#### #004 · 2026-04-22 · 種子條目（GS 誤判事件外部來源） · #認知性 #字面證據 #self-declaration

- **模式**：忽視字面證據（Ignored Literal Evidence）
- **觸發情境**：讀到檔名明寫用途（`PypiConfig.cfg`、`SaltMaster.yml`）或檔內 echo/print 字串（`echo "no pig pkg found on pypi server"`），但推論走向相反結論（「這個 IP 跑 GS」），將作者的 self-declaration 當成裝飾
- **預防做法**：三層字面掃描（檔名 token + docstring + echo/print 字串）。**A 級證據規則**：字面證據（self-declaration）是 A 級，間接推論（如「workflow SSH 到這個 IP」）是 B 級；A 與 B 衝突時默認以 A 為準，B 降為「待查證」
- **檢測信號**：設計規格中推論涉及的檔案，其檔名 token / docstring / 字串常數指向不同用途但設計未說明此衝突 → 審查 high（要求補說明或撤回推論）
- **歷史證據**：種子條目（外部來源 `經驗反思-GS誤判-2026-04-22.md` 2026-04-22，R2 根因）

#### #005 · 2026-04-22 · 種子條目（GS 誤判事件外部來源） · #認知性 #共用值 #N≥3

- **模式**：共用值私有化（Shared-Value Privatization）
- **觸發情境**：config / 資料檔中某 value（IP / URL / 路徑 / 埠號）出現在多個 entry（≥ 3 次），卻推論為某一方的專屬資源（「這個 IP 是 pig 的 GS」）。違反「一個專屬資源不可能同時屬於多方」的基本邏輯
- **預防做法**：全域出現次數檢查。value 出現 ≥ 3 次 → 判為共用資源（pypi / DNS / Salt Master / 監控 / 共用 DB），設計不可推論為某 entry 專屬；≥ 5 次直接視為共享基礎設施
- **檢測信號**：設計規格中出現「某 IP / URL / 服務是某模組專屬」但同 config 中此 value 出現 ≥ 3 次 → 審查 high（推論與共用值衝突）
- **歷史證據**：種子條目（外部來源 `經驗反思-GS誤判-2026-04-22.md` 2026-04-22，R3 根因）

#### #006 · 2026-04-26 · 升格自 3 筆 learning-log · #行數預算 #judgment_failure

- **模式**：主檔行數預算估算樂觀導致緩衝不足
- **觸發情境**：升級含「結構化 metadata 區塊」「表格展開」「Section 子段拆分」時，只算 line-by-line 不算區塊整體展開（一個區塊就 15-20 行）
- **預防做法**：對結構化區塊單獨估 ≥ 15-20 行；審查時實際 `wc -l` 不信任設計者自評；緩衝 ≥ 5 行
- **檢測信號**：`wc -l` 對比預算；緩衝 < 5 → medium；超出上限 → high
- **歷史證據**：v6.0.0 教訓 #2 / #3 + v6.2.0 R-1，完整內容見 `.claude-loop/learning-log.md`
- **v8 註**：此條目是 v6 時期「主檔行數硬上限」規則自己製造的問題。v8 模板約 110 行、無行數預算規則，此條目實務上不會再命中，保留作歷史。

#### #007 · 2026-05-05 · 升格自 3 筆 learning-log · #認知性 #self-review #cross-source #依賴表盲區

- **模式**：Single-Perspective Self-Review Blind Spot。執行者對自己工作的審查有系統性盲點，不論「執行者」是 LLM、session、還是同 session 累積多步操作，self-review 都會漏看自己沒主動檢查的維度
- **觸發情境**：(a) 對「方法論 / 評分 / 評估」類認知性產出做自我審查 / (b) 接續執行跨 session 計畫時預設信任前 session 寫的計畫前提 / (c) 累積多 commit 工作完成時沒主動跑 CLAUDE.md 依賴表 walk / (d) LLM 自評「我做的這套方法論 / 評估很好」類陳述（無外部 baseline）
- **預防做法**：(a) 對「方法論評估 / 計畫前提 / 自評」類認知性產出，不能 single-source 拍板，至少需 cross-LLM review、人類校準、或同 LLM 不同 session 盲評其一；(b) 多 commit 工作完成時主動跑「依賴表 walk」；(c) 接續跨 session 計畫時開工前對「計畫的核心前提」做字面證據掃描；(d) 自評類產出視為 B 級證據，標註「待 cross-source 驗證」
- **檢測信號**：設計引用「之前 session 的計畫」「我之前評估過」類來源 → 需附 cross-source 驗證否則 medium；「方法論 / 自評 / review」類認知性產出無 cross-source 證據 → high；用戶提示「奇怪 / 不對 / 漏了什麼」→ 質疑熔斷 + 強制 walk 依賴表
- **歷史證據**：2026-05-04 自評漏看 5 個 bug 由另一 LLM 補回 + 2026-05-05 兩次同 LLM 漏看。2026-05-19 兩次實戰複測漏看率 50% / 67%。完整內容見 `.claude-loop/learning-log.md`
- **v8 註**：這是全 repo 唯一有量化證據的機制，已固化為 CLAUDE.md「方法論修改的硬規則」。

## 單一事件

> 一次性的 bug 或踩坑。累積 ≥ 3 次同類根因再考慮升格。

### 記錄格式

```markdown
#### [簡短問題標題]

- **時間**：YYYY-MM-DD
- **階段**：設計 / 實作 / 審查 / 測試
- **嚴重度**：high / medium / low
- **問題描述**：發生了什麼，錯誤訊息是什麼
- **根本原因**：為什麼會發生
- **解決方式**：怎麼修的
- **學到的教訓**：下次怎麼避免
```
