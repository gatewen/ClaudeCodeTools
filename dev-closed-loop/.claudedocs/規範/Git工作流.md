# Git 工作流

## 基本原則

閉環流程跟 Git 要配合好。核心原則就三個：

1. **完成一個閉環就 commit 一次** — 不要寫了一大堆才 commit
2. **要做有風險的改動前先 commit** — 留個還原點
3. **大功能開分支** — 不要在主線上亂改

## 閉環與 commit 的對應

### 標準流程

```
功能需求
  ↓
git checkout -b feature/功能名稱     ← 開分支
  ↓
[函式 A 閉環] → 自証通過 → git commit  ← 每個閉環一個 commit
[函式 B 閉環] → 自証通過 → git commit
[函式 C 閉環] → 自証通過 → git commit
  ↓
[模組閉環] → 自証通過 → git commit     ← 模組層級也 commit
  ↓
git merge / PR                         ← 合回主線
```

### commit message 格式

帶上自証結果，讓別人一眼知道這個 commit 的品質狀態：

```
feat: 新增用戶驗證函式

[自証通過] 設計-實作 ✅ | 測試覆蓋 ✅ | 檢核閉合 ✅ | 產出完整 ✅

- 3 個邊界條件全覆蓋
- 2 個錯誤處理全覆蓋
- 檢核報告 0 個未處理問題
```

如果自証有條件通過（例如 low 問題未處理）：

```
feat: 新增用戶驗證函式

[自証通過*] 設計-實作 ✅ | 測試覆蓋 ✅ | 檢核閉合 ⚠️ | 產出完整 ✅

- 1 個 low 問題暫不處理（風格建議，不影響功能）
```

## 什麼時候要先 commit

在做以下事情**之前**，先把目前的狀態 commit 起來：

| 情境 | 為什麼要先 commit |
|------|-----------------|
| 要重構一大段程式碼 | 改壞了可以還原 |
| 要改架構設計 | 設計改了可能連帶改很多地方 |
| 閉環的斷點被觸發（要回去改） | 保存目前狀態，commit message 標 `[斷點A]` 或 `[斷點B]`，方便追蹤 |
| 要試不確定能不能成功的做法 | 失敗了可以 rollback |

## 分支策略

| 情境 | 做法 |
|------|------|
| 新功能開發 | 開 `feature/功能名稱` 分支 |
| 修 bug | 小 bug 直接在主線 commit；大 bug 開 `fix/問題描述` 分支 |
| 想試一個不確定的方案 | 開 `experiment/嘗試內容` 分支 |
| 閉環回退超過 2 次 | 考慮開新分支重來，不要在原地一直改 |

## 不要做的事情

- **不要一個 PR 裡面塞 10 個函式的閉環** — 太大了沒人想看，一個功能一個 PR
- **不要 commit 自証沒通過的程式碼** — 除非你有明確標註「WIP」
- **不要用 `git add .`** — 可能會把暫存檔、敏感資料一起加進去
- **不要 force push 到共用分支** — 會把別人的工作搞丟
