# 產出物格式

CLAUDE.md 要 Claude 產出設計規格、審查發現、追溯表時，用這裡的最小格式。目的只有一個：讓設計、實作、測試三處引用同一個編號，事後對得起來。

## ID 系統

| 前綴 | 含義 | 誰定義 | 誰引用 |
|------|------|--------|--------|
| **BC-x** | 行為契約：在什麼條件下、系統做什麼、預期結果 | 設計 | 實作註解、測試名稱、追溯表 |
| **R-x** | 審查發現：high 必修 / medium 用戶決策 / low 摘要 | 審查 | 修正 commit、追溯表 |

其餘（EH 錯誤處理、IF 介面契約、CR 變更請求）按需在設計規格內 inline 寫，不強制獨立編號。

## 設計規格（中型 3-5 行，大型可展開）

```markdown
## 設計：{功能名}

**目標**：一句話。
**觸及**：{檔案或模組清單}。因果鏈：{呼叫者 N 個，要連動的 / 不需要的理由}；重複定義：{N 處 / 無}
**行為契約**：
- BC-1：{條件} → {行為} → {預期結果}
- BC-2：…
**錯誤處理**（有外部 I/O 時）：{什麼錯誤 → 怎麼處理 → 用戶看到什麼}
**取捨**：{為什麼選這個做法、放棄了什麼}
**教訓查詢**：命中 #X / 無
```

BC-x 的寫法要能直接變成測試名稱。「系統應正確處理邊界」不合格；「輸入為空字串時回傳 Err(EmptyInput)，不 panic」合格。

## 審查發現

```markdown
## 審查：{範圍}

| ID | 嚴重度 | 位置 | 問題 | 建議 |
|----|--------|------|------|------|
| R-1 | high | src/x.ts:42 | … | … |
| R-2 | medium | … | … | … |

low：{N 條，一句話摘要}
判定：pass / fix-required
```

- **high**：會導致錯誤行為、安全問題、或設計與實作不一致。必修。
- **medium**：可改善但不影響正確性。列給用戶決定。
- **low**：風格。合併摘要，不逐條。
- **by-design**：刻意取捨，寫明理由，不計入判定。

## 追溯表（中型任務測試通過後、commit 前）

```markdown
| BC | 實作 | 測試 |
|----|------|------|
| BC-1 | ✅ src/x.ts:42 | ✅ test_x_empty_input |
| BC-2 | ✅ src/x.ts:58 | ❌ 無 |
```

任何 ❌ 不 commit。大型任務可用 `/dev-verify` 做同樣的事並加上反向遍歷（找死碼、未實作、範圍蔓延）。

## 學習日誌（`.claude-loop/learning-log.md`）

一行一筆，只記導致重做的事件：

```markdown
- 2026-09-03 · {功能} · 根因：{一句話} · 下次：{一句話避免做法}
```

同類根因累積 3 筆，提議升格到 `.claudedocs/records/問題追蹤.md` 警惕模式段。

## workflow 產出物位置

`/dev-design` `/dev-review` `/dev-verify` 的報告寫入 `.claude-loop/artifacts/`：`P1-design-spec.md`、`P3-review.md`、`P5-verify.md`。檔名前綴沿用舊版習慣，沒有其他含義。
