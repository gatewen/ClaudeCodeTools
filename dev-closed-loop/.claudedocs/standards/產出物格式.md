# 產出物格式

> **⚠️ 注意**：CLAUDE.md 中的格式定義為執行權威（Claude 只讀 CLAUDE.md）。本文件是給人類閱讀的補充說明，內容相同但如有出入，以 CLAUDE.md 為準。

## 為什麼要統一格式

自証師的工作是比對不同階段的產出物有沒有矛盾。
如果每次寫出來的東西格式都不一樣，比對就會很困難。
所以每個階段的產出物都有固定格式，照著寫就好。

## 格式裡的 ID 系統

每個邊界條件和錯誤處理都有編號（BC-1、EH-1），
後面的階段用這些編號來引用，這樣自証師才能精確比對。

例如：設計規格寫了 BC-1（空輸入），測試報告也要寫 BC-1，
自証師就能確認「BC-1 有設計、有實作、有測試」。

## 設計規格（Phase 1 架構師產出）

```markdown
## 📐 設計規格

### 目標
[一句話說明這段程式碼要解決什麼問題]

### PRD 需求分解（若有 PRD 時必填）

| PRD# | PRD 來源段落 | 可驗證的需求陳述 |
|------|------------|----------------|
| PRD#1 | [例如：註冊功能] | [例如：系統接受 email + 密碼，建立帳號] |
| PRD#2 | [例如：註冊功能] | [例如：email 已存在時拒絕並回報衝突] |

### 函式簽名
- 名稱：[函式名]
- 參數：

| 名稱 | 型別 | 約束條件 | 必填 |
|------|------|---------|------|

- 回傳值：

| 型別 | 說明 |
|------|------|

### 邊界條件

| ID | 條件描述 | 預期行為 | 來源（若有 PRD） |
|----|---------|---------|-----------------|
| BC-1 | [例如：輸入為空字串] | [例如：回傳預設值] | ← PRD#1 |
| BC-2 | [例如：數字超過上限] | [例如：拋出 RangeError] | ← PRD#2 |

### 錯誤處理

| ID | 錯誤類型 | 處理方式 | 來源（若有 PRD） |
|----|---------|---------|-----------------|
| EH-1 | [例如：網路逾時] | [例如：重試 3 次後拋出錯誤] | ← PRD#1 |
| EH-2 | [例如：檔案不存在] | [例如：回傳 null 並記錄 warning] | ← PRD#2 |

### 設計決策
[為什麼這樣設計，排除了什麼替代方案]
```

## 設計審查報告（Phase 1b 獨立設計審查產出）

```markdown
## 🔬 設計審查報告

- 審查對象：[函式/模組名稱]
- 審查時間：[YYYY-MM-DD HH:MM]
- 審查方式：獨立子 agent（不繼承主對話 context）

### 挑戰式審查

| ID | 嚴重度 | 審查項目 | 問題描述 | 替代方案建議 |
|----|--------|---------|---------|-------------|
| DR-1 | high/medium | [例如：架構選型] | [為什麼現方案有問題] | [更優的替代做法] |

### 驗證式審查

| ID | 嚴重度 | 審查項目 | 問題描述 | 建議修正 |
|----|--------|---------|---------|---------|
| DR-2 | high/medium/low | [例如：BC-x 覆蓋度] | [遺漏了什麼邊界] | [建議補充的 BC-x] |

### 嚴重度定義
- **high**：架構有明顯缺陷、遺漏關鍵邊界情境、或存在明顯更優替代方案 → 必須回 Phase 1 修正
- **medium**：設計可改善但不影響正確性，或有值得考慮的替代方向 → 呈現給用戶決定
- **low**：風格偏好或微小建議 → 合併摘要記錄
```

注意「審查方式」欄位——強調這是獨立審查，不是同一個 agent 自己檢查自己。

**寫入位置**：子 agent 必須將此報告寫入 `.claude-loop/artifacts/P1b-design-review.md`。Phase 5 Part C 會驗證此檔案存在。

## 檢核報告（Phase 3 檢核師產出）

```markdown
## 🔍 檢核報告

- 檢核對象：[函式/模組名稱]
- 檢核時間：[YYYY-MM-DD HH:MM]

| ID | 嚴重度 | 位置 | 問題描述 | 建議修正 | 狀態 |
|----|--------|------|---------|---------|------|
| R-1 | high | [檔案:行數] | [問題是什麼] | [建議怎麼改] | open/resolved |
| R-2 | medium | [檔案:行數] | [問題是什麼] | [建議怎麼改] | open/resolved |
| R-3 [TypeScript] | high | [檔案:行數] | [語言專屬問題] | [建議怎麼改] | open/resolved |

### 嚴重度定義
- **high**：邏輯錯誤、安全漏洞、跟設計規格不符 → 一定要修才能往下走
- **medium**：品質問題、可維護性風險 → 建議修，不修的話要在自証時說明
- **low**：風格建議、微小改進 → 記錄就好
```

## 測試報告（Phase 4 測試師產出）

```markdown
## 🧪 測試報告

- 測試對象：[函式/模組名稱]
- 測試時間：[YYYY-MM-DD HH:MM]
- 邊界條件覆蓋：X / Y
- 錯誤處理覆蓋：X / Y

| 測試名稱 | 對應規格 ID | 結果 | 說明 |
|---------|------------|------|------|
| [test_empty_input] | BC-1 | pass/fail | [補充說明] |
| [test_overflow] | BC-2 | pass/fail | [補充說明] |
| [test_network_timeout] | EH-1 | pass/fail | [補充說明] |
| [test_happy_path] | — | pass/fail | [正常路徑測試] |
```

注意「對應規格 ID」欄位——這就是用來跟設計規格做交叉比對的。

**寫入位置**：品質審查子 agent 寫入 `.claude-loop/artifacts/P3-quality-review.md`，安全審查子 agent 寫入 `.claude-loop/artifacts/P3-security-review.md`。Phase 5 Part C 會驗證這兩個檔案存在。

## 自証結果（Phase 5 自証師產出）

```markdown
## ✅ 自証結果

- 自証對象：[函式/模組名稱]
- 自証時間：[YYYY-MM-DD HH:MM]
- **判定：通過 / 不通過**

| 維度 | 狀態 | 證據 | 缺口描述 |
|------|------|------|---------|
| PRD-設計覆蓋（若有 PRD） | ✅/❌ | [例如：PRD#1→BC-1, PRD#2→BC-2+EH-1，全覆蓋] | [若有缺口寫這裡] |
| 設計審查閉合 | ✅/❌ | [例如：DR-1(high) 已修正、DR-2(medium) 用戶決定不改] | [若有缺口寫這裡] |
| 設計-實作一致性 | ✅/❌ | [例如：BC-1, BC-2, EH-1, EH-2 均有對應實作] | [若有缺口寫這裡] |
| 實作-測試覆蓋 | ✅/❌ | [例如：邊界條件 2/2、錯誤處理 2/2] | [若有缺口寫這裡] |
| 檢核-修正閉合 | ✅/❌ | [例如：R-1(high) 已修正、無未處理問題] | [若有缺口寫這裡] |
| 產出物完整性 | ✅/❌ | [例如：設計規格 ✅ 程式碼 ✅ 檢核報告 ✅ 測試報告 ✅] | [若有缺口寫這裡] |

（若不通過）
### 回退建議
- 回退目標：Phase X
- 原因：[具體說明哪裡不一致]
- 修正方向：[建議怎麼修]
```

## 委派產出物檔案（`.claude-loop/artifacts/`）

完整閉環必建 `.claude-loop/artifacts/` 目錄。每個委派 Phase 的子 agent 必須將產出寫入對應檔案，Phase 5 Part C 在步驟 8 前驗證檔案存在性。

| 檔案名稱 | 產出 Phase | 寫入者 |
|---------|-----------|--------|
| `P1b-design-review.md` | Phase 1b | 設計審查子 agent |
| `P3-quality-review.md` | Phase 3 | 品質審查子 agent |
| `P3-security-review.md` | Phase 3 | 安全審查子 agent |
| `P5A-traceability.md` | Phase 5 Part A | 追溯檢查子 agent |
| `P5B-reverse-analysis.md` | Phase 5 Part B | 反向分析子 agent |

每個檔案的內容格式與對應 Phase 的產出物格式相同（見上方各節）。用戶跳過 Phase 1b 時，`P1b-design-review.md` 不需存在。
