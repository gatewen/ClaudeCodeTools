# 產出物格式

> **⚠️ 注意**：CLAUDE.md 中的格式定義為執行權威（Claude 只讀 CLAUDE.md）。本文件是給人類閱讀的補充說明，內容相同但如有出入，以 CLAUDE.md 為準。

## 為什麼要統一格式

自証師的工作是比對不同階段的產出物有沒有矛盾。
如果每次寫出來的東西格式都不一樣，比對就會很困難。
所以每個階段的產出物都有固定格式，照著寫就好。

## 格式裡的 ID 系統

每個邊界條件和錯誤處理都有編號（BC-1、EH-1），
後面的階段用這些編號來引用，這樣自証師才能精確比對。

例如：設計規格寫了 BC-1（空輸入），測試報告也要寫 BC-1，
自証師就能確認「BC-1 有設計、有實作、有測試」。

## 設計規格（Phase 1 架構師產出）

```markdown
## 📐 設計規格

### 目標
[一句話說明這段程式碼要解決什麼問題]

### 函式簽名
- 名稱：[函式名]
- 參數：

| 名稱 | 型別 | 約束條件 | 必填 |
|------|------|---------|------|

- 回傳值：

| 型別 | 說明 |
|------|------|

### 邊界條件

| ID | 條件描述 | 預期行為 |
|----|---------|---------|
| BC-1 | [例如：輸入為空字串] | [例如：回傳預設值] |
| BC-2 | [例如：數字超過上限] | [例如：拋出 RangeError] |

### 錯誤處理

| ID | 錯誤類型 | 處理方式 |
|----|---------|---------|
| EH-1 | [例如：網路逾時] | [例如：重試 3 次後拋出錯誤] |
| EH-2 | [例如：檔案不存在] | [例如：回傳 null 並記錄 warning] |

### 設計決策
[為什麼這樣設計，排除了什麼替代方案]
```

## 檢核報告（Phase 3 檢核師產出）

```markdown
## 🔍 檢核報告

- 檢核對象：[函式/模組名稱]
- 檢核時間：[YYYY-MM-DD HH:MM]

| ID | 嚴重度 | 位置 | 問題描述 | 建議修正 | 狀態 |
|----|--------|------|---------|---------|------|
| R-1 | high | [檔案:行數] | [問題是什麼] | [建議怎麼改] | open/resolved |
| R-2 | medium | [檔案:行數] | [問題是什麼] | [建議怎麼改] | open/resolved |
| R-3 [TypeScript] | high | [檔案:行數] | [語言專屬問題] | [建議怎麼改] | open/resolved |

### 嚴重度定義
- **high**：邏輯錯誤、安全漏洞、跟設計規格不符 → 一定要修才能往下走
- **medium**：品質問題、可維護性風險 → 建議修，不修的話要在自証時說明
- **low**：風格建議、微小改進 → 記錄就好
```

## 測試報告（Phase 4 測試師產出）

```markdown
## 🧪 測試報告

- 測試對象：[函式/模組名稱]
- 測試時間：[YYYY-MM-DD HH:MM]
- 邊界條件覆蓋：X / Y
- 錯誤處理覆蓋：X / Y

| 測試名稱 | 對應規格 ID | 結果 | 說明 |
|---------|------------|------|------|
| [test_empty_input] | BC-1 | pass/fail | [補充說明] |
| [test_overflow] | BC-2 | pass/fail | [補充說明] |
| [test_network_timeout] | EH-1 | pass/fail | [補充說明] |
| [test_happy_path] | — | pass/fail | [正常路徑測試] |
```

注意「對應規格 ID」欄位——這就是用來跟設計規格做交叉比對的。

## 自証結果（Phase 5 自証師產出）

```markdown
## ✅ 自証結果

- 自証對象：[函式/模組名稱]
- 自証時間：[YYYY-MM-DD HH:MM]
- **判定：通過 / 不通過**

| 維度 | 狀態 | 證據 | 缺口描述 |
|------|------|------|---------|
| 設計-實作一致性 | ✅/❌ | [例如：BC-1, BC-2, EH-1, EH-2 均有對應實作] | [若有缺口寫這裡] |
| 實作-測試覆蓋 | ✅/❌ | [例如：邊界條件 2/2、錯誤處理 2/2] | [若有缺口寫這裡] |
| 檢核-修正閉合 | ✅/❌ | [例如：R-1(high) 已修正、無未處理問題] | [若有缺口寫這裡] |
| 產出物完整性 | ✅/❌ | [例如：設計規格 ✅ 程式碼 ✅ 檢核報告 ✅ 測試報告 ✅] | [若有缺口寫這裡] |

（若不通過）
### 回退建議
- 回退目標：Phase X
- 原因：[具體說明哪裡不一致]
- 修正方向：[建議怎麼修]
```
