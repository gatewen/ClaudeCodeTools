# 產出物格式

> **⚠️ 注意**：CLAUDE.md 中的格式定義為執行權威（Claude 只讀 CLAUDE.md）。本文件是給人類閱讀的補充說明，內容相同但如有出入，以 CLAUDE.md 為準。

## v7.0.0 定位

> 本文件的產出物模板沿用 v6.x 的 Phase 標籤（Phase 1 架構師 / Phase 3 檢核師 / Phase 5 自證師…）。v7.0.0 起這些環節由 workflow 編排承擔：Phase 1+1b → `/dev-design`、Phase 3 → `/dev-review`、Phase 5 → `/dev-verify`（對映見 [五階段閉環流程](../process/五階段閉環流程.md)）。**模板本身仍有效**——workflow agent 與中型輕量流程都按這些格式產出。

## 為什麼要統一格式

自證（`/dev-verify` 或中型迷你追溯）要比對不同產出物之間有沒有矛盾。格式統一，比對才精確。

## ID 系統（v7 簡化）

v7.0.0 把 ID 系統收斂為兩個主軸：

- **BC-x（行為契約 / 邊界條件）**：可驗證的行為預期。**主軸**——workflow schema 可直接強制，自證 / 迷你追溯逐項追蹤。
- **R-x（審查發現）**：審查 / 檢核發現的問題，severity high → 必修 / medium → 用戶決策 / low → 摘要。**主軸**。
- **其餘（EH-x / DR-x / IF-x / CR-x）按需 inline 使用，不強制獨立編號**：錯誤處理、設計審查發現、介面契約、契約變更——有需要時沿用下方模板的編號格式，沒需要時併入 BC-x / R-x 敘述即可。

例如：設計規格寫了 BC-1（空輸入），測試 / 自證也引用 BC-1，就能確認「BC-1 有設計、有實作、有測試」。

## ID ↔ 失誤類型對應表（v6.2.0 K-10 新增）

> 每種 ID 出問題時最常對應到哪類 failure_type — 用於 learning-log 條目快速判定。

| ID 系統 | 用途 | 常見 failure_type | 邊界情境 |
|---------|------|-------------------|----------|
| BC-x（邊界條件） | 設計規格定義行為邊界 | judgment_failure | verification_failure |
| EH-x（錯誤處理） | 設計規格定義異常處理 | judgment_failure | verification_failure |
| R-x（檢核發現） | Phase 3 程式碼問題 | verification_failure | judgment_failure |
| R-style（風格漂移） | v6.1.0 R-x 子類 | verification_failure | tooling_failure |
| DR-x（設計審查） | Phase 1b 設計缺陷 | judgment_failure | process_failure |
| IF-x（介面契約） | 跨模組 API 契約 | judgment_failure | process_failure |
| CR-x（契約變更） | 介面變更管理 | process_failure | judgment_failure |

**用法**：常見對應 → 直接填；屬邊界情境 → 「教訓」欄附判定理由；tooling_failure（hook bug / lint 誤判）跨所有 ID 種類獨立判斷不查表；K-14 擴充後「事實誤判」事件的 failure_type 不變（judgment 主、verification 次）。

```markdown
- 參數：

| 型別 | 說明 |

| ID | 條件描述 | 預期行為 | 驗證層級 | 來源（若有 PRD） |
```

```
| BC-1 | [例如：token 過期] | [例如：回傳 401 並觸發刷新] | [testable] | ← PRD#1 |
```

**驗證層級說明**：
- `[testable]`：純邏輯、可程式化驗證 → Phase 4 必須有自動化測試
- `[visual-only]`：渲染、動畫、UI 佈局 → Phase 3 品質審查以 code review 驗證，Phase 4 免除自動化測試
- `[framework-dependent]`：需要框架 runtime → 建議拆分純邏輯方法，無法拆分的部分按 `[visual-only]` 處理

**領域預設**：預設為 `[testable]` 的領域（後端 API / CLI / 系統程式）無需逐項標注驗證層級，只需標注例外（即 `[visual-only]` 或 `[framework-dependent]` 的項目）。

## 設計審查報告（Phase 1b 獨立設計審查產出）

```markdown
## 🔬 設計審查報告

- 審查對象：[函式/模組名稱]
- 審查時間：[YYYY-MM-DD HH:MM]
- 審查方式：獨立子 agent（不繼承主對話 context）
- 審查輪次：第 N 輪（最多 3 輪）

### 挑戰式審查

| ID | 嚴重度 | 審查項目 | 問題描述 | 替代方案建議 |
|----|--------|---------|---------|-------------|
| DR-1 | high/medium/arch-risk | [例如：架構選型] | [為什麼現方案有問題] | [更優的替代做法] |

### 驗證式審查

| ID | 嚴重度 | 審查項目 | 問題描述 | 建議修正 |
|----|--------|---------|---------|---------|
| DR-2 | high/medium/low | [例如：BC-x 覆蓋度] | [遺漏了什麼邊界] | [建議補充的 BC-x] |

### 嚴重度定義
- **high**：架構有明顯缺陷、遺漏關鍵邊界情境、或存在明顯更優替代方案 → 必須回 Phase 1 修正
- **medium**：設計可改善但不影響正確性，或有值得考慮的替代方向 → 呈現給用戶決定
- **low**：風格偏好或微小建議 → 合併摘要記錄
- **arch-risk**：架構設計存在長期風險但不影響當前正確性 → 不觸發閘門/斷點，Phase 5 追蹤

### 迭代狀態
- 本輪結論：通過 / 需回退修正
- 終止條件：本輪無新 high → 通過
```

注意「審查方式」欄位——強調這是獨立審查，不是同一個 agent 自己檢查自己。

**寫入位置**：子 agent 必須將此報告寫入 `.claude-loop/artifacts/P1b-design-review.md`。Phase 5 Part C 會驗證此檔案存在。

## 檢核報告（Phase 3 檢核師產出）

```markdown
## 🔍 檢核報告

- 檢核對象：[函式/模組名稱]
- 檢核時間：[YYYY-MM-DD HH:MM]
- 安全審查狀態：已執行 / by-design 跳過（[原因]）

| ID | 嚴重度 | 位置 | 問題描述 | 建議修正 | 狀態 |
|----|--------|------|---------|---------|------|
| R-1 | high | [檔案:行數] | [問題是什麼] | [建議怎麼改] | open/resolved |
| R-2 | medium | [檔案:行數] | [問題是什麼] | [建議怎麼改] | open/resolved |
| R-3 [TypeScript] | high | [檔案:行數] | [語言專屬問題] | [建議怎麼改] | open/resolved |
| R-4 | arch-risk | [檔案:行數] | [架構長期風險] | [建議方向] | tracked |
| R-style | medium | [檔案:行數] | [style 漂移：quote/type hints/naming/縮排/註解] | [改回對齊既有風格] | open/resolved |

### 嚴重度定義
- **high**：邏輯錯誤、安全漏洞、跟設計規格不符 → 一定要修才能往下走
- **medium**：品質問題、可維護性風險 → 建議修，不修的話要在自證時說明
- **low**：風格建議、微小改進 → 記錄就好
- **arch-risk**：架構設計存在長期風險但不影響當前正確性 → 不觸發閘門/斷點，Phase 5 追蹤
- **R-style**（v6.1.0 新增 · 獨立子類別）：style 漂移專屬編號，跟 R-x medium 並列；只報告改動引入的不一致，不報告既有不一致。詳見 code-reviewer.md 步驟 5.5
```

## 測試報告（Phase 4 測試師產出）

```markdown
## 🧪 測試報告

- 測試對象：[函式/模組名稱]
- 測試時間：[YYYY-MM-DD HH:MM]
- [testable] 覆蓋：X / Y
- [visual-only] 項：N 項（驗證方式：code review）
- [framework-dependent] 項：N 項（驗證方式：[拆分純邏輯/code review]）

| 測試名稱 | 對應規格 ID | 驗證層級 | 結果 | 說明 |
|---------|------------|---------|------|------|
| [test_empty_input] | BC-1 | [testable] | pass/fail | [補充說明] |
| [test_overflow] | BC-2 | [testable] | pass/fail | [補充說明] |
| [test_network_timeout] | EH-1 | [testable] | pass/fail | [補充說明] |
| — | BC-3 | [visual-only] | code review ✅ | [視覺驗證說明] |
| [test_happy_path] | — | [testable] | pass/fail | [正常路徑測試] |
```

注意「驗證層級」欄位——區分自動化測試和替代驗證方式，讓自證師知道每項的驗證方式。

**寫入位置**：品質審查子 agent 寫入 `.claude-loop/artifacts/P3-quality-review.md`，安全審查子 agent（若執行）寫入 `.claude-loop/artifacts/P3-security-review.md`。Phase 5 Part C 會驗證這些檔案存在。

```markdown
| 產出物完整性 | ✅/❌ | [例如：設計規格 ✅ 程式碼 ✅ 檢核報告 ✅ 測試報告 ✅] | [若有缺口寫這裡] |

（若不通過）
### 回退建議
- 回退目標：Phase X
- 原因：[具體說明哪裡不一致]
- 修正方向：[建議怎麼修]
```

## 迷你追溯（精簡閉環步驟 4.5 · 主 agent 產出）

精簡閉環（中型任務）在測試通過後、commit 前，由主 agent 執行的輕量級正向追溯。不委派子 agent，不寫入 artifacts 檔案，直接在畫面輸出。

```markdown
🔍 [迷你追溯] {功能名稱}

### 正向覆蓋
| BC/EH | 描述 | 實作 | 測試 |
|-------|------|------|------|
| BC-1 | [描述] | ✅ src/foo.ts:42 | ✅ test_bc1 |
| BC-2 | [描述] | ✅ src/bar.ts:18 | ✅ test_bc2 |
| EH-1 | [描述] | ✅ src/foo.ts:95 | ✅ test_eh1 |
| BC-3 | [描述] | ✅ src/ui/comp.tsx:30 | [visual-only] code review ✅ |
覆蓋率：X/Y (Z%)

### 品質審查閉合
| R-x | 嚴重度 | 狀態 |
|-----|--------|------|
| R-1 | high   | ✅ 已修（步驟 3 回退確認） |
| R-2 | medium | ⚠️ [描述] — 用戶決策：[修/不修+原因] |

### 判定
✅ 通過 → 進升格檢查 → commit / ❌ 不通過 → [回退目標和原因]
```

**填寫規則**：
- 每個 BC-x/EH-x 都必須出現在表格中，不可省略
- 實作欄：✅ + `檔案:行號`，或 ❌ + 「未實作」
- 測試欄：✅ + 測試名稱；`[visual-only]`/`[framework-dependent]` 標注替代驗證方式
- R-x medium 的用戶決策必須記錄（修 / 不修+原因），不可空白
- 步驟 3 無 R-x 時，品質審查閉合 section 寫「無 R-x」

**跟完整閉環 Phase 5 的差異**：迷你追溯只做正向覆蓋和品質審查閉合，不做反向分析、交叉比對、arch-risk 追蹤。

### 迷你追溯通過後的升格檢查格式

迷你追溯 ✅ 通過後、commit 前，主 agent 直接執行升格檢查（無 verifier sub-agent）。畫面輸出：

```markdown
🛡️ [升格檢查] 兩層教訓架構

### learning-log 分組計數
| 根因關鍵字 | 累積次數 | 已升格？ |
|-----------|---------|---------|
| {根因類型 A} | 4 | ❌ 未升格 |
| {根因類型 B} | 2 | — |
| {根因類型 C} | 1 | — |

### 升格候選（≥ 3 次且未升格）
- 候選 #1：{根因類型 A}（累積 4 次）
  - 觸發情境（草稿）：...
  - 預防做法（草稿）：...
  - 檢測信號（草稿）：...
  - 歷史證據：[時間戳列表]
  - **用戶決策**：[AskUserQuestion 結果 — 升格 / 不升格 + 原因]

### 處理結果
- 升格 N 筆 → 已寫入問題追蹤.md #XXX, #YYY
- 不升格 M 筆 → learning-log 對應條目已加註「[已評估不升格]」
- 或：無升格候選（最高頻根因 N 次未達 3 次門檻）
```

**填寫規則**：
- 無 learning-log 條目 → 寫「無學習日誌」並跳過後續

## 模組登記（`.claude-loop/module-registry.md`）

模組登記是專案級別的模組索引——記錄「有什麼模組、各自的分層和 API、能不能複用」。
不是文檔（詳細設計在 `design-spec.md`），而是像圖書館的目錄卡片，方便查詢和複用。

**建立時機**：第一個模組完成閉環（中型以上）時建立，或用戶要求時建立。
**登記條件**：中型以上閉環通過 **或** 用戶明確要求。

```markdown
# 模組登記

> 專案模組索引。Phase 1 前查詢可複用功能層，閉環通過後登記新模組。

### [模組名] — [一句話職責]
- **分層**：純功能 / 功能+UI
- **功能層路徑**：[src/services/xxx/]
- **功能層 API**：[公開函式簽名摘要]
- **UI 層路徑**：[src/components/xxx/]（純功能模組省略此行）
- **依賴**：[依賴的其他模組，標注 IF-x]
- **被依賴**：[依賴此模組的其他模組]
- **版本**：v[n]（[變更摘要]）
- **閉環**：✅ 自證通過 [YYYY-MM-DD] / 精簡閉環通過 [YYYY-MM-DD]
```

**更新規則**：
- 模組升級（重跑閉環）→ 版本號遞增 + 更新變更摘要和 API
- 新模組依賴此模組 → 更新「被依賴」欄位
- 公開 API 有破壞性變更 → 同時走 CR-x 流程

**分層說明**：
- **純功能**：無使用者介面。核心邏輯、服務、工具函式庫等
- **功能+UI**：有使用者介面。功能層（核心邏輯，不依賴 UI 框架）+ UI 層（呈現/互動，可依賴功能層 API）

## 學習日誌（`.claude-loop/learning-log.md`）

學習日誌記錄閉環中**導致回頭重做的事件**——失敗根因、誤判模式、踩坑教訓。
不是完整報告（那在 `.claude-loop/artifacts/`），而是教訓索引，用於 Phase 1 前查詢歷史。
**只記有學習價值的事**：斷點觸發、DR-x high、熔斷、任務升級、Phase 5 不通過。一次順利通過的閉環只留統計行。

**建立時機**：第一次閉環中有事件記錄，或第一次閉環通過時建立。
**追加時機**：斷點/熔斷觸發時立即追加（教訓不等到結束）；閉環通過時在 commit 前追加完整條目。

### 事件條目格式（斷點/熔斷觸發時立即追加）

```markdown
**[YYYY-MM-DD HH:MM] [code-reviewer] [斷點 A] {功能名稱} — R-{x} high**
- **failure_type**: {process_failure | judgment_failure | verification_failure | tooling_failure}
- 問題：{什麼出錯了}
- 原因：{為什麼會出錯——根因，不是現象}
- 修改：{怎麼修的，檔案:行號}
- 教訓：{下次要注意什麼}
```

`[agent-name]` 標籤對照：斷點 A → `[code-reviewer]` 或 `[security-reviewer]` | 斷點 B → `[tester]` | DR-x high 回退 → `[design-reviewer]` | 熔斷 → `[circuit-breaker]` | **事實誤判** → `[architect]` 或 `[requirements-analyst]`（2026-04-22 v5.22.3 新增）。
Agent 被調用前會 Grep 自己標籤的條目，從歷史教訓中學習。

斷點 B、DR-x high 回退、熔斷觸發同格式，標題標記不同事件類型。
熔斷條目額外記錄「累積失敗模式」和「用戶決策」。

#### 事件類型擴展：`[事實誤判]`（2026-04-22 v5.22.3 新增）

**觸發時機**（任一觸發即追加）：
- 用戶質疑熔斷觸發（見 CLAUDE.md Section 12）
- Phase 1b design-reviewer 因 Step 0a / 0b 不合規提出 DR-x high
- Phase 5 verifier 事實前提追溯發現弱證據（v6.x verifier 內部機制；v7 由 `/dev-verify` 承擔）
- 主 agent 自行發現先前推論為誤（例：用戶指出 memory 有誤後重審）

**failure_type 歸類**：
- 預設 `judgment_failure`（架構師把推論當事實）
- 若是 reviewer 漏抓（Phase 1b 過關但 Phase 5 才發現）→ `verification_failure`

**條目範例**：

```markdown
**[2026-04-22 11:31] [architect] [事實誤判] pig_server 架構分析 — 誤判 pypi 倉庫為 GS**
- **failure_type**: judgment_failure
- 問題：將 `PypiConfig.cfg` 中 `[pig] ip=52.74.89.132` 認定為 pig_server Game Server 機器，基於此寫入 memory + 產出多段架構分析
- 原因：單線索推論（問題追蹤 #003）+ 忽視字面證據（#004，檔名明寫 "Pypi"）+ 共用值私有化（#005，同 IP 被 6 款遊戲共用）
- 修改：memory 已更正為「pypi package registry」，重新從 Salt Master 線索追蹤真正的 GS
- 教訓：任何「X 是 Y」斷言前跑 Step 0a 字面證據掃描 + Step 0b 共用值檢測；memory 寫入前標注 evidence_level
```

`[事實誤判]` 累積 ≥ 3 次 + 用戶確認 → 升格為新長期警惕模式條目（跟既有升格機制共用 AskUserQuestion 流程）。

#### failure_type 4 類定義（必填欄位，2026-04-18 v5.22.2 新增）

按因果順序排列，每類假設前一類已成立：

| 類型 | 定義 | 典型情境 | 例子 |
|------|------|---------|------|
| **process_failure** | 該做的步驟沒做或執行錯誤——流程本身沒走完 | agent 偷懶、跳閘門、依賴影響分析沒做、規則被忽略 | 「修改 X 沒做因果鏈分析」「Phase 1b 跳了沒理由」「architect 跳過學習查詢」 |
| **judgment_failure** | 流程都走了，但判斷方向錯——做得對但想錯 | 根因錯判、優先級錯、方法選錯、framing 錯置 | 「把 routing 問題當 existence 處理」「選錯 framework」「BC-x 設計 over/under-spec」 |
| **verification_failure** | 流程也走了、判斷也對了，但 review/test 沒抓到——檢查層失職 | reviewer 漏檢、test 漏覆蓋、Phase 5 沒抓到不一致 | 「Phase 3 沒抓到的事 Phase 5 才發現」「測試覆蓋了但 assertion 太鬆」 |
| **tooling_failure** | 工具本身的 bug 或誤判——不是人/規則的問題 | hook 誤擋、skill 出錯、script bug、依賴版本踩雷 | 「incremental-lint 對 .ts 檔案誤判」「hook 因短指令誤觸」 |

**判定原則**：
- 從上往下判定：如果是 process_failure，就不是 judgment_failure（流程沒做完，談不上判斷對錯）
- 邊界案例：選最早出問題的類型。例如 reviewer 漏檢 + 後來 test 也漏 → verification_failure（reviewer 那關先壞）
- 不確定時：在「教訓」欄附一句「failure_type 邊界判定理由」，不另設「uncategorized」類型避免訊號污染

### 閉環完整條目格式（通過後、commit 前追加）

```markdown
### [YYYY-MM-DD] {功能名稱} — {完整/精簡}閉環 ✅

#### 教訓
{如果有斷點/熔斷/升級/Phase 5 不通過 → 彙整上方事件條目的教訓}
{如果全程無事件 → 寫「無（一次通過）」}

#### 統計
DR-x {N}h/{N}m | R-x {N}h/{N}m | 斷點 {A×N/B×N/無} | 預防清單命中 {項目/無}
```

**填寫規則**：
- **事件條目在事件發生時就寫**，不等到閉環結束。這樣即使 session 中斷，教訓不會丟失
- **完整條目在 commit 前寫**，跟程式碼一起 commit（原子操作）
- 教訓 section 彙整已追加的事件條目，不重複內容，用「見上方 [斷點 A] ...」引用即可
- 無事件的閉環：教訓寫「無」，統計照填。不浪費空間
- **只記「導致回頭重做」的事件**。R-x medium 被修了、code-simplifier 建議、lint 修正——這些是系統正常運作，不記

### 模式分析格式

條目 ≥ 5 且用戶同意時執行。分析結果追加到 learning-log.md 末尾：

```markdown
---
## 📊 模式分析 [YYYY-MM-DD]（基於 {N} 筆記錄）

### failure_type 分布（v5.22.2 新增）
| failure_type | 次數 | 佔比 | 說明 |
|-------------|------|------|------|
| process_failure | {N} | {N%} | 流程沒走完——指向「規則執行可靠性」問題 |
| judgment_failure | {N} | {N%} | 判斷方向錯——指向「Phase 1 設計品質」問題 |
| verification_failure | {N} | {N%} | review/test 漏檢——指向「Phase 3/5 reviewer 強度」問題 |
| tooling_failure | {N} | {N%} | 工具 bug——指向「hook/skill 需修補」問題 |

**解讀指引**：哪類佔比高，下一版方法論優化方向就應該對應該類。例如 process_failure 高 → 規則太多/agent 偷懶 → 應簡化規則而非加規則。

### 高頻問題（教訓中出現 ≥ 3 次的根因類型）
| 根因類型 | 出現次數 | failure_type | 建議 |
|---------|---------|--------------|------|
| {例如：resource cleanup 遺漏} | {N} | judgment_failure | 加入預防清單 / 加強 Phase 1 提醒 |

### 預防清單效能
| 清單項目 | 命中次數 | 評估 |
|---------|---------|------|
| {項目} | {N} | 有效 / 從未命中（建議移除或修改） |

### 專案特定模式
- {從教訓中歸納的此專案特有踩坑傾向}
```

## 長期警惕模式（`.claudedocs/records/問題追蹤.md` 升格條目）

長期警惕模式是從 learning-log 升格的高頻問題模式，跨閉環累積，每次 Phase 1 前 architect **必讀**。
**跟 learning-log 的分工**：

| 維度 | learning-log（短期） | 長期警惕模式（長期） |
|------|---------------------|---------------------|
| 範圍 | session 內 / 單一閉環 | 跨閉環 / 專案層級 |
| 寫入時機 | 斷點/熔斷觸發即時寫 + 閉環通過追加 | Phase 5 verifier 升格檢查 + 用戶確認後 |
| 觸發條件 | 失敗事件發生 | 同類根因累積 ≥ 3 次 + 用戶確認 |
| 讀取者 | 各 phase agent grep 自己的 tag | architect Phase 1 起手式必讀 |
| 生命週期 | 跟 commit 走 | 永久保留（除非用戶手動移除） |

### 升格門檻（中等）
- learning-log 同類根因累積 ≥ 3 次
- 未在 問題追蹤.md「長期警惕模式」section 升格過
- Phase 5 verifier 步驟 9b 偵測候選後，主 agent 在 Part C 用 AskUserQuestion 確認
- 用戶選是 → 寫入問題追蹤.md + learning-log 對應條目加註「→ 已升格 #XXX」

### 條目格式

```markdown
### #XXX · YYYY-MM-DD · 升格自 N 筆 learning-log · #tag1 #tag2

- **模式**：[一句話描述高頻問題類型]
- **觸發情境**：[何時容易發生這個問題，具體情境而非抽象詞]
- **預防做法**：[Phase 1 設計時要做什麼，可操作的指令或檢查]
- **檢測信號**：[Phase 3 審查 / Phase 5 自證時要看什麼]
- **歷史證據**：[列出 N 個 learning-log 條目的時間戳] → 完整內容見 .claude-loop/learning-log.md
```

### 編號規則

- 流水遞增（#001, #002, #003 ...）
- 種子條目（外部來源、非升格產出）需標明「升格自 0 筆 learning-log（外部來源 [檔案名] [日期]）」
- 升格寫入後 learning-log 對應條目加註：「→ 已升格 問題追蹤#XXX [YYYY-MM-DD]」（避免重複偵測）

### 寫入流程（主 agent 在 Phase 5 Part C 執行）

1. 讀取 P5AB 報告的「升格候選」section
2. 對每個候選用 AskUserQuestion 詢問「累積到 N 次的 [根因類型] 是否升格為長期警惕模式？」
3. 用戶選是：
   - 在問題追蹤.md「模式記錄」末尾追加新條目（編號 = 既有最大值 + 1）
   - 用 Edit 在 learning-log 對應條目末尾加註「→ 已升格 問題追蹤#XXX [YYYY-MM-DD]」
4. 用戶選否：
   - 在 learning-log 對應條目加註「[已評估不升格 - YYYY-MM-DD]」（避免下次重複問）
   - 不寫入問題追蹤.md

## 事實主張閘門（v5.23.0 新增）

事實主張閘門是 CLAUDE.md Section 11 定義的認知驗證機制（承重核·事實求證）的結構化表格。任何 agent 在以下場景必過此閘門：
- 將推論寫入 memory（特別是 `type: project`）
- 向用戶輸出「X 是 Y」類確定語氣結論（含環境事實：IP / DB 位置 / 服務身份 / 部署結構）
- 作為後續行動（SSH / DB / 部署 / 大範圍修改）的事實前提

**輸出格式**：

```markdown
## 🔵 事實主張閘門

### 主張
{一句話，例：52.74.89.132 是 pig_server 的 GS 機器}

### A 級證據（直接 / literal / self-declaration）
| # | 來源 | 原文 / 關鍵字 | 支持 / 反對 |
|---|------|-------------|-----------|
| A-1 | {檔:行} | {echo 字串 / docstring / filename token 原文} | 支持 / 反對 |

### B 級證據（間接 / 相關性 / 推論）
| # | 來源 | 關聯方式 | 強度 |
|---|------|---------|------|
| B-1 | {檔:行 / workflow 節點} | {SSH / import / reference / deploy target} | 弱 / 中 |

### 反例檢查（Falsification）
- 若主張為真，還應觀察到：{expected observations}
- 若主張為假，會觀察到：{falsification conditions}
- 實際觀察：{what I actually see}
- 反例通過？**是 / 否 / 無法判斷**

### 共用值檢查（若主張涉及 config value）
```
