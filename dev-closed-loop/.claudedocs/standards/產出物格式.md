# 產出物格式

> **⚠️ 注意**：CLAUDE.md 中的格式定義為執行權威（Claude 只讀 CLAUDE.md）。本文件是給人類閱讀的補充說明，內容相同但如有出入，以 CLAUDE.md 為準。

## 為什麼要統一格式

自証師的工作是比對不同階段的產出物有沒有矛盾。
如果每次寫出來的東西格式都不一樣，比對就會很困難。
所以每個階段的產出物都有固定格式，照著寫就好。

## 格式裡的 ID 系統

每個邊界條件和錯誤處理都有編號（BC-1、EH-1），
後面的階段用這些編號來引用，這樣自証師才能精確比對。

例如：設計規格寫了 BC-1（空輸入），測試報告也要寫 BC-1，
自証師就能確認「BC-1 有設計、有實作、有測試」。

## 設計規格（Phase 1 架構師產出）

### 單一函式設計規格

適用於單一函式或小範圍變更的設計。

```markdown
## 📐 設計規格

### 目標
[一句話說明這段程式碼要解決什麼問題]

### PRD 需求分解（若有 PRD 時必填）

| PRD# | PRD 來源段落 | 可驗證的需求陳述 |
|------|------------|----------------|
| PRD#1 | [例如：註冊功能] | [例如：系統接受 email + 密碼，建立帳號] |
| PRD#2 | [例如：註冊功能] | [例如：email 已存在時拒絕並回報衝突] |

### 執行順序（有 update/tick/frame 迴圈時必填）
[虛擬碼等級的步驟順序，標明每步的依賴和副作用]

### 函式簽名
- 名稱：[函式名]
- 參數：

| 名稱 | 型別 | 約束條件 | 必填 |
|------|------|---------|------|

- 回傳值：

| 型別 | 說明 |
|------|------|

### 邊界條件

| ID | 條件描述 | 預期行為 | 驗證層級 | 來源（若有 PRD） |
|----|---------|---------|---------|-----------------|
| BC-1 | [例如：輸入為空字串] | [例如：回傳預設值] | [testable] | ← PRD#1 |
| BC-2 | [例如：數字超過上限] | [例如：拋出 RangeError] | [testable] | ← PRD#2 |
| BC-3 | [例如：角色碰牆] | [例如：停止移動] | [framework-dependent] | |
| BC-4 | [例如：閃爍動畫] | [例如：藍白交替] | [visual-only] | |

### 錯誤處理（有外部 I/O 時必填；純本地計算可省略並聲明「無外部 I/O」）

| ID | 錯誤類型 | 處理方式 | 驗證層級 | 來源（若有 PRD） |
|----|---------|---------|---------|-----------------|
| EH-1 | [例如：網路逾時] | [例如：重試 3 次後拋出錯誤] | [testable] | ← PRD#1 |
| EH-2 | [例如：檔案不存在] | [例如：回傳 null 並記錄 warning] | [testable] | ← PRD#2 |

### 設計決策
[為什麼這樣設計，排除了什麼替代方案]
```

### 系統級設計規格

適用於涉及多模組、多檔案的系統級設計。當變更跨越 2 個以上模組時使用此模板。

```markdown
## 📐 系統級設計規格

### 目標
[一句話說明這個系統/功能要解決什麼問題]

### PRD 需求分解（若有 PRD 時必填）

| PRD# | PRD 來源段落 | 可驗證的需求陳述 |
|------|------------|----------------|
| PRD#1 | [例如：用戶管理系統] | [例如：支援 CRUD 操作與角色權限控制] |

### 模組結構

| 模組名稱 | 職責 | 對外依賴 |
|---------|------|---------|
| [例如：auth-service] | [例如：處理認證與 token 管理] | [例如：user-repo, config] |
| [例如：user-repo] | [例如：用戶資料持久化] | [例如：database] |
| [例如：api-gateway] | [例如：路由分發與請求驗證] | [例如：auth-service] |

### 模組間依賴關係

```
api-gateway → auth-service → user-repo → database
                ↘ config
```

[以文字或 ASCII 圖示標明模組間的呼叫方向與資料流向]

### 函式簽名（按模組分組）

#### [模組名稱 1]
- 名稱：[函式名]
- 參數：

| 名稱 | 型別 | 約束條件 | 必填 |
|------|------|---------|------|

- 回傳值：

| 型別 | 說明 |
|------|------|

#### [模組名稱 2]
- 名稱：[函式名]
- 參數：

| 名稱 | 型別 | 約束條件 | 必填 |
|------|------|---------|------|

- 回傳值：

| 型別 | 說明 |
|------|------|

### 邊界條件

| ID | 條件描述 | 預期行為 | 驗證層級 | 來源（若有 PRD） |
|----|---------|---------|---------|-----------------|
| BC-1 | [例如：token 過期] | [例如：回傳 401 並觸發刷新] | [testable] | ← PRD#1 |
| BC-2 | [例如：跨模組事務失敗] | [例如：回滾所有變更] | [testable] | |

### 錯誤處理（有外部 I/O 時必填；純本地計算可省略並聲明「無外部 I/O」）

| ID | 錯誤類型 | 處理方式 | 驗證層級 | 來源（若有 PRD） |
|----|---------|---------|---------|-----------------|
| EH-1 | [例如：下游服務不可用] | [例如：熔斷 + 降級回應] | [testable] | |
| EH-2 | [例如：資料庫連線逾時] | [例如：重試 3 次後拋出錯誤] | [testable] | ← PRD#1 |

### 設計決策
[為什麼這樣設計，排除了什麼替代方案，模組拆分的理由]
```

**驗證層級說明**：
- `[testable]`：純邏輯、可程式化驗證 → Phase 4 必須有自動化測試
- `[visual-only]`：渲染、動畫、UI 佈局 → Phase 3 品質審查以 code review 驗證，Phase 4 免除自動化測試
- `[framework-dependent]`：需要框架 runtime → 建議拆分純邏輯方法，無法拆分的部分按 `[visual-only]` 處理

**領域預設**：預設為 `[testable]` 的領域（後端 API / CLI / 系統程式）無需逐項標注驗證層級，只需標注例外（即 `[visual-only]` 或 `[framework-dependent]` 的項目）。

## 設計審查報告（Phase 1b 獨立設計審查產出）

```markdown
## 🔬 設計審查報告

- 審查對象：[函式/模組名稱]
- 審查時間：[YYYY-MM-DD HH:MM]
- 審查方式：獨立子 agent（不繼承主對話 context）
- 審查輪次：第 N 輪（最多 3 輪）

### 挑戰式審查

| ID | 嚴重度 | 審查項目 | 問題描述 | 替代方案建議 |
|----|--------|---------|---------|-------------|
| DR-1 | high/medium/arch-risk | [例如：架構選型] | [為什麼現方案有問題] | [更優的替代做法] |

### 驗證式審查

| ID | 嚴重度 | 審查項目 | 問題描述 | 建議修正 |
|----|--------|---------|---------|---------|
| DR-2 | high/medium/low | [例如：BC-x 覆蓋度] | [遺漏了什麼邊界] | [建議補充的 BC-x] |

### 嚴重度定義
- **high**：架構有明顯缺陷、遺漏關鍵邊界情境、或存在明顯更優替代方案 → 必須回 Phase 1 修正
- **medium**：設計可改善但不影響正確性，或有值得考慮的替代方向 → 呈現給用戶決定
- **low**：風格偏好或微小建議 → 合併摘要記錄
- **arch-risk**：架構設計存在長期風險但不影響當前正確性 → 不觸發閘門/斷點，Phase 5 追蹤

### 迭代狀態
- 本輪結論：通過 / 需回退修正
- 終止條件：本輪無新 high → 通過
```

注意「審查方式」欄位——強調這是獨立審查，不是同一個 agent 自己檢查自己。

**寫入位置**：子 agent 必須將此報告寫入 `.claude-loop/artifacts/P1b-design-review.md`。Phase 5 Part C 會驗證此檔案存在。

## 檢核報告（Phase 3 檢核師產出）

```markdown
## 🔍 檢核報告

- 檢核對象：[函式/模組名稱]
- 檢核時間：[YYYY-MM-DD HH:MM]
- 安全審查狀態：已執行 / by-design 跳過（[原因]）

| ID | 嚴重度 | 位置 | 問題描述 | 建議修正 | 狀態 |
|----|--------|------|---------|---------|------|
| R-1 | high | [檔案:行數] | [問題是什麼] | [建議怎麼改] | open/resolved |
| R-2 | medium | [檔案:行數] | [問題是什麼] | [建議怎麼改] | open/resolved |
| R-3 [TypeScript] | high | [檔案:行數] | [語言專屬問題] | [建議怎麼改] | open/resolved |
| R-4 | arch-risk | [檔案:行數] | [架構長期風險] | [建議方向] | tracked |

### 嚴重度定義
- **high**：邏輯錯誤、安全漏洞、跟設計規格不符 → 一定要修才能往下走
- **medium**：品質問題、可維護性風險 → 建議修，不修的話要在自証時說明
- **low**：風格建議、微小改進 → 記錄就好
- **arch-risk**：架構設計存在長期風險但不影響當前正確性 → 不觸發閘門/斷點，Phase 5 追蹤
```

## 測試報告（Phase 4 測試師產出）

```markdown
## 🧪 測試報告

- 測試對象：[函式/模組名稱]
- 測試時間：[YYYY-MM-DD HH:MM]
- [testable] 覆蓋：X / Y
- [visual-only] 項：N 項（驗證方式：code review）
- [framework-dependent] 項：N 項（驗證方式：[拆分純邏輯/code review]）

| 測試名稱 | 對應規格 ID | 驗證層級 | 結果 | 說明 |
|---------|------------|---------|------|------|
| [test_empty_input] | BC-1 | [testable] | pass/fail | [補充說明] |
| [test_overflow] | BC-2 | [testable] | pass/fail | [補充說明] |
| [test_network_timeout] | EH-1 | [testable] | pass/fail | [補充說明] |
| — | BC-3 | [visual-only] | code review ✅ | [視覺驗證說明] |
| [test_happy_path] | — | [testable] | pass/fail | [正常路徑測試] |
```

注意「驗證層級」欄位——區分自動化測試和替代驗證方式，讓自証師知道每項的驗證方式。

**寫入位置**：品質審查子 agent 寫入 `.claude-loop/artifacts/P3-quality-review.md`，安全審查子 agent（若執行）寫入 `.claude-loop/artifacts/P3-security-review.md`。Phase 5 Part C 會驗證這些檔案存在。

| 產出物完整性 | ✅/❌ | [例如：設計規格 ✅ 程式碼 ✅ 檢核報告 ✅ 測試報告 ✅] | [若有缺口寫這裡] |

（若不通過）
### 回退建議

- 原因：[具體說明哪裡不一致]
- 修正方向：[建議怎麼修]

## 委派產出物檔案（`.claude-loop/artifacts/`）

完整閉環必建 `.claude-loop/artifacts/` 目錄。每個委派 Phase 的子 agent 必須將產出寫入對應檔案，Phase 5 Part C 在步驟 8 前驗證檔案存在性。

| 檔案名稱 | 產出 Phase | 寫入者 | 條件 |
|---------|-----------|--------|------|
| `P1b-design-review.md` | Phase 1b | 設計審查子 agent | 用戶跳過時不需存在 |
| `P3-quality-review.md` | Phase 3 | 品質審查子 agent | 必須存在 |
| `P3-security-review.md` | Phase 3 | 安全審查子 agent | 安全審查 by-design 跳過時不需存在 |
| `P5AB-bidirectional-tracing.md` | Phase 5 Part AB | 雙向追溯子 agent | 必須存在 |

每個檔案的內容格式與對應 Phase 的產出物格式相同（見上方各節）。
