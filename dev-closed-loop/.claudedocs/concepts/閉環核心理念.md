# 閉環核心理念

## 一句話說明

寫程式的時候，讓不同「角色」輪流檢查同一段程式碼，最後由一個「自證師」確認所有人的結論沒有互相矛盾，這樣才算真的寫完。

## 為什麼需要這套方法

一般寫程式的流程是：寫好 → 測試通過 → 提交。問題在於：

- 設計文件說要處理 5 種錯誤，但程式碼只處理了 3 種，測試只測了 2 種
- 安全檢查說「輸入要驗證」，但測試案例裡根本沒有惡意輸入的測試
- 每個環節各做各的，沒人去比對它們之間有沒有對齊

這些不是 bug，是**產出物之間的不一致**。傳統的 Code Review 和測試抓不到這類問題。

## 三個核心概念

### 1. 閉環原則

每寫一段程式碼，都要走完一整圈：設計 → 實作 → 檢核 → 測試 → 自證。
走完一圈叫「閉環」，圈沒走完就不算做完。

就像工廠的品管流水線——原料進來，經過每個工站檢查，最後過終檢，才能出貨。你不能跳過其中一站就說產品做好了。

### 2. 自證機制

自證是這套方法最特別的地方。

一般的測試是在問：「程式跑出來的結果對不對？」
自證是在問：「前面所有人說的話，有沒有互相矛盾？」

具體來說，自證師會用**雙向追溯**檢查：
- **正向**：架構師的設計規格 → 程式碼有沒有實作？→ 測試有沒有覆蓋？
- **反向**：程式碼中的每個行為 → 設計規格裡有沒有對應？沒有的是遺漏設計還是多餘程式碼？
- **交叉比對**：正向發現的缺失和反向發現的冗餘互為補充，即時比對

v5.4 將正向和反向合併為單一子 agent 執行，因為同時做兩個方向可以即時交叉比對，品質優於分開做再調和。

**自證不是重複測試，而是在做「跨產出物的一致性驗證」。**

### 3. 逐層擴展

不是一口氣把整個系統都跑閉環。而是從最小的單位開始：

- 先對一個**函式**跑閉環
- 函式都通過後，再對**模組**跑閉環
- 模組都通過後，再對**框架/系統**跑閉環

就像蓋房子：先確認每塊磚頭沒問題，再確認每面牆沒問題，最後確認整棟樓沒問題。

## 跟你可能聽過的東西的差別

| 方法 | 在檢查什麼 | 本方法多了什麼 |
|------|-----------|--------------|
| Code Review | 程式碼品質好不好 | 程式碼跟設計有沒有對齊 |
| 單元測試 | 程式跑出來對不對 | 測試有沒有覆蓋設計裡提到的所有情況 |
| CI/CD | 建置和測試有沒有通過 | 所有環節的產出物之間有沒有矛盾 |
| V-Model | 每個開發階段有對應的驗證 | 驗證「跨階段」的一致性，不只是單階段 |

這套方法不是要取代上面這些，而是在它們之上多加一層「自證」來抓住它們抓不到的問題。

## 獨立設計審查

閉環的另一個特色是在 Phase 1（設計）之後、Phase 2（實作）之前，加入一個**獨立的設計審查**。

為什麼需要？因為如果設計本身有問題，後面的實作、檢核、測試再怎麼嚴謹，也只是「正確地做了錯的事」。自證可以比對「設計跟實作有沒有對齊」，但沒人質疑「設計本身是不是最好的選擇」。

怎麼做到獨立？用 Task 工具開一個全新的子 agent。這個子 agent 不知道架構師怎麼想出這個設計的——它沒有設計過程中的推理 context，只看到設計結果、原始需求、和現有的專案結構。這樣它才能用新鮮的眼光去問：「真的沒有更好的做法嗎？」

審查分兩個角度：
- **挑戰式**：有更好的方案嗎？會不會過度設計？
- **驗證式**：邊界條件夠不夠？錯誤處理有沒有漏洞？有 update/tick 迴圈時執行順序是否已定義？

審查結果用 DR-x 編號，嚴重的必須回 Phase 1 修正（全量重審，最多 3 輪），不嚴重的由用戶決定。Phase 5 自證時也會追溯 DR-x 的處理狀態。

v5.5 新增 **arch-risk** 嚴重度：架構設計存在長期風險但不影響當前正確性（例如擴展性瓶頸、耦合度偏高）。arch-risk 不觸發閘門回退，但會記錄下來，在 Phase 5 自證時追蹤其狀態——是否在後續 Phase 中已緩解或仍存在。這讓審查者可以標記「不急但值得注意」的問題，不會因為觸發回退而猶豫不標。

**為什麼回退後要全量重審？** 壓測實證顯示，修正設計缺陷時可能引入新的缺陷（修正 DR-4/5 引入了 DR-13）。設計規格是相互耦合的文件，差分審查在設計層有漏洞風險。

## 獨立檢核

Phase 3（檢核）也採用獨立子 agent。品質審查用獨立子 agent，安全審查視場景條件決定是否執行（純本地無網路應用可跳過）。這樣檢核師不會因為「我剛寫了這段程式碼」而下意識放水——它只看到設計規格和程式碼，不知道實作過程中的推理。

**斷點 A 回退後的差分審查**：回退修正後，Phase 3 只審修改檔案及其依賴檔案（不全量重審）。程式碼變更邊界比設計規格清晰——有明確的 diff、函式簽名、型別系統約束——差分審查在程式碼層是安全的。

## 獨立自證

自證（Phase 5）的核心檢查也由獨立的子 agent 執行，而不是寫程式碼的那個 agent 自己判。

為什麼？因為同一個 agent 從 Phase 1 做到 Phase 4，帶著所有推理過程的「記憶」。這些記憶會讓它在自證時傾向合理化之前的決定——「我當時是這樣想的，所以這樣做沒問題」。這就是球員兼裁判的問題。

解法：Phase 5 的雙向追溯由一個獨立子 agent 執行。它拿到所有產出物（設計規格、程式碼、測試報告），同時做正向追溯和反向分析並即時交叉比對。只有最後的整體評估（Part C）留在主 agent，負責跑驗證指令和彙整結果。

這不能完全消除「同一個模型」的限制（所有子 agent 還是 Claude），但切斷了認知偏見的傳遞鏈——審查者至少不會被前序推理影響。

## 場景適配

v5.5 引入**領域偵測與規則預設**機制，讓閉環根據專案類型自動調整規則嚴格度——不是「降低標準」，而是「把資源分配給真正有價值的檢查」。例如純本地遊戲不需要安全審查，省下的 token 可以讓品質審查做更深的分析。領域未匹配時用最嚴格的預設，確保不會漏檢。具體的領域偵測表和條件規則見 CLAUDE.md Section 6。

## 精簡閉環的追溯保障

完整閉環有 Phase 5 自證做雙向追溯，但精簡閉環（中型任務）不跑 Phase 5——那精簡閉環怎麼確保「設計的都做了、做的都測了」？

v5.15.0 在精簡閉環的測試通過後、commit 前加入**迷你追溯**：主 agent 自己逐項列表，確認每個 BC-x/EH-x 有實作（附檔案:行號）和測試（附測試名稱），同時追蹤品質審查的 medium 問題是否已由用戶決策。有任何 ❌ 就禁止 commit。

跟完整自證的差別：迷你追溯只做正向覆蓋（設計→實作→測試），不做反向分析（找多餘程式碼）和 arch-risk 追蹤。中型任務範圍小（1-3 檔案），反向分析的 ROI 不值得。迷你追溯由主 agent 執行（不委派子 agent），成本約 1-2K tokens。

## 子 agent 失敗與斷點熔斷

閉環大量使用子 agent，但子 agent 可能超時或輸出不完整。失敗處理機制確保流程不卡住：重試→降級自審→標記品質降級，保留可追溯性。

斷點是品質閘門——發現問題就回退修正。但反覆回退只會浪費 token。**斷點熔斷**機制像電路斷路器——正常情況讓電流通過（允許回退），但短路時跳閘（防止無限重試），由人來判斷怎麼處理。具體規則見 CLAUDE.md Section 7-8。

## 常見設計缺陷預防清單

v5.5 在 Phase 1 前加入一份預防清單，列出壓測中最常見的設計缺陷（如 update/tick 順序未定義、資源未釋放、不可達狀態等）。首次使用閉環或進入不熟悉的領域時建議逐項檢查。

這是一種「學習累積」機制——把歷次閉環踩過的坑整理成清單，讓新的任務不必重新踩。就像飛行員的起飛前檢查表，不是限制你的能力，而是防止已知的低級失誤。

## 回顧式學習

預防清單是手動維護的靜態列表。v5.16.0 加入**學習日誌**機制，讓失敗教訓自動沉澱。

核心原則：**只記導致回頭重做的事件**。斷點觸發（程式碼 bug 被攔截）、DR-x high（設計根本缺陷）、熔斷（反覆修不好）、任務升級（規模誤判）——這些是真正的教訓。日常的 R-x medium 修正和 code-simplifier 建議是系統正常運作，不需要「學習」。

每個事件記錄四件事：**什麼問題、什麼原因、怎麼修的、下次要注意什麼**。不是抽象的統計，是具體的、可追溯的事件記錄。下次做類似功能時，Phase 1 前讀這份日誌，不只知道「資源洩漏出現過 3 次」，而是知道每次是什麼具體模式、什麼根因、怎麼修的。

關鍵設計：**失敗事件發生時立即記錄**，不等到閉環結束。斷點觸發 → 馬上追加一條。這樣即使 session 中斷或用戶放棄，教訓也已經落地。閉環通過時在 commit 前追加完整條目，跟程式碼一起 commit。PostToolUse Hook 在 git commit 後檢查 learning-log 是否在 commit 中，作為最後防線。

跟 claude-mem 的差別：claude-mem 存語意記憶（「為什麼選了 A 方案」），學習日誌存事件記錄（「什麼問題因為什麼原因被攔截」）。claude-mem 幫你回憶決策理由，學習日誌幫你識別重複出現的失敗模式。

## 設計文件同步

Phase 2 和 Phase 4 有「設計文件同步」checkpoint——當改動影響 BC-x/EH-x 語意時，必須同步更新設計規格。壓測顯示 Phase 5 反向分析的主要發現往往是「文檔沒更新」而非真正的程式碼問題。在 Phase 2/4 及時同步，Phase 5 就能專注於發現真正的設計-實作矛盾。

## 理解確認

閉環有各種守衛防止 AI 做錯事——但如果 AI 從一開始就理解錯用戶的意思，再多守衛也只是「正確地做了錯的事」。

理解確認在最上游把關：透過 Hook 協作形成阻擋式閘門，強制 AI 在動手前先輸出「我收到的是這個意思，我打算這樣做」，用戶確認方向對了才放行——不對頻就不讓改。

## 同類掃描

閉環的各種守衛都是沿著「這次修改」的縱向深度在走。但有一類問題抓不到：**你改的步數夠不夠？**

舉例：系統有 18 張圖，用戶說「第 2 張圖的 alt 屬性沒加」。只修第 2 張圖就結束，其他 17 張有同樣問題也不會被發現。

同類掃描補這個橫向缺口：先判斷修改對象是不是屬於同類項目，是就掃描同類有沒有同樣問題，報告用戶後才執行。預設只掃同目錄的直接同類，用戶需要時才升級到全專案。

## 可選擴展：PRD 需求分解

如果用戶提供了 PRD（產品需求文檔），架構師在 Phase 1 可以先把 PRD 拆成編號需求項（PRD#1, PRD#2...），再設計 BC-x/EH-x 並標注每項的來源。這樣自證師在 Phase 5 就能多驗一件事：**PRD 裡的每個需求，設計規格都有對應到嗎？**

沒有 PRD 的時候，這個功能完全不啟動，不增加任何流程。

## 模組化與功能/UI 分層

開發一個專案時，很多功能模組的核心邏輯大同小異——用戶認證、權限管理、CRUD 操作、資料驗證。但使用者介面每次都不一樣，因為它跟具體的產品需求和設計風格綁在一起。

如果功能邏輯和 UI 混在一起寫，每次改 UI 都要動到功能層，每次複用功能都要把 UI 一起搬。結果就是：要嘛整個模組照搬再大改，要嘛從零開始。

閉環方法論在 Phase 1 設計時要求**聲明分層結構**：有使用者介面的模組必須拆成功能層和 UI 層。功能層不依賴 UI 框架——這是唯一的硬規則。Phase 3 檢核時會驗證依賴方向是否正確（功能層有沒有反向依賴 UI）。

就像蓋房子時把水電管線和裝潢分開——管線（功能層）走完驗收，裝潢（UI 層）可以隨時換風格而不動管線。

## 模組登記

閉環通過的模組會登記到模組清單（`.claude-loop/module-registry.md`），記錄名稱、分層結構、功能層的公開 API。下次開發新功能時，Phase 1 前先查這份清單——有現成的功能層就直接複用，只設計新的 UI 層或新增功能。

這不是額外的文件工作。模組登記是閉環流程自然產出的索引，目的是讓做過的東西能被找到，避免重複造輪子。
