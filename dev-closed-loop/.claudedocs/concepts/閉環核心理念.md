# 閉環核心理念

## 一句話說明

寫程式的時候，讓不同「角色」輪流檢查同一段程式碼，最後由一個「自証師」確認所有人的結論沒有互相矛盾，這樣才算真的寫完。

## 為什麼需要這套方法

一般寫程式的流程是：寫好 → 測試通過 → 提交。問題在於：

- 設計文件說要處理 5 種錯誤，但程式碼只處理了 3 種，測試只測了 2 種
- 安全檢查說「輸入要驗證」，但測試案例裡根本沒有惡意輸入的測試
- 每個環節各做各的，沒人去比對它們之間有沒有對齊

這些不是 bug，是**產出物之間的不一致**。傳統的 Code Review 和測試抓不到這類問題。

## 三個核心概念

### 1. 閉環原則

每寫一段程式碼，都要走完一整圈：設計 → 實作 → 檢核 → 測試 → 自証。
走完一圈叫「閉環」，圈沒走完就不算做完。

就像工廠的品管流水線——原料進來，經過每個工站檢查，最後過終檢，才能出貨。你不能跳過其中一站就說產品做好了。

### 2. 自証機制

自証是這套方法最特別的地方。

一般的測試是在問：「程式跑出來的結果對不對？」
自証是在問：「前面所有人說的話，有沒有互相矛盾？」

具體來說，自証師會用**雙向追溯**檢查：
- **正向**：架構師的設計規格 → 程式碼有沒有實作？→ 測試有沒有覆蓋？
- **反向**：程式碼中的每個行為 → 設計規格裡有沒有對應？沒有的是遺漏設計還是多餘程式碼？
- **交叉比對**：正向發現的缺失和反向發現的冗餘互為補充，即時比對

v5.4 將正向和反向合併為單一子 agent 執行，因為同時做兩個方向可以即時交叉比對，品質優於分開做再調和。

**自証不是重複測試，而是在做「跨產出物的一致性驗證」。**

### 3. 逐層擴展

不是一口氣把整個系統都跑閉環。而是從最小的單位開始：

- 先對一個**函式**跑閉環
- 函式都通過後，再對**模組**跑閉環
- 模組都通過後，再對**框架/系統**跑閉環

就像蓋房子：先確認每塊磚頭沒問題，再確認每面牆沒問題，最後確認整棟樓沒問題。

## 跟你可能聽過的東西的差別

| 方法 | 在檢查什麼 | 本方法多了什麼 |
|------|-----------|--------------|
| Code Review | 程式碼品質好不好 | 程式碼跟設計有沒有對齊 |
| 單元測試 | 程式跑出來對不對 | 測試有沒有覆蓋設計裡提到的所有情況 |
| CI/CD | 建置和測試有沒有通過 | 所有環節的產出物之間有沒有矛盾 |
| V-Model | 每個開發階段有對應的驗證 | 驗證「跨階段」的一致性，不只是單階段 |

這套方法不是要取代上面這些，而是在它們之上多加一層「自証」來抓住它們抓不到的問題。

## 獨立設計審查

閉環的另一個特色是在 Phase 1（設計）之後、Phase 2（實作）之前，加入一個**獨立的設計審查**。

為什麼需要？因為如果設計本身有問題，後面的實作、檢核、測試再怎麼嚴謹，也只是「正確地做了錯的事」。自証可以比對「設計跟實作有沒有對齊」，但沒人質疑「設計本身是不是最好的選擇」。

怎麼做到獨立？用 Task 工具開一個全新的子 agent。這個子 agent 不知道架構師怎麼想出這個設計的——它沒有設計過程中的推理 context，只看到設計結果、原始需求、和現有的專案結構。這樣它才能用新鮮的眼光去問：「真的沒有更好的做法嗎？」

審查分兩個角度：
- **挑戰式**：有更好的方案嗎？會不會過度設計？
- **驗證式**：邊界條件夠不夠？錯誤處理有沒有漏洞？有 update/tick 迴圈時執行順序是否已定義？

審查結果用 DR-x 編號，嚴重的必須回 Phase 1 修正（全量重審，最多 3 輪），不嚴重的由用戶決定。Phase 5 自証時也會追溯 DR-x 的處理狀態。

v5.5 新增 **arch-risk** 嚴重度：架構設計存在長期風險但不影響當前正確性（例如擴展性瓶頸、耦合度偏高）。arch-risk 不觸發閘門回退，但會記錄下來，在 Phase 5 自証時追蹤其狀態——是否在後續 Phase 中已緩解或仍存在。這讓審查者可以標記「不急但值得注意」的問題，不會因為觸發回退而猶豫不標。

**為什麼回退後要全量重審？** 壓測實證顯示，修正設計缺陷時可能引入新的缺陷（修正 DR-4/5 引入了 DR-13）。設計規格是相互耦合的文件，差分審查在設計層有漏洞風險。

## 獨立檢核

Phase 3（檢核）也採用獨立子 agent。品質審查用獨立子 agent，安全審查視場景條件決定是否執行（純本地無網路應用可跳過）。這樣檢核師不會因為「我剛寫了這段程式碼」而下意識放水——它只看到設計規格和程式碼，不知道實作過程中的推理。

**斷點 A 回退後的差分審查**：回退修正後，Phase 3 只審修改檔案及其依賴檔案（不全量重審）。程式碼變更邊界比設計規格清晰——有明確的 diff、函式簽名、型別系統約束——差分審查在程式碼層是安全的。

## 獨立自証

自証（Phase 5）的核心檢查也由獨立的子 agent 執行，而不是寫程式碼的那個 agent 自己判。

為什麼？因為同一個 agent 從 Phase 1 做到 Phase 4，帶著所有推理過程的「記憶」。這些記憶會讓它在自証時傾向合理化之前的決定——「我當時是這樣想的，所以這樣做沒問題」。這就是球員兼裁判的問題。

解法：Phase 5 的雙向追溯由一個獨立子 agent 執行。它拿到所有產出物（設計規格、程式碼、測試報告），同時做正向追溯和反向分析並即時交叉比對。只有最後的整體評估（Part C）留在主 agent，負責跑驗證指令和彙整結果。

這不能完全消除「同一個模型」的限制（所有子 agent 還是 Claude），但切斷了認知偏見的傳遞鏈——審查者至少不會被前序推理影響。

## 場景適配

v5.5 引入**領域偵測與規則預設**機制，讓閉環在 Phase 1 前根據專案語言、框架、imports 自動偵測領域（遊戲開發、後端 API、前端 SPA、CLI 工具、系統程式），套用對應的預設規則：

- **EH-x 條件化**：有外部 I/O → 必須定義；純本地計算 → 可選
- **安全審查條件化**：有網路/敏感資料/unsafe → 必須執行；純本地無攻擊面 → 可跳過
- **測試分層**：`[testable]` 必須自動化測試；`[visual-only]` 用 code review；`[framework-dependent]` 建議拆分純邏輯
- **驗證層級預設**：每個領域有自己的預設驗證層級。例如後端 API 預設所有項目都是 `[testable]`（不需逐項標注），只有例外才需要標 `[visual-only]` 或 `[framework-dependent]`；遊戲開發則預設 `[framework-dependent]`，只有可測純邏輯才標 `[testable]`。這大幅減少標注負擔

這些不是「降低標準」，而是「把資源分配給真正有價值的檢查」。安全審查跳過省下的 token 可以讓品質審查做更深的跨模組資料流追蹤。領域未匹配時用後端 API 預設（最嚴格），確保不會漏檢。

## 子 agent 失敗處理

閉環大量使用子 agent（Phase 1b 設計審查、Phase 3 檢核、Phase 5 自証追溯）。但子 agent 可能超時、輸出為空、或明顯不完整。v5.5 定義了統一的失敗處理機制：

1. **第一次失敗**：重試一次（相同 prompt）
2. **第二次失敗**：主 agent 自行執行相同審查，標記「降級自審」
3. 降級自審的結果在 Phase 5 產出物驗證中不視為缺失，但會記錄品質降級

這確保流程不會因為子 agent 的偶發故障就卡住，同時保留了品質降級的可追溯性。

## 斷點熔斷

斷點（Phase 3 的斷點 A、Phase 4 的斷點 B）是閉環的品質閘門——發現問題就回退修正。但如果問題反覆出現，無限回退只會浪費 token 而不解決根本問題。

v5.5 引入**斷點熔斷**機制：同一 Phase 的斷點累計觸發 3 次後，暫停流程，交由用戶決定：
- 繼續嘗試修正
- 降級為精簡閉環完成剩餘工作
- 重新設計（回 Phase 1 重新開始）

這就像電路斷路器——正常情況下讓電流通過（允許回退修正），但短路時跳閘（防止無限重試），由人來判斷怎麼處理。

## 常見設計缺陷預防清單

v5.5 在 Phase 1 前加入一份預防清單，列出壓測中最常見的設計缺陷（如 update/tick 順序未定義、資源未釋放、不可達狀態等）。首次使用閉環或進入不熟悉的領域時建議逐項檢查。

這是一種「學習累積」機制——把歷次閉環踩過的坑整理成清單，讓新的任務不必重新踩。就像飛行員的起飛前檢查表，不是限制你的能力，而是防止已知的低級失誤。

## 設計文件同步

v5.4 在 Phase 2 和 Phase 4 增加「設計文件同步」checkpoint。當修正 bug 或改動影響 BC-x/EH-x 語意時，必須同步更新設計規格。

為什麼？壓測顯示 Phase 5 反向分析的主要發現往往是「文檔沒更新」而非真正的程式碼問題。在 Phase 2/4 及時同步，Phase 5 就能專注於發現真正的設計-實作矛盾。

## 理解確認

閉環有各種守衛防止 AI 做錯事——但如果 AI 從一開始就理解錯用戶的意思，再多守衛也只是「正確地做了錯的事」。

理解確認就是在最上游把關：用戶提交指令時，Hook 自動提醒 AI 先輸出「我收到的是這個意思，我打算這樣做」，用戶確認方向對了才動手。Hook 會強制觸發提醒，但不會阻擋操作（不像因果鏈守衛會 block 修改）——AI 是否遵循仍靠 CLAUDE.md 規則約束。

同時，所有 Hook 觸發時都統一輸出橙色 `🟠 收到：...` 前綴，讓用戶清楚看到系統在每一步做了什麼把關。

## 同類掃描

閉環的各種守衛（因果鏈分析、合理性審查）都是沿著「這次修改」的縱向深度在走——確保你改的東西是對的、不會壞掉別的東西。但有一類問題它們抓不到：**你改的步數夠不夠？**

舉個例子：系統有 18 張圖，用戶說「第 2 張圖的 alt 屬性沒加」。如果只修第 2 張圖就結束，其他 17 張有同樣問題也不會有人發現——因為因果鏈分析只看「改第 2 張圖會不會影響別的東西」，不會問「其他圖有沒有一樣的問題」。

同類掃描就是補這個橫向的缺口。收到修改指令時，先判斷修改對象是不是屬於一組同類項目——如果是，掃描同類項目有沒有同樣的問題，報告用戶後才執行。

這不是每次都做的全專案掃描。預設只掃同目錄 / 同層級的直接同類，用戶需要時才升級到全專案範圍。目的是在不明顯增加成本的前提下，避免「只修了冰山一角」的情況。

## 可選擴展：PRD 需求分解

如果用戶提供了 PRD（產品需求文檔），架構師在 Phase 1 可以先把 PRD 拆成編號需求項（PRD#1, PRD#2...），再設計 BC-x/EH-x 並標注每項的來源。這樣自証師在 Phase 5 就能多驗一件事：**PRD 裡的每個需求，設計規格都有對應到嗎？**

沒有 PRD 的時候，這個功能完全不啟動，不增加任何流程。
