# 閉環核心理念

## 一句話

改程式之前先弄清楚兩件事：**這一改會牽動誰**，以及**我相信的「事實」是不是真的**。其他都是配套。

## 這套方法在補什麼

LLM 寫程式有三個老毛病：替你做假設然後不查證、把東西寫複雜、順手改掉它不理解的東西。這套方法一開始（v3 到 v7）用五個角色的流水線來管：架構師寫規格、程序設計師實作、檢核師審、測試師測、自證師比對五份產出物有沒有矛盾。

2026 年 5 月做了六場對照實驗（代號 A 到 F），每場三組：裸寫一次、裸寫加一次外部審查、完整五階段。用藏起來的測試套件評分。

結果六場全部平手。五階段流水線對程式正確性零增益，成本最高是裸寫的 7 倍。原因很直接：流水線強制做的事（讀完整個 codebase、做影響分析、核對事實、枚舉邊界），前沿模型認真做事時本來就會做。把它儀式化只是疊成本。

同一批實驗也指出真正有價值的東西：**把契約寫下來**，以及**換一個沒有原推理脈絡的視角看一次**。一份 note 加一次外部審查，跟完整五階段同分。

## v8 保留了什麼，為什麼

CLAUDE.md 從 344 行砍到約 125 行，留下的每一條都對應一個「模型自己不會可靠做到」的點：

| 保留 | 補的是什麼 |
|------|-----------|
| 任務分級 | 決定什麼時候值得花編排成本。這是判斷，不是能力 |
| 修改前紀律（因果鏈） | 模型會做分析，但你在它動手前看不到。強制它寫出 2-4 行，你就能在落地前攔錯 |
| 事實求證 | 確認偏誤不會因為模型變強就消失。字面證據、反例檢查、共用值三條是 GS 誤判事件的直接教訓 |
| Push back 白名單 | 價值是反向的：限制模型只在五種情境反對你，避免多嘴 |
| 設計前查教訓 | 專案專屬的坑，模型不可能從訓練資料知道 |
| 跨來源審查（R-2） | 全 repo 唯一有量化證據的機制：同一來源自審漏看率 50-67%，換一個 context 就抓回來 |
| 增量 lint hook | 唯一提供地面真值的 hook，回報的是編譯器的事實 |

砍掉的：Karpathy 四原則對映表、領域偵測表、升格降級機制、KPI 指標、給人看的實驗校準段、三支 hook、agent 素材庫、六語言指南、五份流程文檔。理由和證據在方法論 repo 的 `design/15-v8-slim.md`。

## 因果鏈：hook 能保證什麼，不能保證什麼

`impact-analysis-guard.sh` 在每輪用戶指令內、首次修改既有原始碼檔時擋一次，印出以檔名粗搜到的相關檔案，要模型先寫出因果鏈分析再重試。

它保證的是**暫停一次、分析可見**。它不保證分析正確：不解析 grep 結果、呼叫者為零也不會真的拒絕、用 Bash 改檔完全不會觸發。真正的保護是模型的分析加你的眼睛加測試。hook 的角色是讓你的眼睛有機會用上。

v7 以前的版本把這支 hook 描述成「機械保證」，2026 年 6 月逐行讀過腳本後修正了措辭。v8 進一步把它收窄：不擋新檔、不擋 md / json / yaml、marker 依 session 隔離、訊息改走 stderr（exit 2 時模型只看得到 stderr，舊版印在 stdout 等於模型看不到）。

## 事實求證：為什麼需要反例檢查

實作任務靠測試驗證，認知任務沒有測試可跑。GS 誤判事件是：模型看到 config 裡某 IP 出現在某 entry，就斷言那是某遊戲的 Game Server，寫進 memory，後面的推論全建在這上面。事後發現那個 IP 在六個 entry 都出現，是共用的 pypi server，檔名還明寫 `PypiConfig`。

三條原則各擋一種錯：字面證據擋「忽視作者自己寫的用途」，共用值擋「把共用資源當專屬」，反例檢查擋「只找支持自己假設的證據」。前兩條是去找證據，第三條是逼自己想反面，所以不能省。

模型驗自己有循環依賴，真正外部的把關是你。所以有質疑熔斷：你問「你確定嗎」，它必須停下來攤證據、誤判就認。

## 工作流程長什麼樣

- **微小任務**：直接做，因果鏈紀律照跑。
- **中型任務**：3-5 行設計（含至少一條 BC-x）→ 實作 → 測試 → 逐條確認每條 BC-x 有實作有測試。
- **大型任務**：建議用 `/dev-design` 做多方案架構設計，實作後用 `/code-review` 或 `/dev-review` 審，測試，逐條追溯。
- **需求未定**：`/dev-prd` 或 `/dev-design`。

workflow 需要付費方案與 research preview。開不了就用 AskUserQuestion 自己多角度探索、自己列方案取捨，核心紀律不受影響。

## 學習迴圈

失敗時（同一任務修三次不過、事實誤判）寫一行到 `.claude-loop/learning-log.md`。同類根因累積三次，提議寫進 `問題追蹤.md` 的警惕模式段，下次設計前模型會掃到。退場靠人判斷，不設機械門檻。

## 誠實邊界

- 六場實驗測的是「前沿模型、單一 context、機械可驗的正確性」。超大型、多人長時程的情境沒測過。
- 保留下來的紀律，除了跨來源審查，都沒有量化證據證明「有它比沒它好」。它們是「未否證、成本低、對人有可見性價值」的選擇，不是「已證有效」。
- workflow 對正確性的增益同樣未測。保留是因為運行時零成本，且多方案加新鮮 context 批評是單一 context 做不到的事。
