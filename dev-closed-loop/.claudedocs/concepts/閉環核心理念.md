# 閉環核心理念

## 一句話說明

改動程式之前，先把兩件事做扎實：**這一改會牽動誰**（因果鏈／依賴影響）、**我相信的「事實」是不是真的事實**（認知驗證）——這是本方法論的**承重核**。需求未定或大型的工作，再開獨立的多方案審查，治理「設計、實作、測試對不對得上」。

自 v7.0.0 起，把「多角色審查編排」交給 Claude Code 原生 Workflow，CLAUDE.md 只保留三樣東西：**承重核**、**一定會跑的紀律（always-on hook）**、**workflow 不可用時的退化路徑**。

## 為什麼需要這套方法

一般寫程式的流程是：寫好 → 測試通過 → 提交。問題在於：

- 設計文件說要處理 5 種錯誤，但程式碼只處理了 3 種，測試只測了 2 種
- 安全檢查說「輸入要驗證」，但測試案例裡根本沒有惡意輸入的測試
- 每個環節各做各的，沒人去比對它們之間有沒有對齊

這些不是 bug，是**產出物之間的不一致**。傳統的 Code Review 和測試抓不到這類問題。

但更根本的盲區有兩個，傳統流程連碰都沒碰：

- **改一個地方會不會弄壞另一個地方**（因果鏈／依賴漣漪）——測試只測你想到要測的路徑。
- **你所依據的「事實」根本是錯的**——前提錯了，後面做得再完美也只是「正確地放大錯誤」。

本方法論把前兩類（一致性、依賴漣漪）交給編排與審查，把後一類（事實前提）作為**最上游的承重核**。

## 什麼時候用、什麼時候別用（實證校準）

2026-05-30 起做了一系列對照 dogfood（代號 A–F）：涵蓋 review 找植入 bug、從規格建小型 / 大型重牽連系統、改既有碼且有隱藏跨模組漣漪、需求植入「對代碼為假」的事實前提、以及「修 A 壞 B」是否落在注意力窗內等 regime。每種都用「裸寫一次 / 裸寫 + 一次外部 LLM review / 完整五階段閉環」三臂對照，再用同一套「藏起來的」測試套件評分。這六場刻意涵蓋了「代碼正確性、質量維護、修改因果鏈、事實求證」四個維度。

結果：**六場在 correctness 軸每次都同分（天花板平手）**，note = 一次外部 review = 完整五階段同分，而閉環成本最高約裸寫的 7 倍。也就是說，當任務小到中大型、規格清楚、前沿模型一次就能可靠處理時，閉環不會讓「代碼本身的正確性」更好——模型已經做對了，五階流水線只是疊加流程與成本。

**為什麼會這樣？** 因為閉環把「一個前沿模型認真做事時本來就會做的認知」外部化、儀式化了：讀完整個 codebase、做依賴影響分析、把規格的事實宣稱拿去跟實際代碼核對、枚舉邊界情況——模型本來就在做這些。五階流水線只是**強制**它們。所以對「模型自己一次產出的代碼」，這份強制是淨成本。

所以這套方法的價值**不在**「讓單一模型一次性產出的代碼更正確」。它真正可能賺到的價值錨在**人**（以下三點為設計意圖／方向性假設——人軸 proxy 未否證、非量化證實，詳見下方誠實邊界）：

- **跨產出物一致性治理**（設計↔實作↔測試對不對得上）——當有「人」要長期維護、稽核、交接時才看得到價值
- **失敗模式累積**（長期警惕模式）——跨任務、跨時間才划算
- **跨 session 防漂移**——長時程、多 session 的工作（小任務一次做完用不到）

> ⚠️ **誠實邊界**：2026-06-01 的「人軸 proxy」實驗（模擬接手者讀產出物）顯示方向落在「把握度校準 + 發現成本攤銷 + 前提層防禦」，但**主指標 correctness 仍平手**——也就是**未否證 ≠ 已證**。承重核的人軸價值是「未被推翻」，不是「已被量化證實」，不可宣稱已解決自評漏看率（#007）。（校準限制：correctness 軸 A–F 為前沿模型、單一 context 任務；超大型與多人長時程 regime 尚未驗證。）

**一句話**：把編排用在大型 / 長時程 / 多人協作 / 需稽核的工作；小而清楚、一次能做完的任務，承重核（因果鏈 hook + 事實求證）照跑，但別開重編排讓流程變成淨成本。

**∴ v7.0.0 的設計回應**：把零增益的「五階流水線 ritual」交給 workflow 編排（理論上省主 agent 逐 Phase 委派的 context；**但 workflow 編排 vs 五階的 token / 品質從未對照實測**），只保留實證上承重的部分——承重核 + always-on 紀律 + 跨 session 學習。

## 三層架構（v7.0.0 核心）

v7 把方法論重組成三層，解決「workflow 是付費 + 新版 + research preview 功能，必然有人開不了」的 fail-safe 問題：

| 層 | 是什麼 | 何時跑 |
|----|--------|--------|
| **L1 always-on hook** | 修改前因果鏈閘門 + 理解確認，由 PreToolUse Hook 強制觸發 | 每次 Edit/Write，無論模型想不想、workflow 有沒有 |
| **L2 workflow（預設首選）** | `/dev-prd` `/dev-design` `/dev-review` `/dev-verify`，多 agent 編排 + 對抗驗證 | 大型 / PRD / 架構設計開；中型可選 |
| **L3 文字層（退化路徑）** | CLAUDE.md 條文：事實求證、push back、退化流程 | workflow 不可用時主 agent inline 走 |

關鍵設計：**承重核錨在 L1（hook），不靠 L2（workflow）**。workflow 是 opt-in，hook 是無論如何都跑——所以即使用戶用免費方案、舊版、headless，承重核（因果鏈那一半）仍強制觸發，紀律不會靜默歸零。事實求證那一半沒有對應 hook，是 L3 文字層自律 + 用戶質疑（質疑熔斷）外部把關——這個不對稱是已知且誠實標註的（見後文「承重核」與 CLAUDE.md Section 14）。

## 承重核：修改類動作的雙層防禦

整套方法論真正承重的，是修改類動作的兩道防禦。

### 1. 因果鏈（依賴影響分析）

每次改一個檔案 / 函式前，先機械地問：**誰呼叫它？逐一 grep 列出、逐一判斷要不要連動。呼叫者 = 0 就停**（可能有 inline 實作繞過，硬改會錯）。再追隱性風險：快取失效、時序變化、簽章不變但語意變了。

這一層由 L1 hook（`impact-analysis-guard.sh`）強制觸發，是承重核裡 model-independent 的硬核。

> ⚠️ 誠實邊界：grep 機械子集（呼叫者窮舉、=0 禁改）是硬核；但「語意 / 間接 / 隱性」欄位仍是同源自審，漏看率 50-67%（#007）。在有編譯器 / 型別系統的 codebase 承重面縮小。workflow 可用時開 `/dev-review` 派異源 skeptic 重做能強化這層。

### 2. 事實求證（認知驗證）

前面所有閘門都在驗「你做出來的東西對不對」；這一層驗的是更上游的問題：**你所相信的「事實」真的是事實嗎？**

這是 GS 誤判事件揭露的盲區：Claude 看到 config 中 `ip=...` 就斷言那是某服務的 Game Server，基於此寫 memory、推論架構、準備行動——整個下游建立在錯誤事實上。

核心洞察：

> 實作任務驗證靠執行、測試、assert；認知任務驗證要靠證據分級、反例檢查、多實例掃描——這是完全不同的驗證範式。

具體做法（CLAUDE.md Section 11 事實主張閘門）：把主張的證據分 A 級（字面 / 自我宣告）/ B 級（間接），做反例檢查（若為真應觀察到 X、若為假會觀察到 Y），做共用值檢查。強證據才能寫 memory / 給確定答案；弱證據必須明說「仍不確定」。

> ⚠️ 誠實邊界：事實主張閘門是「模型驗自己」，有循環依賴（確認偏誤正是讓它信弱證據的機制）。真正外部的把關是用戶質疑（Section 12 質疑熔斷）。workflow 可用時可派獨立 context skeptic 重做反例檢查，打破同源天花板（只降低不解決）。

歷史證據：問題追蹤 #003（單線索 → 事實）/ #004（忽視字面證據）/ #005（共用值私有化），皆 2026-04-22 GS 誤判事件升格種子條目。

## 按任務等級選編排

不是每個任務都走重編排。CLAUDE.md Section 1 先判等級：

| 等級 | 怎麼處理 |
|------|---------|
| 微小（< 50 行 · 單檔） | 直接做，但 L1 hook 因果鏈 + 事實求證文字層仍跑 |
| 中型（1-3 檔 · < 300 行） | 輕量流程：設計自檢 → 實作 → 審查 → 測試 → 迷你追溯（可選開 `/dev-review`）|
| 大型（≥ 3 檔或 ≥ 300 行且多子系統交互） | 開 workflow：`/dev-design` → 實作 → `/dev-review` →（可選）`/dev-verify` |
| PRD / 架構設計（需求未定 / 多方案取捨） | 強制開 workflow：`/dev-prd` 或 `/dev-design` |

就像不會為了釘一根釘子叫整條產線——小任務直接做，大任務才開編排。但「先想清楚會牽動誰、事實對不對」這道承重核，連釘一根釘子都要做。

## 獨立審查：為什麼要用全新 context 的 agent

方法論最防偏見的設計，是審查永遠由**不知道設計怎麼想出來的**獨立 agent 做。v7 用 workflow 的多 agent 編排 + 對抗驗證實現：

- **`/dev-design`（取代舊 Phase 1+1b）**：多方案架構 → adversarial-verify 砍缺陷 → 設計規格（含 BC-x）。審查 agent 沒有設計過程的推理 context，只看設計結果、原始需求、現有結構，才能用新鮮的眼光問「真的沒有更好的做法嗎？」。分兩個角度——挑戰式（有更好方案嗎？過度設計嗎？）+ 驗證式（邊界夠嗎？錯誤處理有漏洞嗎？有 update/tick 迴圈時執行順序定義了嗎？）。
- **`/dev-review`（取代舊 Phase 3）**：parallel 跑 correctness / security / repro 三個視角 → 對抗驗證 findings。檢核 agent 不會因為「我剛寫了這段」而下意識放水。安全審查視場景決定（純本地無網路可跳過）。
- **`/dev-verify`（取代舊 Phase 5，可選）**：對可枚舉項做 adversarial-verify + 輕量 verifier 做反向遍歷（找死碼 / 未實作）。

為什麼要獨立？因為同一個 agent 從設計做到測試，帶著所有推理過程的記憶，自證時會傾向合理化之前的決定——球員兼裁判。獨立 context 切斷認知偏見的傳遞鏈（不能完全消除「都是 Claude」的限制，但審查者至少不被前序推理污染）。

> ⚠️ workflow 不可用時：這些審查退化為主 agent inline 自審或用 Task 工具委派子 agent（見 CLAUDE.md Section 14），獨立性會打折，但承重核的 hook 那半（因果鏈）不受影響、事實求證文字層仍跑（這個不對稱見上方「三層架構」）。

## 自證：雙向追溯與一致性驗證

自證（`/dev-verify` 或中型的迷你追溯）的特別之處，不在「程式跑出來對不對」，而在「前面所有人說的話有沒有互相矛盾」：

- **正向**：設計規格 → 程式碼有沒有實作？→ 測試有沒有覆蓋？
- **反向**：程式碼中的每個行為 → 設計規格裡有沒有對應？沒有的是遺漏設計還是多餘程式碼？
- **交叉比對**：正向缺失與反向冗餘互為補充，即時比對。

**自證不是重複測試，而是在做「跨產出物的一致性驗證」。**

**中型任務的迷你追溯**：中型不開 `/dev-verify`，但在測試通過後、commit 前由主 agent 自己逐項列表，確認每個 BC-x 有實作（檔案:行號）和測試（測試名稱），同時追蹤品質審查的 medium 問題是否已由用戶決策。只做正向覆蓋，不做反向分析——中型範圍小（1-3 檔），反向分析的 ROI 不值得。有任何 ❌ 就禁止 commit。

## 跟你可能聽過的東西的差別

| 方法 | 在檢查什麼 | 本方法多了什麼 |
|------|-----------|--------------|
| Code Review | 程式碼品質好不好 | 程式碼跟設計有沒有對齊 + 改動會牽動誰 |
| 單元測試 | 程式跑出來對不對 | 測試有沒有覆蓋設計裡提到的所有情況 |
| CI/CD | 建置和測試有沒有通過 | 所有環節的產出物之間有沒有矛盾 |
| V-Model | 每個開發階段有對應的驗證 | 驗證「跨階段」的一致性 + 前提事實對不對 |

這套方法不是要取代上面這些，而是在它們之上多加「承重核（因果鏈 + 事實求證）」+「跨產出物自證」來抓它們抓不到的問題。

## 場景適配

CLAUDE.md Section 5 的**領域偵測與規則預設**讓承重核與審查根據專案類型自動調整嚴格度——不是「降低標準」，而是「把資源分配給真正有價值的檢查」。例如純本地遊戲不需要安全審查，省下的資源讓品質審查做更深的分析。領域未匹配時用最嚴格（後端 API）預設，確保不會漏檢。

## 子 agent 失敗與斷點熔斷

workflow / 委派大量使用子 agent，子 agent 可能超時或輸出不完整。失敗處理確保流程不卡住：重試一次 → 主 agent 自行執行（標記「降級自審」）→ 結果標記品質降級，保留可追溯性。

斷點是品質閘門——發現問題就回退修正。但反覆回退只會浪費資源。**斷點熔斷**機制像電路斷路器——正常情況讓電流通過（允許回退），短路時跳閘（同一階段累計 3 次 → 暫停 → 先追加學習日誌 → 用 AskUserQuestion 讓人決定繼續修正 / 降級 / 重新設計）。

## 常見設計缺陷預防清單

`/dev-design` 與中型的設計自檢時，可參照一份壓測中最常見的設計缺陷清單（如 update/tick 順序未定義、資源未釋放、不可達狀態等）。這是「學習累積」機制——把歷次踩過的坑整理成清單，像飛行員的起飛前檢查表，不是限制你的能力，而是防止已知的低級失誤。

## 回顧式學習

預防清單是手動維護的靜態列表。**學習日誌**（`.claude-loop/learning-log.md`）讓失敗教訓自動沉澱。

核心原則：**只記導致回頭重做的事件**。斷點觸發（程式碼 bug 被攔截）、設計根本缺陷（high severity）、熔斷（反覆修不好）、任務升級（規模誤判）——這些是真正的教訓。日常的 medium 修正是系統正常運作，不需要「學習」。

每個事件記錄四件事：**什麼問題、什麼原因、怎麼修的、下次要注意什麼**。下次做類似功能時，設計前（CLAUDE.md Section 6）讀這份日誌，不只知道「資源洩漏出現過 3 次」，而是知道每次是什麼具體模式、什麼根因、怎麼修的。

關鍵設計：**失敗事件發生時立即記錄**，不等流程結束。這樣即使 session 中斷或用戶放棄，教訓也已落地。PostToolUse Hook 在 git commit 後檢查 learning-log 是否在 commit 中，作為最後防線。

跟 claude-mem 的差別：claude-mem 存語意記憶（「為什麼選了 A 方案」），學習日誌存事件記錄（「什麼問題因為什麼原因被攔截」）。claude-mem 幫你回憶決策理由，學習日誌幫你識別重複出現的失敗模式。

## 升格-降級機制（兩層教訓架構）

learning-log 累積 ≥ 3 次同類根因 → 偵測升格候選 → 用戶確認後寫入問題追蹤「長期警惕模式」（active），設計前必讀。升格後 n=10 個任務無新證據 → 偵測降級候選 → 用戶確認後移至「條件式紀律」（⏸️）。條件式條目 m=5 內 ≥ 2 次命中 → 自動升回 active（無需用戶確認）。

## 兩層教訓查詢與設計文件同步

- **設計前查兩層教訓**（CLAUDE.md Section 6）：先讀問題追蹤「長期警惕模式」（必讀，R-3），再掃 learning-log 補充，設計產出末尾標示查詢結果。
- **設計文件同步**：改動影響 BC-x 語意時必須同步更新設計規格。否則自證的反向分析會把「文檔沒更新」報成發現，淹沒真正的設計-實作矛盾。

## 理解確認

各種守衛防止 AI 做錯事——但如果 AI 從一開始就理解錯用戶的意思，再多守衛也只是「正確地做了錯的事」。

理解確認在最上游把關（L1 hook 閘門 A）：透過 Hook 協作形成阻擋式閘門，強制 AI 動手前先輸出「我收到的是這個意思，我打算這樣做」，用戶確認方向對了才放行——不對頻就不讓改。

## 同類掃描

各種守衛都沿著「這次修改」的縱向深度走。但有一類問題抓不到：**你改的步數夠不夠？**

舉例：系統有 18 張圖，用戶說「第 2 張圖的 alt 屬性沒加」。只修第 2 張圖就結束，其他 17 張有同樣問題也不會被發現。

同類掃描（CLAUDE.md Section 10）補這個橫向缺口：先判斷修改對象是不是屬於同類項目，是就掃描同類有沒有同樣問題，報告用戶後才執行。預設只掃同目錄的直接同類，用戶需要時才升級到全專案。

## 模組化與功能/UI 分層

開發一個專案時，很多功能模組的核心邏輯大同小異——用戶認證、權限管理、CRUD 操作、資料驗證。但使用者介面每次都不一樣，因為它跟具體的產品需求和設計風格綁在一起。

如果功能邏輯和 UI 混在一起寫，每次改 UI 都要動到功能層，每次複用功能都要把 UI 一起搬。結果就是：要嘛整個模組照搬再大改，要嘛從零開始。

設計時（`/dev-design` 或中型的設計自檢）要求**聲明分層結構**：有使用者介面的模組必須拆成功能層和 UI 層。功能層不依賴 UI 框架——這是唯一的硬規則。審查時（`/dev-review` 引用 design-reviewer 素材庫的分層審查維度）會驗證依賴方向是否正確（功能層有沒有反向依賴 UI）。

就像蓋房子時把水電管線和裝潢分開——管線（功能層）走完驗收，裝潢（UI 層）可以隨時換風格而不動管線。

## 模組登記

閉環通過的模組會登記到模組清單（`.claude-loop/module-registry.md`），記錄名稱、分層結構、功能層的公開 API。下次開發新功能時，設計前先查這份清單——有現成的功能層就直接複用，只設計新的 UI 層或新增功能。

這不是額外的文件工作。模組登記是流程自然產出的索引，目的是讓做過的東西能被找到，避免重複造輪子。

## 橫切自檢層

前面所有機制都把 Karpathy 4 原則「切片」到不同階段——設計對應 Think、寫碼對應 Surgical、測試 / 自證對應 Goal。但 cross-cutting concerns 不該被切片：寫碼時也該先 Think（這檔的呼叫者假設是什麼）、自證時也該檢查 Simplicity（產出物冗餘）。

CLAUDE.md Section 0「四原則橫切自檢層」是這個切片問題的補丁——4 個自問（Q1 Think / Q2 Simplicity / Q3 Surgical / Q4 Goal）橫切所有階段。對映表把每個 Q 連到既有閘門，不是新發明機制——是把既有機制重組成「橫切視角」。

來源是 [andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills) repo 的 Karpathy 4 原則，閉環從「實作方法論 + 認知方法論」升級為「實作 + 認知 + 行為哲學」。

## 主動質疑（三方認知驗證）

認知驗證不是單向的——AI 會錯、用戶會錯、Claude 對自己的推論也會錯。三者互為制衡：

| 觸發方向 | 機制 | 主動方 |
|---------|------|--------|
| Claude 對自己推論升格事實 | Section 11 事實主張閘門 | Claude 自查 |
| Claude 對用戶斷言事實 | Section 11.5 第 5 條 | Claude 反問用戶 |
| 用戶對 Claude 結論 | Section 12 質疑熔斷協議 | 用戶質疑（白名單句式） |

設計精神：push back 不是不尊重用戶，是強制讓用戶看到代價再決定。反模式：對所有需求都 push back（多嘴）/ push back 後不接受用戶決定（越權）/ 無具體替代方案。

## Anti-Patterns Summary（仿 Karpathy EXAMPLES.md）

| 原則 | Anti-Pattern | 修正 |
|------|------------|------|
| Q1 Think | 默默選一種解讀就動手 | 列假設、有歧義列選項、必要時 push back |
| Q2 Simplicity | Strategy pattern 處理單一計算 | 一個函式直到複雜度真的需要 |
| Q3 Surgical | 修 bug 順手 reformat 引號 / 加 type hints | 只改解 bug 的那幾行 |
| Q4 Goal | 「我先 review 再改善」 | 「寫測試重現 bug → 讓它通過 → 確認無回歸」 |

詳見 CLAUDE.md Section 0 對映表。每條 Anti-Pattern 對應 4 原則之一——4 原則自檢失效時，這個對照表是檢測信號。

## 紀律保底層（反向劃線）

自治原則（Section 0 四原則）+ 機械化（Hook 阻擋 + 閘門）皆失效時的紀律兜底。對應 CLAUDE.md Section 12.6 五條反向劃線 R-1~R-5：

| R-x | rule 摘要 | 為何反向劃線 |
|-----|----------|-------------|
| R-1 | 質疑熔斷協議 / 事實主張閘門不可 bypass | 用戶口頭命令繞過 = 認知驗證上游失效 |
| R-2 | 方法論修改 / 重大認知性產出強制 cross-source review | #007 升格實證 single-LLM 自評漏看率 50-67% |
| R-3 | 升格 / 降級 / 兩層教訓查詢不可 bypass | 「急」是 #006 行數膨脹的主要藉口 |
| R-4 | 架構體質拆解 + 合理性自檢不可省略 | 規格清楚 ≠ 設計合理 |
| R-5 | 連續 ≥ 2 次 needs-attention 強制降級 scope | #007 第 2 次實證：漏看率反升至 67% |

設計精神：R-1~R-5 不是「建議」是「劃線」。自治判斷可繞過、機械化可被關，但反向劃線不可——這是 #007 升格教訓對「自評可靠性」的最終回應。

**與 K-16 對照表關係**：本對映表 ≠ 上方「Anti-Patterns Summary」（K-16）。K-16 對映 anti-pattern → Q1-Q4 四原則，是自治層輔助；本對映表對映 R-1~R-5 → Section 11/12 紀律，是保底層兜底。兩表並存不衝突，分屬「自治建議」與「紀律劃線」兩個層次。
