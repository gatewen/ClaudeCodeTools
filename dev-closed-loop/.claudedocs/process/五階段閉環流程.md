# 五階段閉環流程

## 全景圖

```
用戶需求
  ↓
[Section 6] 領域偵測 → 套用領域預設（EH-x/安全審查/驗證層級/單檔上限）
  ↓
[Phase 1] 架構師 📐 → 產出：設計規格
  ↓
[Phase 1b] 設計審查 🔬 → 產出：DR-x 審查報告（獨立子 agent）
  ↓                ↑
  ├── DR-x high？→ 回到 Phase 1 修正（最多 3 輪，全量重審）
  ├── DR-x arch-risk？→ 記錄但不阻擋，Phase 5 追蹤
  ↓
[Phase 2] 程序設計師 💻 → 產出：程式碼
  ↓
  🔧 code-simplifier 強制優化（不能跳過，除非用戶明確說保留原始碼）
  🔄 設計文件同步（特定觸發條件下同步更新設計規格）
  ↓
[Phase 3] 檢核師 🔍 → 產出：檢核報告
  ↓                ↑
  ├── 斷點 A：有嚴重問題？→ 回到 Phase 2 修正（差分審查：只審修改檔案+依賴檔案）
  ↓
[Phase 4] 測試師 🧪 → 產出：測試報告
  ↓                ↑
  ├── 斷點 B：測試失敗？→ 回到 Phase 2 修正
  ↓
[Phase 5] 自証師 ✅ → 產出：自証結果
  ↓                ↑
  ├── 不通過？→ 回到指定的 Phase 修正
  ↓
完成 ✅ → commit

斷點熔斷：同一 Phase 斷點累計觸發 3 次 → 暫停，問用戶怎麼辦
```

## 什麼時候要走完整閉環

**要走的情況：**
- 新寫一個函式、類別或模組
- 改動範圍影響到 3 個以上的函式
- 碰到安全相關的程式碼（登入、加密、權限）
- 用戶明確說「完整閉環」

**不用走的情況：**
- 修 1-3 行的明顯 bug
- 改錯字、更新註解
- 調設定檔
- 純文件更新

**用戶隨時可以覆蓋：**
- 說「完整閉環」→ 不管多小都走全流程
- 說「快速修改」→ 不管多大都跳過閉環

## 領域自動偵測（Section 6）

Phase 1 前會根據專案語言、框架、imports 自動偵測領域，套用對應的預設規則。用戶可覆蓋。

| 領域 | EH-x | 安全審查 | 驗證層級預設 | 單檔上限 |
|------|------|---------|------------|---------|
| 遊戲開發 | 可選 | 可跳過 | 預設 `[framework-dependent]` | 400 行 |
| 後端 API | 必要 | 必要 | 預設 `[testable]`，無需標注 | 300 行 |
| 前端 SPA | 條件判定 | 條件判定 | 混合，須逐項標注 | 300 行 |
| CLI 工具 | 條件判定 | 條件判定 | 預設 `[testable]`，無需標注 | 300 行 |
| 系統程式 | 必要 | 必要 | 預設 `[testable]`，無需標注 | 300 行 |

**「預設 `[testable]`，無需標注」**的意思是：該領域的 BC-x/EH-x 一律視為可自動化測試，只有例外（渲染/動畫等）才需標注 `[visual-only]` 或 `[framework-dependent]`。這樣可以省去大量重複標注。

## 各階段詳細說明

### Phase 1：架構師 📐

**用白話說**：先想清楚要做什麼、怎麼做，畫出藍圖再動手。

**做什麼**：
- **架構體質拆解**（涉及現有模組時）：設計之前，先用第一性原理拆解相關的現有架構——每個模組/層級為什麼存在？這些理由今天還成立嗎？有沒有東西兩邊都不需要了可以一起移除？現有架構能支撐這次改動加未來擴展嗎？發現地基不穩 → 告知用戶，建議先修架構
- 把用戶的需求翻譯成技術設計
- 定義函式的名字、吃什麼參數、吐什麼結果
- 想清楚會遇到哪些邊界情況（例如：輸入是空的怎麼辦？數字超大怎麼辦？）
- 若有外部 I/O → 想清楚會遇到哪些錯誤（例如：網路斷了怎麼辦？檔案不存在怎麼辦？）；純本地計算 → EH-x 可選，聲明「無外部 I/O」（具體按領域預設）
- 若有 update/tick/frame 迴圈 → 必須定義步驟執行順序（虛擬碼等級）
- 每個 BC-x/EH-x 標注驗證層級：`[testable]`（可自動化測試）、`[visual-only]`（渲染/動畫）、`[framework-dependent]`（需框架 runtime）。領域預設為 `[testable]` 的不用逐項標注，只標例外
- **（可選）PRD 需求分解**：如果用戶給了 PRD 或需求文檔，先把它拆成編號需求項（PRD#1, PRD#2...），再設計 BC-x/EH-x 並標注每項來自哪個 PRD#n
- **常見缺陷預防**：首次使用閉環或不熟悉的領域時，參考本文件末尾的「常見設計缺陷預防清單」

**不做什麼**：
- 不寫程式碼，只寫規格
- 不做超出需求範圍的設計

**必須交出來的東西**：設計規格（格式見 [產出物格式](../standards/產出物格式.md#設計規格)）

**⛔ 閘門（逐項檢查清單）**：
- [ ] 架構體質拆解已完成（或全新模組不適用）
- [ ] 合理性自檢已通過（或用戶確認接受）
- [ ] 所有參數有型別
- [ ] BC-x ≥ 2
- [ ] EH-x 符合領域預設（必要時覆蓋異常；可選時已聲明不適用）
- [ ] 涉及 status 變更的 BC-x 有行為約束
- [ ] 有 update/tick 迴圈時已定義執行順序
- [ ] 驗證層級已標注（或領域預設為 `[testable]` 時例外項已標注）
- [ ] （若有 PRD）所有 PRD#n 有 ≥ 1 對應 BC-x/EH-x

全部 ✅ → 進 Phase 1b。

### Phase 1b：設計審查 🔬

**用白話說**：找另一個人來看你的藍圖，看看有沒有更好的做法、有沒有漏想的情況。

**跟 Phase 3 的差別**：Phase 3 是「程式碼寫完後檢查品質」，Phase 1b 是「動手前先確認藍圖本身夠不夠好」。

**獨立性**：用 Task 工具啟動一個全新的子 agent，這個子 agent 不知道架構師是怎麼想出這個設計的，它只看到設計結果。這樣才能用新鮮的眼光挑問題。

**產出寫入檔案**：子 agent 必須將 DR-x 報告寫入 `.claude-loop/artifacts/P1b-design-review.md`。Phase 5 Part C 會驗證此檔案存在。

**可以跳過嗎？** 可以。用戶說「跳過設計審查」就直接進 Phase 2。適合用在熟悉的、重複性的設計模式。

**子 agent 拿到什麼**：
- Phase 1 的設計規格（邊界條件、錯誤處理清單）
- 用戶原始的需求描述
- 專案結構摘要（一層目錄 + 每個模組一句話職責 + 現有介面契約）

**做什麼**：
- **挑戰**：有沒有更好的架構方案？設計會不會太複雜或太簡單？BC-x 數量跟功能複雜度匹配嗎？
- **架構體質**：新設計是建在穩固的基礎上，還是在脆弱/過時的架構上堆疊？現有模組的存在理由還成立嗎？有沒有多餘的層級可以移除？這個架構能支撐未來擴展嗎？
- **驗證**：每個邊界條件的預期行為可以測試嗎？錯誤處理有沒有漏掉外部失敗（網路/IO/權限/並發）？資源管理有沒有配對？有 update/tick 迴圈時執行順序是否已定義？

**必須交出來的東西**：DR-x 審查報告（格式見 [產出物格式](../standards/產出物格式.md#設計審查報告)）

**嚴重度定義**（v5.5 新增 arch-risk）：
- **high**：邏輯缺陷、遺漏關鍵邊界情境、或存在明顯更優的替代方案 → 觸發閘門回退
- **arch-risk**：架構設計存在長期風險但不影響當前正確性（如擴展性瓶頸、耦合度偏高）→ 不觸發閘門，記錄到 Phase 5 追蹤
- **medium**：設計可改善但不影響正確性
- **low**：風格偏好或微小建議（合併摘要）

**閘門規則**：
- 有 high 問題 → 回 Phase 1 修設計 → 重跑 Phase 1b（全量重審）
- 有 arch-risk → 記錄但不阻擋，Phase 5 追蹤
- 只有 medium/low → 呈現給用戶決定要不要改
- 沒問題 → 進 Phase 2

**迭代規則**：
- 本輪無新 high → 通過（arch-risk/medium/low 記錄但不阻擋）
- 最多 3 輪。第 3 輪仍有新 high → 主 agent 介入判斷設計是否需重構
- 為什麼全量重審不做差分：設計規格是相互耦合的文件，修一處可能破壞另一處假設（壓測實證：修正 DR-4/5 引入了新的 DR-13）

### Phase 2：程序設計師 💻

**用白話說**：按照藍圖施工，不要自作主張加東西。

**做什麼**：
- 嚴格按照 Phase 1 的設計規格寫程式碼
- 設計裡提到的每個邊界條件和錯誤處理都要實作
- 遵守專案現有的命名和程式碼風格

**不做什麼**：
- 不自己加設計裡沒有的功能
- 不改動設計規格（覺得設計有問題就回報，不要自己改）

**每步上限**：最多 2-3 個檔案或約 300 行。**依賴捆綁**：有強型別依賴的檔案（拆開會導致增量驗證失敗）可捆綁在同一步，即使超過 3 檔。

**單檔上限**：按領域預設（遊戲開發 400 行，其他 300 行）。**內聚性豁免**：超出上限但模組內聚度高（拆分會增加跨模組耦合且無自然拆分點）時，可放寬並在檔案頂部註記原因。

**必須交出來的東西**：可以跑的程式碼

**🔧 強制程式碼優化（進入 Phase 3 前必須做）**：

程式碼寫完後，必須用 `code-simplifier` 優化所有新增和修改的程式碼。這一步的目的是防止 AI 偷懶——不能把舊程式碼原樣照搬過來就算完事，必須審視有沒有更簡潔、更一致的寫法。

code-simplifier 審查三件事：
- **清晰度**：命名表意、邏輯一目了然
- **一致性**：風格跟專案慣例對齊
- **可維護性**：去除不必要的複雜度

注意：code-simplifier 只能簡化「怎麼寫」，不能改「做什麼」。功能行為必須跟 Phase 1 的設計規格一致。

唯一可以跳過的情況：用戶明確說「保留原始碼」或「不要優化」。

**🔄 設計文件同步**：

以下情況須同步更新設計規格（不修改 ID，只更新描述）：
- bug 修正改變了 BC-x 描述的預期行為
- code-simplifier 改變了函式簽名或參數型別
- 測試揭示設計規格的描述有歧義需要澄清

不觸發同步：純重命名（不影響語意）、程式碼風格調整、新增內部 helper 函式。

**什麼情況算通過**：
- 程式碼沒有語法錯誤
- 設計規格裡的每個項目都有對應的程式碼
- code-simplifier 已執行完畢

### Phase 3：檢核師 🔍

**用白話說**：找碴。看看程式碼有沒有問題、安不安全、跟設計對不對得上。

**獨立性**：品質審查用一個獨立子 agent（Task 工具）。安全審查視領域預設和條件決定是否執行。子 agent 不知道程式碼是怎麼寫出來的，只看到設計規格和程式碼本身。

**產出寫入檔案**：品質審查子 agent 寫入 `.claude-loop/artifacts/P3-quality-review.md`，安全審查子 agent（若執行）寫入 `.claude-loop/artifacts/P3-security-review.md`。

**安全審查什麼時候可以跳過**：
同時滿足以下全部條件時可跳過，在品質審查報告末尾標記原因：
- 無網路連線（含 WebSocket/fetch/API 呼叫）
- 無使用者敏感資料處理
- 無檔案系統寫入（僅限本地設定檔讀取除外）
- 無 unsafe/eval/動態程式碼執行
- 無第三方認證/授權流程

**做什麼**：
- 檢查程式碼邏輯跟設計規格是不是一致
- 檢查程式碼品質（命名清不清楚、有沒有重複的程式碼）
- 檢查安全性（有沒有驗證輸入、有沒有注入風險）——若未跳過
- 檢查邊界處理（null、空字串、超大數字這些有沒有處理）
- 檢查跨模組資料流（模組間傳遞的資料在拆分邊界是否保持語意正確）
- 若專案有部署語言指南，**必須**讀取 Phase 3 段落做語言專屬審查，問題標 `[語言名]`

**每個問題標嚴重度**：
- **high**：邏輯錯誤、安全漏洞、跟設計不符 → 一定要修
- **arch-risk**：架構風險但不影響當前正確性 → 不觸發斷點 A，記錄到 Phase 5 追蹤
- **medium**：品質問題、未來可能出事 → 建議修
- **low**：風格建議、小改進 → 合併摘要

**必須交出來的東西**：檢核報告（格式見 [產出物格式](../standards/產出物格式.md#檢核報告)）

**⚠️ 斷點 A**：如果有任何 high 問題 → 回到 Phase 2 修正 → 修完後重跑 Phase 3。arch-risk 記錄但不阻擋。

**斷點 A 回退後的差分審查**：
回退修正後，不需全量重審，改用範圍限定的品質審查：
1. 被修改的檔案 → 全量審查
2. 依賴被修改檔案的檔案 → 只看呼叫點
3. 無關檔案 → 跳過
4. 原 R-x high → 逐項確認修復
安全審查不需重跑。

### Phase 4：測試師 🧪

**用白話說**：用實際的測試來驗證程式碼做的事情跟設計說的一不一樣。

**做什麼**：
- 對照 Phase 1 的設計規格，為每個 `[testable]` 邊界條件寫測試
- 對照 Phase 1 的設計規格，為每個 `[testable]` 錯誤處理寫測試
- `[visual-only]` 和 `[framework-dependent]` 項在測試報告中列出並標注驗證方式（如 code review、手動驗證）
- 正常使用路徑至少寫一個測試
- 用專案的測試框架跑測試，拿到實際結果

**覆蓋要求**：
- `[testable]` 設計項 100% 自動化測試覆蓋
- `[visual-only]`/`[framework-dependent]` 項必須列出替代驗證方式
- 測試修正程式碼時同步更新設計規格

**必須交出來的東西**：測試程式碼 + 測試報告（格式見 [產出物格式](../standards/產出物格式.md#測試報告)）

**⚠️ 斷點 B**：如果有測試失敗 → 回到 Phase 2 修正 → 重跑 Phase 3 和 Phase 4

### Phase 5：自証師 ✅

**用白話說**：把前面所有人交出來的東西攤開來，看看有沒有互相打架的地方。

**跟前面的 Phase 有什麼不同**：Phase 1-4 都是同一個 agent 在做，Phase 5 的核心檢查（雙向追溯）改由**單一獨立子 agent** 執行。這個子 agent 不知道前面的推理過程，只看到產出物本身，用新鮮的眼光做正向和反向的交叉比對。

**v5.4 變更**：原本 Part A（正向追溯）和 Part B（反向分析）由兩個獨立子 agent 分別執行。v5.4 合併為單一子 agent 做雙向追溯，理由：單一 agent 可即時交叉比對正向缺失和反向冗餘，品質優於兩個 agent 各做一半再調和。

**產出寫入檔案**：雙向追溯子 agent 寫入 `.claude-loop/artifacts/P5AB-bidirectional-tracing.md`。Part C 在步驟 8 前做驗證：
1. **產出物檔案驗證**：確認 `.claude-loop/artifacts/` 下產出物檔案全部存在（用戶跳過 1b、安全審查 by-design 跳過時對應檔案除外）
2. **委派呼叫驗證**：讀取 `.claude-loop/artifacts/.delegation-log`（由 Hook 自動寫入）。delegation-log 缺失但產出物存在時，以產出物存在為準（Hook 可能因平台相容性未觸發）

**怎麼分工**：
- **Part AB（雙向追溯）**：單一獨立子 agent 做。同時做正向追溯（設計→程式碼→測試）和反向分析（程式碼→設計），即時交叉比對。
- **Part C（整體評估）**：主 agent 收集 Part AB 結果，跑全專案驗證，做最終判定。

**子 agent 拿到什麼（驗證包）**：
- Phase 1 設計規格全文（BC-x/EH-x/IF-x 清單，含驗證層級）
- Phase 1b DR-x 審查報告（含 arch-risk 項目清單）
- Phase 3 R-x 檢核報告（含 arch-risk 項目清單）
- Phase 2 程式碼檔案路徑清單（子 agent 自行讀取比對）
- Phase 4 測試檔案路徑清單（子 agent 自行讀取比對）
- PRD 分解表（若有）、語言指南部署狀態

**子 agent 的角色定義**：「你是獨立自証審查者（雙向追溯），與開發者無關，不知道開發過程」

**做什麼**（七個維度逐一檢查）：

| 維度 | 在比對什麼 | 怎樣算通過 |
|------|-----------|-----------|
| PRD-設計覆蓋（若有 PRD） | PRD 裡的每個需求項，設計規格都有對應嗎？ | 每個 PRD#n 有 ≥ 1 個 BC-x/EH-x |
| 設計審查閉合 | Phase 1b 的 DR-x high 都修了嗎？medium 有用戶決策記錄嗎？ | high 已修正、medium 有決策記錄 |
| arch-risk 追蹤 | Phase 1b 和 Phase 3 標記的 arch-risk 項目，是否在後續 Phase 中已緩解或仍存在？ | 每項都有追蹤記錄 |
| 設計-實作一致性 | 設計規格裡的每個項目，程式碼裡都有做到嗎？ | 沒有遺漏 |
| 實作-測試覆蓋 | `[testable]` 設計項都有自動化測試嗎？其他項有標注驗證方式嗎？ | `[testable]` 100% 覆蓋 + 其他項有驗證記錄 |
| 檢核-修正閉合 | 檢核報告裡的 high/medium 問題，都處理了嗎？ | 沒有未處理的 high/medium |
| 語言審查覆蓋 | 若有語言指南：檢核報告有包含帶 `[語言名]` 標記的項目嗎？ | 有語言專屬項（或無語言指南則跳過） |
| 產出物完整性 | 每個階段都有交出東西嗎？ | 產出物都在（安全審查跳過時除外） |

**必須交出來的東西**：自証結果（格式見 [產出物格式](../standards/產出物格式.md#自証結果)）

**不通過時的回退規則**：

| 發現的問題 | 回到哪裡 | 為什麼 |
|-----------|---------|--------|
| 設計審查 high 未修 | Phase 1 | DR-x 指出的架構缺陷未處理 |
| 設計審查決策未記錄 | 補記錄 | medium 的用戶決策需留存供追溯 |
| arch-risk 未追蹤 | 補追蹤記錄 | 需記錄當前狀態供後續評估 |
| 設計跟程式碼對不上 | Phase 2（嚴重的話回 Phase 1） | 要嘛實作錯了，要嘛設計就有問題 |
| 測試沒覆蓋到 | Phase 4 | 測試計畫漏了東西 |
| 檢核問題沒修 | Phase 2 | 已知問題沒處理 |
| 缺產出物 | 缺的那個 Phase | 某個階段沒做完 |

## 子 agent 失敗處理（全域規則）

子 agent（Phase 1b/3/5 的 Task 委派）超時、輸出為空、或明顯不完整時：
1. **第一次失敗**：重試一次（相同 prompt）
2. **第二次失敗**：主 agent 自行執行相同審查（標記「降級自審」）
3. 降級自審的結果在 Phase 5 產出物驗證中標記，不視為缺失但記錄品質降級

## 斷點熔斷（全域規則）

同一 Phase 的斷點累計觸發 **3 次** → 暫停流程，用 AskUserQuestion 報告情況，由用戶決定：
- 繼續嘗試修正
- 降級為精簡閉環完成剩餘工作
- 重新設計（回 Phase 1 重新開始）

## 精簡閉環（中型任務）

中型任務觸發五步流程：設計→設計快審→實作→品質審查→測試驗證。

**跟完整閉環的差別**：
- 設計快審只跑 1 輪（不回退重審）
- 品質審查同完整閉環，但不含安全審查
- 不跑 Phase 5 自証
- 斷點 A 回退用差分審查

**什麼時候用精簡閉環**：
- 新增單一函式/元件 · 1-3 檔案 · < 300 行（內聚性豁免可放寬行數）
- 用戶沒有說「完整閉環」

## 配額管理策略

多階段連續開發時，子 agent 委派配額可能在 session 後半段耗盡。

**降級優先順序**（先降低價值的）：
1. P5 雙向追溯 → 主 agent 自審
2. P3 安全審查 → 跳過（需滿足跳過條件）
3. P1b → 降為單輪不回退
4. P3 品質審查 → ⛔ **不可降級**

## 多函式的情況

如果一個需求要寫好幾個函式：

1. **每個函式各跑一次閉環**（方法層級）
2. 全部函式的閉環都通過後，再跑一次**模組層級的閉環**
3. 模組層級多驗證的東西：函式之間的協作對不對、職責有沒有劃清楚
4. **單模組 vs 多模組判定**：子系統共享核心狀態物件且 API 邊界不清晰 → 視為單模組；子系統有獨立狀態且透過明確介面溝通 → 視為多模組

詳見 [層級擴展](層級擴展.md)

## 常見設計缺陷預防清單

Phase 1 設計時可參考。首次使用閉環或不熟悉的領域時建議逐項檢查。

| # | 常見缺陷 | 怎麼防 |
|---|---------|--------|
| 1 | update/tick 步驟順序未定義 | 有迴圈就定義虛擬碼等級的步驟順序，標明依賴和副作用 |
| 2 | 資源建立後未釋放 | 每個 open/create/subscribe 配對 close/destroy/unsubscribe |
| 3 | 不可達的狀態 variant | 確認每個 enum variant 都有進入路徑，無用的刪除 |
| 4 | 碰撞/交互時機未定義 | 明確在哪一步偵測，偵測後的處理順序和優先級 |
| 5 | UI 與引擎狀態不同步 | 混合架構（Canvas+React、遊戲+UI）需定義同步回調機制 |
| 6 | 跨模組拆分語意遺漏 | 拆分邊界的資料過濾/轉換不得改變下游模組的預期 |
| 7 | 初始狀態不合法 | 預設值/起始位置/初始參數是否符合所有不變量（invariant） |
| 8 | 設計精度不足 | 粒度應到「可直接翻譯為程式碼」，非「方向指引」 |

## 因果鏈分析守衛

每次 AI 要修改檔案（Edit/Write/MultiEdit）的前一刻，PreToolUse Hook 會自動掃描「誰引用了這個檔案」，輸出依賴清單，並**阻擋這次修改**（exit 2）。AI 必須在畫面上顯示因果鏈分析結果，讓用戶看到推導過程，然後**重試修改**——Hook 偵測到已分析過即放行。這是阻擋式守衛，不是提醒式——沒做分析，修改就不會執行。

### 為什麼需要這個

改 A 壞 B 是最常見的 bug 來源。Hook 的掃描只能找到「表面引用」（誰 import 了這個檔案），但真正的因果鏈往往更深——函式簽章沒變但語意變了、初始化順序改了影響下游時序、驗證規則放寬導致上游的極端值打穿。這些不會觸發編譯錯誤，但會造成運行時 bug。

所以 AI 收到 Hook 提醒後，不能只看表面引用就結束，必須做深度推導。

### 分析深度要求

1. **追溯根因**：從需求或 bug 追到「為什麼要改這個檔案」
2. **穿透呼叫鏈**：A 引用 B，B 引用 C。改 C 不能只看 B，要看 A 是否也受影響
3. **語意影響**：介面沒變但行為變了（例如回傳值的含義改變），這種必須標出
4. **狀態與時序**：初始化順序、事件觸發時機、快取策略的改變是否影響依賴特定順序的邏輯
5. **邊界條件**：驗證規則或錯誤處理改變後，上游傳入的極端值是否還能正確處理

### 輸出格式

AI 必須在畫面輸出以下格式，用戶才知道分析有在做：

```
⚠️ [因果鏈分析] 修改 {檔案名}
├─ 根因：{為什麼要改}
├─ 直接影響：{引用此檔案的模組，逐一說明}
├─ 間接影響：{直接影響的下游}
├─ 隱性風險：{不會立即報錯但行為可能改變的情況}
└─ 決策：{連動更新清單，或說明為什麼不需要}
```

### 場景分流

- **Phase 2/4 中**（按設計規格實作）：可省略根因（Phase 1 已定義），但仍須輸出影響分析和決策
- **斷點回退修正**（超出原始設計）：完整分析，包含根因
- **非閉環修改**（微小任務或用戶直接指示）：完整分析

## 合理性審查

每次改動都要退一步想：「這個改動放到整個系統裡，整體還合理嗎？」

### 為什麼需要這個

AI 做事的常見模式是：用戶說什麼就做什麼，只確保功能正確，但不會質疑「這樣做合不合理」。每個改動單獨看都沒問題，但累積起來可能造成：
- 操作流程變得不順
- 解法的複雜度遠超問題本身
- 新功能跟舊功能放在一起風格不一致
- 效率退步但沒人注意到

### 檢查什麼

| 維度 | 問什麼 |
|------|--------|
| 一致性 | 跟系統現有的風格、模式、慣例一致嗎？ |
| 體驗 | 使用者的操作流程有沒有因此變複雜？ |
| 比例 | 解法的複雜度跟問題的規模成正比嗎？ |
| 可操作性 | 日常使用會不會造成不便或效率下降？ |
| 整合性 | 跟其他已有功能放在一起，整體還合理嗎？ |

### 在流程中怎麼做

- **完整閉環**：Phase 1 閘門前有合理性自檢（畫面輸出），Phase 3 品質審查包含合理性維度
- **精簡閉環**：設計自檢包含合理性問題（④⑤）
- **非閉環微小任務**：改完後一句話回答「放到整體合理嗎」
- **連續改動**：第 3 個改動後做一次整合性檢查

重點是**有意識地想過**，不是加 checkbox。發現不合理就主動告知用戶。
