# 五階段閉環流程

## 全景圖

```
用戶需求
  ↓
[Phase 1] 架構師 📐 → 產出：設計規格
  ↓
[Phase 1b] 設計審查 🔬 → 產出：DR-x 審查報告（獨立子 agent）
  ↓                ↑
  ├── DR-x high？→ 回到 Phase 1 修正
  ↓
[Phase 2] 程序設計師 💻 → 產出：程式碼
  ↓
  🔧 code-simplifier 強制優化（不能跳過，除非用戶明確說保留原始碼）
  ↓
[Phase 3] 檢核師 🔍 → 產出：檢核報告
  ↓                ↑
  ├── 斷點 A：有嚴重問題？→ 回到 Phase 2 修正
  ↓
[Phase 4] 測試師 🧪 → 產出：測試報告
  ↓                ↑
  ├── 斷點 B：測試失敗？→ 回到 Phase 2 修正
  ↓
[Phase 5] 自証師 ✅ → 產出：自証結果
  ↓                ↑
  ├── 不通過？→ 回到指定的 Phase 修正
  ↓
完成 ✅ → commit
```

## 什麼時候要走完整閉環

**要走的情況：**
- 新寫一個函式、類別或模組
- 改動範圍影響到 3 個以上的函式
- 碰到安全相關的程式碼（登入、加密、權限）
- 用戶明確說「完整閉環」

**不用走的情況：**
- 修 1-3 行的明顯 bug
- 改錯字、更新註解
- 調設定檔
- 純文件更新

**用戶隨時可以覆蓋：**
- 說「完整閉環」→ 不管多小都走全流程
- 說「快速修改」→ 不管多大都跳過閉環

## 各階段詳細說明

### Phase 1：架構師 📐

**用白話說**：先想清楚要做什麼、怎麼做，畫出藍圖再動手。

**做什麼**：
- 把用戶的需求翻譯成技術設計
- 定義函式的名字、吃什麼參數、吐什麼結果
- 想清楚會遇到哪些邊界情況（例如：輸入是空的怎麼辦？數字超大怎麼辦？）
- 想清楚會遇到哪些錯誤（例如：網路斷了怎麼辦？檔案不存在怎麼辦？）
- **（可選）PRD 需求分解**：如果用戶給了 PRD 或需求文檔，先把它拆成編號需求項（PRD#1, PRD#2...），再設計 BC-x/EH-x 並標注每項來自哪個 PRD#n

**不做什麼**：
- 不寫程式碼，只寫規格
- 不做超出需求範圍的設計

**必須交出來的東西**：設計規格（格式見 [產出物格式](../standards/產出物格式.md#設計規格)）

**什麼情況算通過**：
- 每個參數都有型別定義
- 至少寫了 2 個邊界條件
- 錯誤處理覆蓋了可以預見的異常
- （若有 PRD）每個 PRD#n 都有至少一個對應的 BC-x 或 EH-x

### Phase 1b：設計審查 🔬

**用白話說**：找另一個人來看你的藍圖，看看有沒有更好的做法、有沒有漏想的情況。

**跟 Phase 3 的差別**：Phase 3 是「程式碼寫完後檢查品質」，Phase 1b 是「動手前先確認藍圖本身夠不夠好」。

**獨立性**：用 Task 工具啟動一個全新的子 agent，這個子 agent 不知道架構師是怎麼想出這個設計的，它只看到設計結果。這樣才能用新鮮的眼光挑問題。

**產出寫入檔案**：子 agent 必須將 DR-x 報告寫入 `.claude-loop/artifacts/P1b-design-review.md`。Phase 5 Part C 會驗證此檔案存在。

**可以跳過嗎？** 可以。用戶說「跳過設計審查」就直接進 Phase 2。適合用在熟悉的、重複性的設計模式。

**子 agent 拿到什麼**：
- Phase 1 的設計規格（邊界條件、錯誤處理清單）
- 用戶原始的需求描述
- 專案結構摘要（一層目錄 + 每個模組一句話職責 + 現有介面契約）

**做什麼**：
- **挑戰**：有沒有更好的架構方案？設計會不會太複雜或太簡單？BC-x 數量跟功能複雜度匹配嗎？
- **驗證**：每個邊界條件的預期行為可以測試嗎？錯誤處理有沒有漏掉外部失敗（網路/IO/權限/並發）？資源管理有沒有配對？

**必須交出來的東西**：DR-x 審查報告（格式見 [產出物格式](../standards/產出物格式.md#設計審查報告)）

**閘門規則**：
- 有 high 問題 → 回 Phase 1 修設計 → 重跑 Phase 1b
- 只有 medium/low → 呈現給用戶決定要不要改
- 沒問題 → 進 Phase 2

### Phase 2：程序設計師 💻

**用白話說**：按照藍圖施工，不要自作主張加東西。

**做什麼**：
- 嚴格按照 Phase 1 的設計規格寫程式碼
- 設計裡提到的每個邊界條件和錯誤處理都要實作
- 遵守專案現有的命名和程式碼風格

**不做什麼**：
- 不自己加設計裡沒有的功能
- 不改動設計規格（覺得設計有問題就回報，不要自己改）

**必須交出來的東西**：可以跑的程式碼

**🔧 強制程式碼優化（進入 Phase 3 前必須做）**：

程式碼寫完後，必須用 `code-simplifier` 優化所有新增和修改的程式碼。這一步的目的是防止 AI 偷懶——不能把舊程式碼原樣照搬過來就算完事，必須審視有沒有更簡潔、更一致的寫法。

code-simplifier 審查三件事：
- **清晰度**：命名表意、邏輯一目了然
- **一致性**：風格跟專案慣例對齊
- **可維護性**：去除不必要的複雜度

注意：code-simplifier 只能簡化「怎麼寫」，不能改「做什麼」。功能行為必須跟 Phase 1 的設計規格一致。

唯一可以跳過的情況：用戶明確說「保留原始碼」或「不要優化」。

**什麼情況算通過**：
- 程式碼沒有語法錯誤
- 設計規格裡的每個項目都有對應的程式碼
- code-simplifier 已執行完畢

### Phase 3：檢核師 🔍

**用白話說**：找碴。看看程式碼有沒有問題、安不安全、跟設計對不對得上。

**獨立性**：品質審查和安全審查各用一個獨立子 agent（Task 工具），可以同時進行。跟 Phase 1b 和 Phase 5 一樣，子 agent 不知道程式碼是怎麼寫出來的，只看到設計規格和程式碼本身。

**產出寫入檔案**：品質審查子 agent 寫入 `.claude-loop/artifacts/P3-quality-review.md`，安全審查子 agent 寫入 `.claude-loop/artifacts/P3-security-review.md`。

**做什麼**：
- 檢查程式碼邏輯跟設計規格是不是一致
- 檢查程式碼品質（命名清不清楚、有沒有重複的程式碼）
- 檢查安全性（有沒有驗證輸入、有沒有注入風險）
- 檢查邊界處理（null、空字串、超大數字這些有沒有處理）
- 若專案有部署語言指南，**必須**讀取 Phase 3 段落做語言專屬審查，問題標 `[語言名]`（如 `R-5 [TypeScript]: 使用 any 型別`）

**每個問題標嚴重度**：
- **high**：邏輯錯誤、安全漏洞、跟設計不符 → 一定要修
- **medium**：品質問題、未來可能出事 → 建議修
- **low**：風格建議、小改進 → 記一下就好

**必須交出來的東西**：檢核報告（格式見 [產出物格式](../standards/產出物格式.md#檢核報告)）

**⚠️ 斷點 A**：如果有任何 high 問題 → 回到 Phase 2 修正 → 修完後重跑 Phase 3

### Phase 4：測試師 🧪

**用白話說**：用實際的測試來驗證程式碼做的事情跟設計說的一不一樣。

**做什麼**：
- 對照 Phase 1 的設計規格，為每個邊界條件寫測試
- 對照 Phase 1 的設計規格，為每個錯誤處理寫測試
- 正常使用路徑至少寫一個測試
- 用專案的測試框架跑測試，拿到實際結果

**覆蓋要求**：
- 設計規格裡的每個邊界條件都要有測試
- 設計規格裡的每個錯誤處理都要有測試
- 覆蓋率不到 100% 不能往下走

**必須交出來的東西**：測試程式碼 + 測試報告（格式見 [產出物格式](../standards/產出物格式.md#測試報告)）

**⚠️ 斷點 B**：如果有測試失敗 → 回到 Phase 2 修正 → 重跑 Phase 3 和 Phase 4

### Phase 5：自証師 ✅

**用白話說**：把前面所有人交出來的東西攤開來，看看有沒有互相打架的地方。

**跟前面的 Phase 有什麼不同**：Phase 1-4 都是同一個 agent 在做，Phase 5 的核心檢查（Part A 追溯、Part B 反向分析）改由**獨立的子 agent** 執行。這些子 agent 不知道前面的推理過程，只看到產出物本身，用新鮮的眼光比對。

**產出寫入檔案**：Part A 子 agent 寫入 `.claude-loop/artifacts/P5A-traceability.md`，Part B 子 agent 寫入 `.claude-loop/artifacts/P5B-reverse-analysis.md`。Part C 在步驟 8 前先驗證所有委派產出物檔案存在（`P1b-design-review.md`、`P3-quality-review.md`、`P3-security-review.md`、`P5A-traceability.md`、`P5B-reverse-analysis.md`），缺一不可（用戶跳過 1b 時除外）。

**怎麼分工**：
- **Part A（追溯檢查表）**：獨立子 agent 做。拿到設計規格、程式碼路徑、測試路徑、檢核報告，逐項比對有沒有對齊。
- **Part B（反向分析）**：另一個獨立子 agent 做。讀程式碼反推，找出不在設計裡的行為路徑。
- **Part C（整體評估）**：主 agent 收集 Part A + B 結果，跑全專案驗證，做最終判定。
- Part A 和 Part B **可以同時進行**，因為它們互相獨立。

**子 agent 拿到什麼（驗證包）**：

Part A 驗證包：
- Phase 1 設計規格全文（BC-x/EH-x/IF-x 清單）
- Phase 1b DR-x 審查報告
- Phase 3 R-x 檢核報告
- Phase 2 程式碼檔案路徑清單（子 agent 自行讀取比對）
- Phase 4 測試檔案路徑清單（子 agent 自行讀取比對）
- PRD 分解表（若有）、語言指南部署狀態

Part B 驗證包：
- Phase 1 設計規格（BC-x/EH-x 清單）
- Phase 2 程式碼檔案路徑清單（子 agent 自行讀取分析）

**子 agent 的角色定義**：
- Part A：「你是獨立自証審查者（追溯檢查），與開發者無關，不知道開發過程」
- Part B：「你是獨立自証審查者（反向分析），與開發者無關，不知道開發過程」

**衝突解決**：如果 Part A 和 Part B 的結論互相矛盾（例如 Part A 說 BC-3 ✅ 但 Part B 發現 BC-3 附近有未覆蓋路徑），以 **Part B 為準**（反向分析比正向追溯更深入）。主 agent 重新審視爭議點後判定。仍無法判定時，呈現兩方結論給用戶決定。

**做什麼**（七個維度逐一檢查）：

| 維度 | 在比對什麼 | 怎樣算通過 |
|------|-----------|-----------|
| PRD-設計覆蓋（若有 PRD） | PRD 裡的每個需求項，設計規格都有對應嗎？ | 每個 PRD#n 有 ≥ 1 個 BC-x/EH-x |
| 設計審查閉合 | Phase 1b 的 DR-x high 都修了嗎？medium 有用戶決策記錄嗎？ | high 已修正、medium 有決策記錄 |
| 設計-實作一致性 | 設計規格裡的每個項目，程式碼裡都有做到嗎？ | 沒有遺漏 |
| 實作-測試覆蓋 | 設計規格裡的每個場景，測試都有測到嗎？ | 邊界條件覆蓋率 100% |
| 檢核-修正閉合 | 檢核報告裡的 high/medium 問題，都處理了嗎？ | 沒有未處理的 high/medium |
| 語言審查覆蓋 | 若有語言指南：檢核報告有包含帶 `[語言名]` 標記的項目嗎？ | 有語言專屬項（或無語言指南則跳過） |
| 產出物完整性 | Phase 1-4（含 1b）每個階段都有交出東西嗎？ | 五份產出物都在 |

**必須交出來的東西**：自証結果（格式見 [產出物格式](../standards/產出物格式.md#自証結果)）

**不通過時的回退規則**：

| 發現的問題 | 回到哪裡 | 為什麼 |
|-----------|---------|--------|
| 設計審查 high 未修 | Phase 1 | DR-x 指出的架構缺陷未處理 |
| 設計審查決策未記錄 | 補記錄 | medium 的用戶決策需留存供追溯 |
| 設計跟程式碼對不上 | Phase 2（嚴重的話回 Phase 1） | 要嘛實作錯了，要嘛設計就有問題 |
| 測試沒覆蓋到 | Phase 4 | 測試計畫漏了東西 |
| 檢核問題沒修 | Phase 2 | 已知問題沒處理 |
| 缺產出物 | 缺的那個 Phase | 某個階段沒做完 |

## 多函式的情況

如果一個需求要寫好幾個函式：

1. **每個函式各跑一次閉環**（方法層級）
2. 全部函式的閉環都通過後，再跑一次**模組層級的閉環**
3. 模組層級多驗證的東西：函式之間的協作對不對、職責有沒有劃清楚

詳見 [層級擴展](層級擴展.md)
