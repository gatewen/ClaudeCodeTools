## 什麼時候要走完整閉環

**要走的情況：**
- 新寫一個函式、類別或模組
- 改動範圍影響到 3 個以上的函式
- 碰到安全相關的程式碼（登入、加密、權限）
- 用戶明確說「完整閉環」

**不用走的情況：**
- 修 1-3 行的明顯 bug
- 改錯字、更新註解
- 調設定檔
- 純文件更新

**用戶隨時可以覆蓋：**
- 說「完整閉環」→ 不管多小都走全流程
- 說「快速修改」→ 不管多大都跳過閉環

## 領域自動偵測（Section 6）

Phase 1 前會根據專案語言、框架、imports 自動偵測領域，套用對應的預設規則。用戶可覆蓋。

| 領域 | EH-x | 安全審查 | 驗證層級預設 | 單檔上限 |
|------|------|---------|------------|---------|
| 遊戲開發 | 可選 | 可跳過 | 預設 `[framework-dependent]` | 400 行 |
| 後端 API | 必要 | 必要 | 預設 `[testable]`，無需標注 | 300 行 |
| 前端 SPA | 條件判定 | 條件判定 | 混合，須逐項標注 | 300 行 |
| CLI 工具 | 條件判定 | 條件判定 | 預設 `[testable]`，無需標注 | 300 行 |
| 系統程式 | 必要 | 必要 | 預設 `[testable]`，無需標注 | 300 行 |

未匹配時用後端 API 預設（最嚴格）。偵測信號和條件判定的具體規則見 CLAUDE.md Section 6。

## 各階段詳細說明

### Phase 1：架構師 📐

**用白話說**：先想清楚要做什麼、怎麼做，畫出藍圖���動手。

**做什麼**：
- **模組資產查詢**（Phase 1 前）：module-registry.md 存在時，先查詢有無可複用的���能層。有 → 設計時標注複用，只設計新增功能或 UI 層
- **架構體質拆解**（涉及現有模組時）：用第一性原理拆解現有架構——每個模組為什麼存在？理由還成立嗎？有沒有多餘的層級？能支撐這次改動嗎？地基不穩 → 告知用戶
- 把用戶的需求翻譯成技術設計（函式簽名、參數型別、回傳值）
- **聲明分層結構**：有使用者介面的模組 → 分為功能層（核心邏輯，不依賴 UI 框架）+ UI 層（呈現/互動）。純後端/工具/服務 → 標注「純功能」
- 想清楚邊界情況和錯誤處理（按領域預設決定 EH-x 的必要性）
- 若有 update/tick/frame 迴圈 → 必須定義步驟執行順序
- 每個 BC-x/EH-x 標注驗證層級（按領域預設，只標例外）
- **（可選）PRD 需求分解**、**常見缺陷預防**（參考本文件末尾清單）

**不做什麼**：不寫程式碼，不做超出需求範圍的設計。

**必須交出來的東西**：設���規格（格式見 [產出物格式](../standards/產出物格式.md#設計規格)）

**閘門**：具體的逐項 checkbox 見 CLAUDE.md Phase 1 閘門。核心要求：參數有型別、BC-x ≥ 2、EH-x 符合領域預設、分層結構已聲明。全部通過 → 進 Phase 1b。

### Phase 1b：設計審查 🔬

**用白話說**：找另一個人來看你的藍���，看看有���有更好的做法、有沒有漏想的情況。

**跟 Phase 3 的差別**：Phase 3 是「程式碼寫完後檢查品質」，Phase 1b 是「動手前先確認藍圖本身夠不夠好」。

**獨立性**：用 Task 工具啟動一個全新的子 agent，不知道架構師怎麼想出這個設計的，只看到設計結果。

**可以跳過嗎？** 可以。用戶說「跳過設計審查」就直接進 Phase 2。

**做什麼**：
- **挑戰**：有沒有更好的方案？設計複雜度跟需求匹配嗎？
- **架構體質**：地基穩嗎？多餘的層級？能支撐未來擴展？
- **驗證**：邊界條件可測嗎？錯誤處理覆蓋外部失敗？資源配對？
- **分層**（功能+UI 模組）：功能層 API 夠抽象嗎？依賴方向正確？複用潛力？

**必須交出來的東西**：DR-x ��查報告，寫入 `.claude-loop/artifacts/P1b-design-review.md`

**閘門**：有 high → 回 Phase 1（全量重審，最多 3 輪）；有 arch-risk → 記錄不阻擋；medium/low → 用戶決定。全量重審的理由：設計規格相互耦合，修一處可能破壞另一處（壓測實證：修正 DR-4/5 引入了 DR-13）。

### Phase 2：程序設計師 💻

**用白話說**：按照藍圖施工，不要自作主張加東西。

**做什麼**：
- 嚴格按照 Phase 1 的設計規格寫程式碼
- 每個邊界條件和錯誤處理都要實作
- 遵守專案現有的命名和程式碼風格

**不做什麼**：不自己加設計裡沒有的功能，不改動設計規格。

**必須交出來的東西**：可以跑的程式碼

**強制優化**：實作完必須跑 `code-simplifier`（審查清晰度/一致性/可維護性，不改行為規格）。唯一可跳過：用戶明確說「保留原始碼」。

**通過條件**：無語法錯誤 + 設計項都有實作 + code-simplifier 已執行。每步上限、單檔上限、設計文件同步等執行細節見 CLAUDE.md Phase 2。

### Phase 3：檢核師 🔍

**用白話說**：找碴。看看程式碼有沒有問題、安不安全、跟設計對不對得上。

**獨立性**：品質審查用獨立子 agent。安全審查按領域預設和條件決定是否執行（具體跳過條件見 CLAUDE.md Phase 3）。

**做什麼**：
- 比對程式碼邏輯跟設計規格一致性
- 檢查程式碼品質、邊界處理、跨模組資料流
- **檢查依賴方向**（功能+UI 分層的模組）：功能層有沒有 import UI 框架？有 → R-x high
- 安全性檢查（若未跳過）
- 語言專屬審查（若有語言指南）

**必須交出來的東西**：檢核報告（格式見 [產出物格式](../standards/產出物格式.md#檢核報告)）

**斷點 A**：有 high → 回 Phase 2 修正 → 回退後用差分審查（只審修改檔案 + 依賴���案）。嚴重度定義和差分審查細節見 CLAUDE.md Phase 3。

### Phase 4：測試師 🧪

**用白話說**：用實際的測試來驗證程式碼做的事情跟設計說的一不一樣。

**做什麼**：
- 為每個 `[testable]` BC-x/EH-x 寫自動化測試
- `[visual-only]`/`[framework-dependent]` 項在報告中列出替代驗證方式
- 正常使用路徑至少一個測試
- 用專案的測試框架跑測試

**必須交出來的東西**：測試程式碼 + 測試報告（格式見 [產出物格式](../standards/產出物格式.md#測試報告)）

**斷點 B**：有測試失敗 → 回 Phase 2 修正 → 重跑 Phase 3 + 4

### Phase 5：自証師 ✅

**用白話說**：把前面所有人交出來的東西攤開來，看看有沒有��相打架的地方。

**跟前面的 Phase 有什麼不同**：Phase 1-4 都是同一個 agent 在做，Phase 5 的核心檢查（雙向追溯）改由**單一獨立子 agent** 執行。這個子 agent 不知道前面的推理過程，只看到產出物本身，用新鮮的眼光做正向和反向的交叉比對。

**怎麼分工**：
- **Part AB（雙向追溯）**：獨立子 agent，先枚舉所有行為路徑建立「分母」，再做正向（設計→程式碼→測試）和反向（程式碼→設計）追溯，最後交叉比對
- **Part C（整體評估）**：主 agent 收集結果，跑全專案驗證，做跨 Phase 一致性檢查，做最終判定

**做什麼**（七個維度逐一檢查）：

| 維度 | 在比對什麼 | 怎樣算通過 |
|------|-----------|-----------|
| PRD-���計覆蓋（若有 PRD） | PRD 裡的���個需求項，設計規格都有對應嗎？ | 每個 PRD#n 有 ≥ 1 個 BC-x/EH-x |
| 設計審查閉合 | Phase 1b 的 DR-x high 都修了嗎？ | high 已修正、medium 有決策記錄 |
| arch-risk 追蹤 | arch-risk 項目是否已緩解或仍存在？ | 每項都有追蹤記錄 |
| 設計-實作一致性 | 設計規格裡的每個項目，程式碼裡都有做到嗎？ | 沒有遺漏 |
| 實作-測試覆蓋 | `[testable]` 設計項都有自動化測試嗎？ | `[testable]` 100% 覆蓋 + 其他項有驗證記錄 |
| 檢核-修正閉合 | 檢核報告裡的 high/medium 問題都處理了嗎？ | 沒有未處理的 high/medium |
| 產出物完整性 | 每個階段都有交出東西嗎？ | 產出物都在（安全審查跳過時除外） |

**必須交出來的東西**：自証結果（格式見 [產出物格式](../standards/產出物格式.md#自証結果)）

**不通過時的回退規則**：

| 發現的問題 | 回到哪裡 | 為什麼 |
|-----------|---------|--------|
| 設計審查 high 未修 | Phase 1 | DR-x 指出的架構缺陷未處理 |
| 設計跟程式碼對不上 | Phase 2（嚴重回 Phase 1） | 實作錯了或設計有問題 |
| 測試沒覆蓋到 | Phase 4 | 測試計畫漏了東西 |
| 檢核問題沒修 | Phase 2 | 已知問題沒處理 |
| 缺產出物 | 缺的那個 Phase | 某個階段沒做完 |

**Part C 跨 Phase 一致性檢查**：主 agent 比對 Phase 3 的 R-x 數量與 Phase 5 反向分析的未覆蓋路徑數量。若 R-x ≥ 3 但未覆蓋路徑 = 0，判定是品質問題（合理）還是反向分析不夠深入（需重做）。這用一個 Phase 的數據驗證另一個 Phase 的品質，成本幾乎為零。

驗證包內容等執行細節見 CLAUDE.md Phase 5。

## 全域規則

**子 agent 失敗處理**：子 agent 可能超時或輸出不完整，閉環有「重試→降級自審→標記品質降級」的三段式容錯，確保流程不卡住又保留可追溯性。具體規則見 CLAUDE.md Section 7。

**斷點熔斷**：同一 Phase 的斷點反覆觸發時，熔斷機制像電路斷路器一樣跳閘，暫停流程交由用戶決定下一步。具體規則見 CLAUDE.md Section 8。

## 精簡閉環（中型任務）

中型任務觸發六步流程：設計（含模組資產查詢+學習日誌查詢+分層聲明）→設計快審→實作→品質審查→測試驗證→迷你追溯→模組登記（用戶要求時）→學習日誌追加。

**跟完整閉環的差別**：
- 設計快審只跑 1 輪（不回退重審）
- 品質審查同完整閉環，但不含安全審查
- 不跑完整 Phase 5 自証，改用**迷你追溯**（正向覆蓋 + 品質審查閉合，不含反向分析和 arch-risk 追蹤）
- 迷你追溯由主 agent 執行（不委派子 agent），成本 ~1-2K tokens
- 斷點 A 回退用差分審查
- 模組登記為用戶要求時執行（完整閉環為自動登記）

**迷你追溯做什麼**：
測試通過後、commit 前，主 agent 逐項列表確認每個 BC-x/EH-x 有實作（附檔案:行號）和測試（附測試名稱），並追蹤 R-x medium 的用戶決策。正向覆蓋有 ❌ → 禁止 commit；R-x medium → 必須經用戶決策。格式見 [產出物格式](../standards/產出物格式.md#迷你追溯)。

**什麼時候用精簡閉環**：
- 新增單一函式/元件 · 1-3 檔案 · < 300 行（內聚性豁免可放寬行數）
- 用戶沒有說「完整閉環」

## 配額管理策略

多階段連續開發時，子 agent 配額可能耗盡。降級優先順序（先降低價值的）：P5 雙向追溯 → P3 安全審查 → P1b → ⛔ P3 品質審查**不可降級**。具體分配策略見 CLAUDE.md。

## 回顧式學習

學習日誌只記**導致回頭重做的事件**——斷點觸發、DR-x high 回退、熔斷、任務升級。日常的 R-x medium 修正和 code-simplifier 建議不記（系統正常運作，不是教訓）。

**捕獲時機**：失敗事件（斷點/熔斷）發生時**立即追加**到 `.claude-loop/learning-log.md`（不等到閉環結束，避免 session 中斷導致教訓丟失）。閉環通過時在 **commit 前**追加完整條目（跟程式碼一起 commit）。PostToolUse Hook 在 git commit 後檢查 learning-log 是否在 commit 中，未包含則提醒。

**查詢時機**：Phase 1 前讀取日誌，找出與當前需求相關的歷史失敗根因。

累積 ≥ 5 筆記錄後可執行模式分析——識別高頻問題根因、預防清單效能、專案特有模式。格式見 [產出物格式](../standards/產出物格式.md#學習日誌)。

## 多函式的情況

如果一個需求要寫好幾個函式：

1. **每個函式各跑一次閉環**（方法層級）
2. 全部函式的閉環都通過後，再跑一次**模組層級的閉環**
3. 模組層級多驗證的東西：函式之間的協作對不對、職責有沒有劃清楚
4. **單模組 vs 多模組判定**：子系統共享核心狀態物件且 API 邊界不清晰 → 視為單模組；子系統有獨立狀態且透過明確介面溝通 → 視為多模組

詳見 [層級擴展](層級擴展.md)

## 模組化與功能/UI 分層

### 為什麼要分層

功能邏輯跨需求大同小異（認證、權限、CRUD、資料處理），但 UI 每個���景都可能不同。如果功能和 UI 混在一起，每次 UI 變動都牽動功能邏輯，複用性為零。

分層的核心約束：**功能層不依賴 UI 框架**。這樣功能層可以帶走複用，UI 層隨時替換。

### 模組登記

閉環通過的模組登記到 `.claude-loop/module-registry.md`，記錄名稱、分層結構、功能層 API、依賴��係。新需求的 Phase 1 前先查 registry，有可複用的功能層就不重新設計。

這不是額外的文件工作——是閉環流程自然產出的索引，讓已做過的東西能被找到。

登記條件：中型以上閉環通過，或用戶明確要求。格式見 [產出物格式](../standards/產出物格式.md#模組登記)。

## 常見設計缺陷預防清單

Phase 1 設計時可參考。首次使用閉環或不熟悉的領域時建議逐項檢查。

| # | 常見缺陷 | 怎麼防 |
|---|---------|--------|
| 1 | update/tick 步驟順序未定義 | 有迴圈就定義虛擬碼等級的步驟順序，標明依賴和副作用 |
| 2 | 資源建立後未釋放 | 每個 open/create/subscribe 配對 close/destroy/unsubscribe |
| 3 | 不可達的狀態 variant | 確認每個 enum variant 都有進入路徑，無用的刪除 |
| 4 | 碰撞/交互時機未定義 | 明確在哪一步偵測，偵測後的處理順序和優先級 |
| 5 | UI 與引擎狀態不同步 | 混合架構（Canvas+React、遊戲+UI）需定義同步回調機制 |
| 6 | 跨模組拆分語意遺漏 | 拆分邊界的資料過濾/轉換不得改變下游模組的預期 |
| 7 | 初始狀態不合法 | 預設值/起始位置/初始參數是否符合所有不變量（invariant） |
| 8 | 設計精度不足 | 粒度應到「可直接翻譯為程式碼」，非「方向指引」 |

## 因果鏈分析守衛

每次 AI 要修改檔案時，PreToolUse Hook 執行兩道阻擋式閘門，任一未通過即阻擋修改。

### 為什麼需要這個

改 A 壞 B 是最常見的 bug 來源。Hook 掃描只能找到「表面引用」，但真正的因果鏈往往更深——語意變了、時序改了、驗證規則放寬。這些不會觸發編譯錯誤，但會造成運行時 bug。

### 分析深度要求

1. **追溯根因**：從需求或 bug 追到「為什麼要改這個檔案」
2. **穿透呼叫鏈**：改 C 不能只看 B，要看 A 是否也受影響
3. **語意影響**：介面沒變但行為變了，必須標出
4. **狀態與時序**：初始化順序、事件���發時機的改變
5. **邊界條件**：驗證規則改變後，上游極端值是否還能正確處理
6. **呼叫者存在性**：修改函式前 grep 確認呼叫者，呼叫者 = 0 → 停下來找真正的執行路徑（executor/orchestrator 層可能有 inline 實作繞過模組）

### 輸出格式

AI 被阻擋後必須在畫面輸出以下格式，讓用戶看到分析過程：

```
⚠️ [因果鏈分析] 修改 {檔案名}:{函式名}
├─ 根因：{為什麼要改}
├─ 呼叫者（grep 結果 N 個，逐一分析）：
│   ├─ {檔案:行號} — {呼叫端函式名}
│   │   影響：{這個呼叫者會受什麼影響}
│   │   需連動：{是/否} — {理由}
│   └─ （每個 grep 結果都展開，不可省略）
│   呼叫者 = 0 → ⛔ 停
├─ 隱性風險：{快取失效/時序變化/語意漂移}
└─ 決策：{連動更新清單，或逐條說明為什麼不需要}
```

場景分流規則（閉環中/斷點回退/非閉環的輸出差異）見 CLAUDE.md Section 9。

## 合理性審查

每次改動都要退一步想：「這個改動放到整個系統裡，整體還合理嗎？」

### 為什麼需要這個

AI 做事的常見模式是：用戶說什麼就做什麼，只確保功能正確，但不會質疑「這樣做合不合理」。每個改動單獨看都沒問題，但累積起來可能造成操作流程不順、過度複雜、風格不一致。

### 檢查什麼

| 維度 | 問什麼 |
|------|--------|
| 一致性 | 跟系統現有的風格、模式、慣例一致嗎？ |
| 體驗 | 使用者的操作流程有沒有因此變複雜？ |
| 比例 | 解法的複雜度跟問題的規模成正比嗎？ |
| 可操作性 | 日常使用會不會造成不便或效率下降？ |
| 整合性 | 跟其他已有功能放在一���，整體還合理嗎？ |

重點是**有意識地想過**，不是加 checkbox。發現不合理就主動告知用戶。在流程中的執行規則見 CLAUDE.md Section 10。
