## 一、Executive Summary

`dev-closed-loop/` 是一套自建的**軟體開發品質保證方法論**——「開發設計閉環」（v3.4）。核心理念是：每段非微小的程式碼變更都必須經過五個角色的驗證（架構師 → 程序設計師 → 檢核師 → 測試師 → 自証師），最後由**自証師**確認所有產出物之間沒有矛盾，才算完成。

**獨特價值**：傳統 Code Review 檢查程式碼品質、測試驗證行為、安全掃描找漏洞——但很少有人系統性驗證「這些產出物之間是否一致」。自証師就是填補這個缺口的角色，執行的是 **Meta-validation**（跨產出物一致性驗證）。

## 三、核心方法論：五階段閉環

### 3.1 流程概覽

```
Phase 1：架構師 📐 → 產出：設計規格（BC-x, EH-x 編號）
    ↓
Phase 2：程序設計師 💻 → 產出：可執行的程式碼
    ↓ 強制調用 code-simplifier 優化
Phase 3：檢核師 🔍 → 產出：檢核報告（R-x 編號）
    ↓ ⚠️ 斷點 A：有 high 問題 → 回 Phase 2
Phase 4：測試師 🧪 → 產出：測試程式碼 + 測試報告
    ↓ ⚠️ 斷點 B：有測試失敗 → 回 Phase 2
Phase 5：自証師 ✅ → 產出：自証結果（通過/不通過）
    ↓ 自証失敗 → 回到缺口對應的 Phase
    ✅ 自証通過 → commit + 完成
```

### 3.2 各 Phase 詳解

| Phase | 角色 | 目標 | 首選工具 | 核心約束 | 必要產出 |
|-------|------|------|---------|---------|---------|
| 1 | 架構師 | 產出設計藍圖 | `sc:design` | 只設計不實作；BC-x/EH-x 編號；≥2 邊界條件 | 設計規格 |
| 2 | 程序設計師 | 按設計規格實作 | `sc:implement` | 嚴格對照設計；不自行增加功能；**強制 code-simplifier** | 程式碼 |
| 3 | 檢核師 | 找出設計-實作不符 | `sc:analyze` / Task agents | 必須對照設計規格比對；R-x 編號；安全檢核不可跳過 | 檢核報告 |
| 4 | 測試師 | 驗證程式碼正確性 | `sc:test` | 每個測試標注對應 BC-x/EH-x；必須實際執行測試 | 測試程式碼+報告 |
| 5 | 自証師 | 跨產出物一致性驗證 | 自証檢查表+Skills | 不是重新測試；逐步執行 6 步檢查表；用 ID 精確追溯 | 自証結果 |

### 3.3 ID 編號系統（追溯的基礎）

| 前綴 | 含義 | 定義於 | 引用於 |
|------|------|-------|-------|
| BC-x | 邊界條件 (Boundary Condition) | Phase 1 | Phase 2, 4, 5 |
| EH-x | 錯誤處理 (Error Handling) | Phase 1 | Phase 2, 4, 5 |
| R-x | 檢核問題 (Review Finding) | Phase 3 | Phase 5 |

### 3.4 斷點與回退機制

| 斷點 | 觸發條件 | 回退目標 |
|------|---------|---------|
| 斷點 A | Phase 3 發現 high 嚴重度問題 | → Phase 2 修正 → 重跑 Phase 3 |
| 斷點 B | Phase 4 有測試失敗 | → Phase 2 修正 → 重跑 Phase 3 + 4 |
| 自証失敗 | Phase 5 發現缺口 | → 缺口對應的 Phase |

### 3.5 Phase 5 自証檢查表（6 步，核心特色）

1. **建立基準清單**：從 Phase 1 列出所有 BC-x、EH-x ID
2. **設計-實作一致性**：逐一確認 Phase 2 是否有對應實作（✅/❌）
3. **實作-測試覆蓋**：逐一確認 Phase 4 是否有對應測試（✅/❌）
4. **檢核-修正閉合**：確認所有 high/medium R-x 已修正（✅/❌）
5. **產出物完整性**：確認四份產出物都存在
6. **產出自証結果**：四維度全 ✅ → 通過；任何 ❌ → 不通過 + 回退建議

### 3.6 觸發與跳過條件

**必須走閉環**：新增函式/類別/模組、重構 ≥3 函式、安全相關、用戶說「完整閉環」
**可跳過**：1-3 行 bug 修正、註解/設定微調、純文件更新、用戶說「快速修改」

## 四、CLAUDE_TEMPLATE.md — 核心產物分析

### 4.1 設計哲學：自包含

> 本檔案包含 Claude 執行閉環所需的所有資訊。不需要讀取其他檔案就能跑完整流程。

- 所有 Phase 的調用方式、約束、產出物格式都嵌入此檔案
- `.claudedocs/` 是給人類閱讀的補充文檔
- 部署後 Claude Code 自動讀取並遵循

### 4.2 Placeholder 變數

| 變數 | 用途 | 填充時機 |
|------|------|---------|
| `{{PROJECT_NAME}}` | 專案名稱 | `/dev:init-claude` 執行時 |
| `{{LANGUAGE}}` | 程式語言 | 自動偵測或用戶指定 |
| `{{FRAMEWORK}}` | 框架 | 自動偵測或用戶指定 |
| `{{TEST_COMMAND}}` | 測試指令 | 自動偵測或用戶指定 |
| `{{BUILD_COMMAND}}` | 建置指令 | 自動偵測或用戶指定 |

### 4.3 進度可見性規則

閉環執行時強制輸出：
1. **TaskCreate**：建立 5 個任務卡追蹤進度
2. **Phase 進出標記**：用分隔線格式輸出每個 Phase 的開始/完成/斷點
3. **Agent 調用宣告**：每次調用 Agent 時輸出 `→ 調用 ...`，完成時輸出 `← ... 完成`

### 4.4 Agent 調用優先順序

1. **sc: Skill**（優先）— 在當前對話中執行，能看到完整上下文
2. **superpowers: Skill**（次選）— 更專門化的流程
3. **Task agent**（用於子任務）— 獨立子程序，需手動傳遞上下文

### 4.5 強制程式碼優化（Phase 2 → 3 之間）

**code-simplifier** Task agent 是強制步驟，不可跳過：
- **三個面向審查**：Clarity（清晰度）、Consistency（一致性）、Maintainability（可維護性）
- **禁止照搬舊碼**：即使邏輯相同也必須審視
- **不能改設計**：只簡化實作方式，不改行為規格
- **唯一例外**：用戶明確說「保留原始碼」或「不要優化」

## 五、Skill 與部署機制

### 5.1 雙層架構

```
安裝層（setup.sh 一次執行）：
  skill/init-claude.md (含 {{REPO_PATH}})
  → sed 替換 → ~/.claude/commands/dev/init-claude.md (路徑已填入)

使用層（/dev:init-claude 在每個專案執行）：
  讀取已部署的 Skill → 定位模板 → 偵測+確認+填充 → 專案/CLAUDE.md
```

### 5.2 init-claude.md 執行流程

1. **Step 0：環境依賴檢查** — 確認 SuperClaude 和 Superpowers 已安裝
2. **Step 1：前置檢查** — 工作目錄、模板路徑、CLAUDE.md 衝突處理（合併/覆蓋/取消）
3. **Step 2：專案偵測** — 兩階段掃描（根目錄 + 一層子目錄），偵測語言/框架/測試指令/建置指令
4. **Step 2.5：偵測結果驗證** — 全部未偵測到時強制攔截（手動輸入/切換目錄/繼續生成）
5. **Step 3：互動確認** — 呈現偵測結果讓用戶確認或修正
6. **Step 4：模板填充** — 替換 5 個 placeholder + 複製 .claudedocs/
7. **Step 5：驗證** — placeholder 殘留檢查 + .claudedocs 完整性（8/8）+ 最終報告

## 六、.claudedocs 補充文檔分析

### 6.1 閉環核心理念

- 方法論的哲學基礎：跨產出物一致性驗證
- 自証 ≠ 測試：測試驗證程式碼行為，自証驗證產出物之間的一致性
- 分形結構：同一套流程在不同粒度重複套用

### 6.2 五階段閉環流程

- 每個 Phase 的詳細步驟說明（比 CLAUDE_TEMPLATE 更白話文）
- 注意：CLAUDE.md 為 Claude 的執行權威，此文件為人類閱讀補充

### 6.3 層級擴展

三個擴展層級（超越基礎的方法閉環）：

| 層級 | 範圍 | 額外 ID | 額外驗證維度 |
|------|------|--------|------------|
| **模組** | 一組相關函式 | MC-x（模組協作）、EP-x（錯誤傳播） | 協作正確性、錯誤傳播完整性 |
| **框架** | 整體系統 | MD-x（模組依賴） | 跨模組一致性、依賴合理性 |

**產出物彙整規則**：底層帶上「設計規格 + 自証結果」給上層；不帶檢核報告和測試報告（已在底層驗證過）。

### 6.4 Agent 使用指南

- 三類 Agent 差異：sc: Skill（完整上下文）> superpowers: Skill > Task agent（獨立子程序）
- 各 Phase 的選擇邏輯和常見錯誤
- code-simplifier 使用 Task agent 的原因：避免「自己審自己」的偏見
- SkillsMP 外部 Skills 資源（含安全警告：26% 含漏洞）

### 6.5 Git 工作流

- 每完成一個閉環 commit 一次
- commit message 帶自証結果摘要
- 斷點觸發時先 commit 當前狀態（標 `[斷點X]`）
- 不要 `git add .`、不要 force push 到共用分支

### 6.6 產出物格式

- 與 CLAUDE_TEMPLATE 中的格式定義相同（CLAUDE.md 為權威）
- 強調統一格式是自証能做交叉比對的基礎

### 6.7 問題追蹤

- 開發中問題的記錄模板：時間、階段、嚴重度、問題描述、根本原因、解決方式、教訓
- 含兩個範例（測試框架版本不相容、自証發現設計規格遺漏）

## 七、設計歷史與演進分析

### 7.1 演進路線

```
01_原始構想 — 理論框架
  • 4 層級 × 9 角色 = 分形化閉環
  • 自我觀察：角色太多、自証不清、缺少回退機制
      ↓
02_深度分析 — 問題診斷
  • 核心洞察：自証 = Meta-validation（跨產出物一致性驗證）
  • 回退成本過高 → 建議加入 mini 自証斷點
  • 產出物無法自動化比對 → 需要統一 Schema
  • 與 V-Model / Code Review Pipeline 比較
      ↓
03_落地路線圖 — 工程化
  • 9 角色 → 5 角色 MVP（精簡）
  • 5 Phase 實施計畫：自証標準 → 精簡閉環 → Schema → 擴展 → AI Agent
  • 產出物 Schema 設計（YAML 格式）
      ↓
04_Skill設計規劃 — 工具化
  • /dev:init-claude 設計藍圖
  • 自動偵測 + 互動確認 + 模板填充
  • 未來擴展：--minimal / --full / --security / --perf
```

### 7.2 核心轉折點

1. **從完整到精簡**：9 角色 → 5 角色（務實決策）
2. **自証概念清晰化**：從模糊的「綜合驗證」→ 具體的 6 步檢查表 + ID 追溯
3. **手動到自動化**：從人工部署 → setup.sh + /dev:init-claude 一鍵部署

## 九、關鍵設計亮點

1. **自包含模板**：CLAUDE_TEMPLATE.md 包含 Claude 執行閉環的所有資訊，無需讀取其他檔案
2. **ID 追溯系統**：BC-x / EH-x / R-x 編號貫穿 Phase 1-5，實現精確的交叉比對
3. **斷點機制**：Phase 3 和 Phase 4 各有一個質量關卡，問題在中途被攔截
4. **強制 code-simplifier**：Phase 2 → 3 之間的必經步驟，防止 AI 照搬舊碼
5. **進度可見性**：TaskCreate + Phase 標記 + Agent 調用宣告，用戶全程知情
6. **分層擴展**：方法 → 模組 → 框架，同一套流程在不同粒度重複
7. **雙層部署架構**：setup.sh（repo 級別）+ /dev:init-claude（專案級別）
8. **完整性驗證**：.claudedocs 8 檔案 + placeholder 殘留檢查

## 十、研究結論

`dev-closed-loop/` 是一套**成熟且精心設計的軟體開發品質方法論**，從理論構想到工具化部署經歷了完整的演進。其核心創新——**自証師的 Meta-validation**——填補了傳統軟體工程中「跨產出物一致性驗證」的空白。

方法論的設計注重實用性（5 角色精簡版本、觸發/跳過條件、斷點回退），同時保留了擴展性（層級擴展、外部 Skills）。雙層部署架構使得安裝和使用流程清晰分離。

**當前狀態**：v3.4，核心產物和工具化均已完成，屬於可使用的成熟狀態。
