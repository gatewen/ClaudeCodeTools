# 實戰驗證流程（Methodology Retrospective）

> **v7.0.0 定位**：retrospective 機制在 v7 仍有效，目的不變（把規則升級從直覺驅動轉為證據驅動）。下方模板的 Phase 標籤、「精簡 / 完整閉環」、「code-simplifier 強制」等為 v6.x 用語——v7 對映：閉環模式 → 任務等級（中型輕量 / 大型 workflow）、Phase 1b/3/5 → `/dev-design` / `/dev-review` / `/dev-verify`、code-simplifier 已非強制。**做 retrospective 時，「主觀規則疲勞」清單應對照當前版本的實際規則填**（v7 含：因果鏈 hook、事實求證、push back、workflow 是否該開、升格檢查等）。

## 用途

跑完 N 個真實任務後做一次**方法論本身**的 retrospective，產生「v5.x.y 在實戰中先壞在哪裡」的證據。

目的**不是**評斷個案，是用來判斷下一版方法論是否需要規則升級、升級在哪、不升級在哪。

## 為什麼存在

方法論演進若不靠實戰證據，容易掉入「想到就加」的迴圈：發現議題 → 寫方案 → 做下一版 → 沒驗證。retrospective 是把「規則升級」從**直覺驅動**轉為**證據驅動**的最低成本機制。

對應 [產出物格式 — failure_type 4 類](../standards/產出物格式.md#事件條目格式斷點熔斷觸發時立即追加)：

| 我們收集的證據 | 用來決定 |
|---|---|
| failure_type 4 類分布 | 下一版該補哪一類缺口 |
| 主觀規則疲勞 | 哪些規則該簡化或移除 |
| Phase 卡關熱點 | 哪個 Phase 設計需要重新思考 |
| 規格 vs gap 對照 | 哪些「想像中的缺口」其實不存在 |

## 何時跑

任一條件成立時觸發：

- 累積 ≥ 3 個閉環任務後
- ≥ 1 個有回退/熔斷的任務後
- 方法論版本改動超過 30 天但未驗證過

## 樣本選擇要求

至少包含：

- **1 個中型任務**（精簡閉環）
- **1 個大型任務**（完整閉環）
- **1 個有回退或熔斷的任務**（無此案例可從 learning-log 找近期斷點觸發紀錄補上）

不足 3 個樣本時不建議跑——訊號太薄會誘導錯判。

## Retrospective 模板

每次 retrospective 產出一份檔案，建議路徑 `.claude-loop/retrospectives/YYYY-MM-DD-vX.Y.Z.md`（不存在則建目錄）。

```markdown
# Retrospective YYYY-MM-DD（基於 v{X.Y.Z}）

## 樣本任務清單

| # | 任務名 | 任務等級 | 閉環模式 | commit hash | 是否有回退 |
|---|--------|---------|---------|-------------|-----------|
| 1 | ... | 中型 | 精簡閉環 | abc1234 | 否 |
| 2 | ... | 大型 | 完整閉環 | def5678 | Phase 3→2 一次 |
| 3 | ... | ... | ... | ... | ... |

## 4 類失敗統計

從 learning-log 條目的 failure_type 欄位 + 主觀觀察補充。

| failure_type | 次數 | 涉及樣本 # | 高頻根因 |
|------|------|-----------|---------|
| process_failure | N | [1, 3] | {ex: 閘門被跳 / 學習查詢沒做} |
| judgment_failure | N | [2] | {ex: 根因錯判} |
| verification_failure | N | [] | {ex: reviewer 漏檢} |
| tooling_failure | N | [3] | {ex: hook 誤判} |

**訊號解讀**：
- process_failure 高 → 規則執行可靠性差 → **應簡化規則而非加規則**
- judgment_failure 高 → Phase 1 設計品質不夠 → 改善 architect prompt 或加學習查詢深度
- verification_failure 高 → Phase 3/5 reviewer 強度不足 → 加 reviewer 檢查項
- tooling_failure 高 → hook/skill 需修 bug → 工程修補而非規則升級

## 主觀規則疲勞調查（最重要的 section）

對照 v{X.Y.Z} 規則清單，逐項標記**你自己的主觀感受**。這比 agent 是否真跳更重要——你今天嫌麻煩沒跳，明天就會跳；你嫌麻煩 agent 看你的指示也會嫌麻煩。

| 規則 | 是否曾想跳過？ | 原因 | 跳過後實際出事？ |
|------|---------------|------|----------------|
| 因果鏈分析（修改前 · L1 hook） | Y / N | {ex: 微小修改也要做覺得瑣碎} | Y / N |
| 事實主張閘門 / push back | Y / N | ... | Y / N |
| 學習查詢（問題追蹤+learning-log） | Y / N | ... | Y / N |
| 該開 workflow 卻沒開（大型/PRD） | Y / N | ... | Y / N |
| 設計審查（`/dev-design` adversarial-verify） | Y / N | ... | Y / N |
| 品質+安全審查（`/dev-review`） | Y / N | ... | Y / N |
| 自證（`/dev-verify` / 迷你追溯） | Y / N | ... | Y / N |
| 升格檢查 AskUserQuestion | Y / N | ... | Y / N |
| failure_type 強制標 4 類 | Y / N | ... | Y / N |
| ...（補本版本所有可能想跳的規則）... | ... | ... | ... |

**判讀規則**：
- 「想跳但沒跳 + 沒出事」≥ 3 次 → 該規則疑似 over-spec，下一版考慮放寬
- 「想跳但沒跳 + 出事」 → 該規則確實有用，繼續保留
- 「跳了 + 出事」 → 規則重要但執行可靠性差，需加閘門或 hook 阻擋
- 「跳了 + 沒出事」≥ 3 次 → 規則可能無用，下一版考慮移除

| 缺口（疑似） | 真的缺 vs 想像的缺 | 證據 |
```

## 限制聲明

- 個人工具規模下，retrospective 不需要嚴謹的統計（樣本太小）；本模板的價值在**強迫你具體列證據**而非估計
- 主觀規則疲勞 section 比客觀統計更重要——LLM 沒有疲勞感，只有人類有
- 不要把 retrospective 升級成「方法論審計報告」——保持輕量，否則 retrospective 自己會變成被嫌麻煩的規則
