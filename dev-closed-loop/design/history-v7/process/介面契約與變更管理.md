# 介面契約與變更管理

跨模組專案中，模組之間的介面定義散落在各自的設計規格裡，模組 A 改了介面，模組 B 不知道。
本文件定義 IF-x（介面契約）和 CR-x（變更請求）兩套機制，形式化跨模組介面、追蹤介面變更的連鎖影響。

> **v7.0.0 定位**：IF-x（介面契約）/ CR-x（變更請求）在 v7 ID 系統中屬「**按需 inline，不強制獨立編號**」（主軸是 BC-x + R-x）——僅「跨模組公開 API 的多模組專案」需要時才用本文件的完整格式；單檔 / 中型任務併入 BC-x / R-x 敘述即可。本文件的 Phase 標籤（Phase 1/5、斷點 A/B）為 v6.x；v7 大型任務由 workflow 編排（設計 → `/dev-design`、審查 → `/dev-review`、自證 → `/dev-verify`），介面一致性檢查在 `/dev-verify` 或退化路徑追溯。

---

## IF-x 介面契約

### 什麼是 IF-x

IF-x 是跨模組公開 API 的**唯一真相來源**（single source of truth）。
提供模組和消費模組都引用同一個 IF-x，不各自描述介面。

存放路徑：`.claude-loop/interfaces/IF-{n}.md`

### 完整格式

```markdown
## 📋 介面契約 IF-[n]：[介面名稱]

- 提供模組：[模組名稱]
- 消費模組：[模組1, 模組2, ...]
- 版本：v[n]
- 最後更新：[YYYY-MM-DD HH:MM]
- 狀態：草案 / 生效 / 已廢棄

### 函式簽名

| 函式名 | 參數 | 回傳值 | 說明 |
|--------|------|--------|------|
| [verifyToken] | [token: string] | [User | null] | [驗證 token 回傳用戶] |

### 資料格式

[定義跨模組傳遞的資料型別，用程式碼區塊標示]

### 錯誤契約

| 錯誤類型 | 觸發條件 | 消費模組應如何處理 |
|---------|---------|-------------------|
| [InvalidTokenError] | [token 無效或過期] | [回傳 401] |

### 效能契約（選填）

| 指標 | 保證值 |
|------|--------|
| [回應時間] | [< 100ms p95] |
```

### 欄位說明

| 欄位 | 必填 | 說明 |
|------|------|------|
| 提供模組 | 是 | 實作並暴露此 API 的模組 |
| 消費模組 | 是 | 呼叫此 API 的模組清單 |
| 版本 | 是 | 從 v1 開始，每次變更遞增 |
| 狀態 | 是 | 草案（探索中）→ 生效（已確認）→ 已廢棄（不再使用） |
| 函式簽名 | 是 | 完整的參數型別和回傳值 |
| 資料格式 | 視情況 | 若跨模組傳遞複雜資料結構，必須定義 |
| 錯誤契約 | 是 | 消費模組需要知道如何處理錯誤 |
| 效能契約 | 否 | 有效能要求時才填 |

### 生命週期

1. **建立**：Phase 1 定義跨模組公開 API 時建立，初始狀態為「草案」或「生效」
2. **引用**：消費模組的 Phase 1 從 `interfaces/` 讀取 IF-x，設計規格引用而非自行描述
3. **變更**：模組修改了 IF-x 定義的介面 → 更新 IF-x 版本號 → 建立 CR-x
4. **廢棄**：介面不再被任何模組使用 → 狀態改為「已廢棄」

### 與 MD-x 的關係

層級擴展中定義的 MD-x（模組依賴）描述「誰依賴誰、透過什麼」——一行摘要。
IF-x 描述「那個介面的完整規格」——獨立檔案。兩者互補：

- MD-x 行引用 IF-x：`MD-1 | 模組 X | 模組 Y | IF-2 | ...`
- IF-x 是介面的唯一真相來源
- 模組的 design-spec 引用 IF-x 而非自行描述跨模組介面

### 與 MC-x 的區別

| | MC-x（模組協作） | IF-x（介面契約） |
|---|---|---|
| 範圍 | 模組內部函式間的協作 | 跨模組公開 API |
| 定義位置 | 模組的 design-spec 內 | 獨立檔案 `interfaces/IF-{n}.md` |
| 變更影響 | 僅影響模組內部 | 影響所有消費模組 |
| 需要 CR-x | 否 | 是 |

### 範例

auth 模組提供 `verifyToken` 和 `getUserPermissions`，order 模組消費：

```markdown
## 📋 介面契約 IF-1：Auth 驗證介面

- 提供模組：auth
- 消費模組：order, notification
- 版本：v1
- 最後更新：2026-02-14 10:00
- 狀態：生效

### 函式簽名

| 函式名 | 參數 | 回傳值 | 說明 |
|--------|------|--------|------|
| verifyToken | token: string | User | null | 驗證 JWT token，回傳用戶物件 |
| getUserPermissions | userId: string | Permission[] | 取得用戶權限清單 |

### 資料格式

\`\`\`typescript
interface User {
  id: string;
  email: string;
  role: 'admin' | 'user';
}

interface Permission {
  resource: string;
  action: 'read' | 'write' | 'delete';
}
\`\`\`

### 錯誤契約

| 錯誤類型 | 觸發條件 | 消費模組應如何處理 |
|---------|---------|-------------------|
| InvalidTokenError | token 無效或過期 | 回傳 401 Unauthorized |
| UserNotFoundError | token 有效但用戶不存在 | 回傳 403 Forbidden |
```

## CR-x 變更請求

### 什麼是 CR-x

當模組修改了 IF-x 定義的介面時，必須建立 CR-x 記錄變更內容和影響範圍。
CR-x 確保所有受影響的模組都知道介面變了、都處理了影響。

存放路徑：`.claude-loop/changes/CR-{n}.md`

### 完整格式

```markdown
## 🔄 變更請求 CR-[n]：[變更摘要]

- 觸發模組：[模組名稱]
- 觸發原因：斷點修正 / 設計變更 / 需求變更
- 影響的介面契約：IF-[x]
- 影響的模組：[模組1, 模組2, ...]
- 建立時間：[YYYY-MM-DD HH:MM]
- 狀態：待處理 / 處理中 / 已完成

### 變更內容

| 項目 | 變更前 | 變更後 |
|------|--------|--------|
| [函式簽名 / 資料格式 / 錯誤契約] | [原定義] | [新定義] |

### 影響分析

| 受影響模組 | 當前狀態 | 需要的動作 |
|-----------|---------|-----------|
| [order] | [Phase 5 通過] | [需重新驗證 Phase 5] |

### 處理記錄

| 時間 | 模組 | 動作 | 結果 |
|------|------|------|------|
| [YYYY-MM-DD HH:MM] | [order] | [重跑 Phase 5] | [通過 — 新介面向下兼容] |
```

### 觸發條件

以下情境必須建立 CR-x：

1. **斷點修正中改變了介面**：模組在 Phase 2 回退修正時，改動了 IF-x 定義的函式簽名、資料格式或錯誤契約
2. **設計變更**：模組 Phase 1 重新設計時改變了公開 API
3. **需求變更**：外部需求變化導致介面需要調整

### 處理流程

1. 觸發模組建立 CR-x，填寫變更內容和影響分析
2. 同步更新 IF-x 的版本號和內容
3. 同步更新 `project-state.md` 和受影響模組的 `status.md`
4. 每個受影響模組讀取 CR-x，評估是否向下兼容：
   - **向下兼容**：不需要改程式碼，但需重跑 Phase 5 確認
   - **不兼容**：需重跑受影響的 Phase（通常從 Phase 1 或 Phase 2 開始）
5. 在 CR-x 的處理記錄中填寫每個模組的處理結果
6. 所有模組處理完畢 → CR-x 狀態標記「已完成」

### 與 project-state.md / status.md 的連動

- 建立 CR-x 時 → 在 `project-state.md` 的進度表標注受影響模組需要處理 CR
- 受影響模組的 `status.md` → 追加歷史記錄「收到 CR-x，需重新驗證」
- CR-x 處理完畢 → 更新所有相關的 `status.md` 和 `project-state.md`

### 範例

user 模組改了 `User.id` 的型別從 `number` 改為 `string`，auth 模組需要重新驗證：

```markdown
## 🔄 變更請求 CR-1：User.id 型別從 number 改為 string

- 觸發模組：user
- 觸發原因：設計變更（配合 UUID 遷移）
- 影響的介面契約：IF-1
- 影響的模組：auth, order
- 建立時間：2026-02-14 14:00
- 狀態：已完成

### 變更內容

| 項目 | 變更前 | 變更後 |
|------|--------|--------|
| User.id 型別 | number | string (UUID) |

### 影響分析

| 受影響模組 | 當前狀態 | 需要的動作 |
|-----------|---------|-----------|
| auth | Phase 5 通過 | 需重新驗證 Phase 2 和 Phase 5 |
| order | Phase 3 進行中 | 需重新驗證 Phase 1 和 Phase 2 |

### 處理記錄

| 時間 | 模組 | 動作 | 結果 |
|------|------|------|------|
| 2026-02-14 15:00 | auth | 重跑 Phase 2, 5 | 通過 — 已更新所有 id 相關邏輯 |
| 2026-02-14 16:00 | order | 重跑 Phase 1, 2, 3 | 通過 — 訂單模型已改用 string id |
```

## 與現有閉環的整合

### Phase 1 如何引用 IF-x

- 若模組依賴其他模組的公開 API → 從 `.claude-loop/interfaces/` 讀取相關 IF-x，設計規格引用而非自行描述
- 若模組定義新的跨模組公開 API → 同時產出 IF-x 介面契約，寫入 `.claude-loop/interfaces/IF-{n}.md`

### Phase 5 如何驗證 IF-x 一致性

- 自證步驟 1（基準清單）：除了 BC-x 和 EH-x，加入 IF-x（若有）
- 自證步驟 2（設計-實作一致性）：IF-x 需額外確認實作的函式簽名和資料格式是否與介面契約一致
- 自證結果：新增選用維度「介面契約一致性」（僅在模組有 IF-x 時出現）

### 斷點修正如何觸發 CR-x

1. Phase 3 斷點 A 或 Phase 4 斷點 B 觸發回退
2. Phase 2 修正過程中，若改動了 IF-x 定義的介面 → 建立 CR-x
3. CR-x 填寫變更內容和影響分析
4. 受影響模組在下次進入閉環時讀取並處理 CR-x

## 適用範圍

### 需要 IF-x 的情境

- 模組暴露公開 API 且被其他模組依賴（跨模組依賴 ≥ 1）
- 框架層級的多模組專案

### 不需要 IF-x 的情境

- 方法層級閉環（單一函式/類別）
- 模組內部函式間的協作（用 MC-x）
- 模組沒有被其他模組依賴的公開 API

原則：**避免過度形式化**。不是每個函式都需要 IF-x，只有跨模組公開 API 才需要。

## 自動化方向（原 v3 預告 · v7 由 workflow 承接）

早期 v3 規劃的「專案協調者」自動化方向，在 v7.0.0 部分由 workflow 編排承接（多 agent 分析 + 對抗驗證），其餘仍為未實作的方向參考：

- **自動建立 IF-x**：分析模組依賴圖，為每個跨模組依賴建議 IF-x
- **自動偵測介面變更**：比對程式碼和 IF-x 定義，偵測不一致（可由 `/dev-review` 派 lens 承擔）
- **自動傳播 CR-x**：建立 CR-x 後自動通知受影響模組，追蹤處理進度
- **Session 0 協議**：正式的專案初始化流程，包含模組劃分、依賴定義、IF-x 建立
