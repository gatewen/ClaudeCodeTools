# 深度分析：開發設計閉環

## 整體評估

這套閉環系統的核心價值在於提出了**跨產出物一致性驗證**（Cross-artifact Consistency Validation）的概念。傳統軟體工程中，Code Review 檢查程式碼、測試驗證行為、安全掃描找漏洞——但很少有人系統性地驗證「這些產出物之間是否一致」。

自証師正是填補這個缺口的角色。

---

## 核心洞察

### 1. 自証 ≠ 測試，自証是 meta-validation

| 面向 | 測試師 | 自証師 |
|------|--------|--------|
| 驗證對象 | 程式碼的行為正確性 | 所有產出物的一致性 |
| 輸入 | 程式碼 + 測試案例 | 9 份產出物（設計、程式碼、報告...） |
| 判斷標準 | 測試通過/失敗 | 產出物之間是否矛盾、遺漏、不一致 |
| 舉例 | 函式回傳值是否正確 | 安全報告說要驗證輸入，但測試計畫沒涵蓋 |

自証師的核心問題是：**設計文件說的 → 程式碼做的 → 測試驗的 → 安全查的，這四條線是否對齊？**

### 2. 閉環的分形結構是強項

同一套角色流程在不同粒度層級重複套用，這個設計有兩個好處：
- **認知一致性**：學一次流程，適用所有層級
- **可組合性**：方法層級的閉環完成後，自然成為模組層級的輸入

但也有一個隱含假設需要驗證：**低層級的閉環品質是否能保證高層級的閉環品質？** 整合問題往往出現在組合的時候，而非個別元件。

### 3. 這套系統天然適合 AI Agent 實作

9 個角色本質上就是 9 個不同 prompt 的 AI Agent。每個角色有明確的：
- **輸入**：前一個角色的產出
- **職責**：單一且明確
- **產出**：結構化文件

這是 AI Agent Workflow（如 CrewAI、AutoGen）的經典模式。

## 問題識別

### 問題 A：回退成本過高

```
目前：1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 9（自証）
                                              ↓
                                         不通過 → 回到某步
```

如果自証師在第 9 步發現「設計」有問題，前面 7 步的工作可能全部白費。

**建議**：加入早期斷點（mini 自証）

```
1 → 2 → 3 → [斷點A：設計-實作一致性檢查]
→ 4 → 5 → 6 → 7 → [斷點B：安全-測試覆蓋檢查]
→ 8 → 9（最終自証）
```

這樣問題能在中途被攔截，降低回退成本。

### 問題 B：層級串接機制未定義

文件定義了四個層級，但沒有說明：
- 方法層級閉環 **全部完成後**，誰觸發模組層級閉環？
- 模組層級的架構師，是否需要**重新審視**方法層級的設計？
- 跨層級的產出物如何**繼承與轉換**？

這是讓系統從「概念」變成「可運作流程」的關鍵缺口。

### 問題 C：產出物缺少標準格式

9 個角色產出 9 種不同文件。自証師要做跨產出物比對，需要：
- **統一的 schema**：每份產出物有固定的結構
- **可追溯的引用**：產出物之間能互相引用（例如：測試案例引用設計文件的需求 ID）
- **機器可讀的格式**：讓 AI 自証師能自動化比對

### 問題 D：缺少「需求」作為閉環起點

架構師根據什麼來設計？目前閉環從「設計」開始，但設計的依據（需求）不在閉環內。

這意味著即使所有產出物一致，也可能**一致地做了錯的事情**。

需要在架構師之前加入：
- **需求分析師**：將模糊需求轉化為明確規格
- 或至少有一份**需求文件**作為閉環的輸入基準

## 與 AI Agent 系統的對應

### 角色 → Persona 映射

| 閉環角色 | SuperClaude Persona | 核心工具 |
|---------|---------------------|---------|
| 需求分析師（建議新增） | `--persona-analyzer` | Sequential MCP |
| 架構師 | `--persona-architect` | Sequential MCP + Context7 |
| 程序設計師 | `--persona-backend` / `--persona-frontend` | Edit / Write / Magic MCP |
| 程序檢核師 | `--persona-refactorer` | Grep + Read |
| 安全檢核師 | `--persona-security` | Grep + Sequential MCP |
| 測項規劃師 | `--persona-qa`（規劃模式） | Sequential MCP |
| 單元測試設計師 | `--persona-qa`（實作模式） | Write + Context7 |
| 測試師 | `--persona-qa`（執行模式） | Bash + Playwright MCP |
| 效能評估師 | `--persona-performance` | Bash + Playwright MCP |
| 自証師 | 新角色，跨 persona 整合 | Sequential MCP（主要） |

### 自証師的特殊性

自証師無法簡單對應到現有的任何 persona，因為它的工作是**跨角色比對**。
它需要：
- 讀取所有前面角色的產出物
- 用結構化推理（Sequential MCP）比對一致性
- 產出明確的通過/不通過判定，附帶不一致的具體位置

這可能需要設計一個**專用的自証 prompt 模板**。

## 與既有框架的比較

| 面向 | V-Model | Code Review Pipeline | 本閉環系統 |
|------|---------|---------------------|-----------|
| 驗證時機 | 每個開發階段有對應驗證 | 程式碼提交時 | 每個角色完成時 |
| 驗證範圍 | 需求-設計-實作各層 | 程式碼品質 | 所有產出物的一致性 |
| 自動化程度 | 中等 | 高 | 設計中（可高） |
| 獨特價值 | 層級對稱性 | 快速回饋 | **跨產出物一致性驗證** |
| 主要風險 | 流程僵化 | 覆蓋面有限 | 角色過多、流程過長 |

本閉環系統的獨特價值在於「自証」這個 meta-validation 層。
V-Model 驗證的是「每層做對了嗎」，本系統驗證的是「所有層之間是否一致」。
