# 落地路線圖：開發設計閉環

## 執行原則

- **先跑通再完善**：用最精簡版本驗證可行性，再逐步擴展
- **自証優先**：先定義清楚自証標準，其他角色才有明確的終點
- **實際驗證**：每個階段都用真實程式碼跑一次閉環

---

## Phase 1：定義自証標準

**目標**：回答「自証師到底在驗證什麼」

### 待定義項目

#### 1.1 自証師的輸入

自証師需要收到哪些產出物？建議最精簡版本：

| 產出物 | 來源角色 | 格式要求 |
|--------|---------|---------|
| 設計規格 | 架構師 | 函式簽名、輸入/輸出定義、邊界條件 |
| 程式碼 | 程序設計師 | 實際可執行的程式碼 |
| 檢核結果 | 程序檢核師 | 問題清單（嚴重度、位置、建議） |
| 測試結果 | 測試師 | 通過/失敗、覆蓋率、邊界測試結果 |
| 自証結論 | 自証師自己 | 通過/不通過 + 不一致項目列表 |

#### 1.2 自証的驗證維度

| 維度 | 驗證問題 | 判定標準 |
|------|---------|---------|
| 設計-實作一致性 | 程式碼是否完整實現了設計規格？ | 所有設計的輸入/輸出/邊界都有對應實作 |
| 實作-測試覆蓋 | 測試是否覆蓋了設計中定義的所有場景？ | 覆蓋率 ≥ 設計規格中的場景數 |
| 檢核-修正閉合 | 檢核報告中的問題是否都已修正？ | 所有嚴重度 ≥ 中 的問題已處理 |
| 產出物完整性 | 所有必要的產出物是否都存在？ | 無缺漏的產出物 |

#### 1.3 不通過時的回退規則

| 不一致類型 | 回退目標 | 原因 |
|-----------|---------|------|
| 設計-實作不一致 | 程序設計師（或架構師） | 實作偏離設計，或設計本身需修正 |
| 測試覆蓋不足 | 測項規劃師 | 測試計畫遺漏場景 |
| 檢核問題未修正 | 程序設計師 | 已知問題未處理 |
| 產出物缺漏 | 對應角色 | 某角色未產出文件 |

## Phase 2：最精簡方法層級閉環

**目標**：用 5 個角色跑通一次完整閉環

### 精簡角色配置

```
需求輸入（前置條件，非角色）
    ↓
[1] 架構師 → 產出：設計規格
    ↓
[2] 程序設計師 → 產出：程式碼
    ↓
[3] 檢核師 → 產出：檢核報告（合併程式碼 + 安全檢核）
    ↓
[4] 測試師 → 產出：測試程式碼 + 測試結果（合併規劃 + 設計 + 執行）
    ↓
[5] 自証師 → 產出：自証結果
    ↓
  通過 → 完成
  不通過 → 回退到對應角色
```

### 合併邏輯

| 原始角色 | 合併為 | 合併原因 |
|---------|--------|---------|
| 程序檢核師 + 安全檢核師 | 檢核師 | 方法層級的安全問題通常與程式碼品質相關 |
| 測項規劃師 + 單元測試設計師 + 測試師 | 測試師 | 方法層級的測試規模小，一人可完成全流程 |
| 效能評估師 | 暫時移除 | 方法層級的效能問題較少，先不納入 |

### 驗證場景

選擇一個具體的函式作為測試案例，建議：
- 複雜度適中（有 2-3 個邊界條件）
- 有明確的輸入/輸出定義
- 涉及基本的錯誤處理

## Phase 3：產出物 Schema 設計

**目標**：定義統一的產出物格式，讓自証師能結構化比對

### 設計規格 Schema（架構師產出）

```yaml
function_spec:
  name: ""
  purpose: ""
  inputs:
    - name: ""
      type: ""
      constraints: ""
  outputs:
    - type: ""
      description: ""
  boundary_conditions:
    - condition: ""
      expected_behavior: ""
  error_handling:
    - error_type: ""
      handling: ""
```

### 檢核報告 Schema（檢核師產出）

```yaml
review_report:
  target: ""
  reviewer: ""
  findings:
    - id: ""
      severity: "high|medium|low"
      location: ""
      description: ""
      recommendation: ""
      status: "open|resolved"
```

### 測試結果 Schema（測試師產出）

```yaml
test_report:
  target: ""
  coverage:
    boundary_conditions_covered: 0
    boundary_conditions_total: 0
    error_handling_covered: 0
    error_handling_total: 0
  results:
    - test_name: ""
      spec_reference: ""  # 對應設計規格中的哪個條件
      status: "pass|fail"
      details: ""
```

### 自証結果 Schema（自証師產出）

```yaml
verification_result:
  target: ""
  verdict: "pass|fail"
  checks:
    - dimension: "設計-實作一致性|測試覆蓋|檢核閉合|產出完整性"
      status: "pass|fail"
      evidence: ""
      gap_description: ""  # 若 fail，描述不一致的具體內容
  rollback_recommendation:
    target_role: ""
    reason: ""
```

## Phase 4：擴展角色與層級

**前提**：Phase 2 的精簡閉環已驗證可行

### 4.1 擴展角色（方法層級）

逐步加回被移除的角色：
1. 先加入安全檢核師（從檢核師中拆分）
2. 再加入效能評估師
3. 最後拆分測試角色（規劃 → 設計 → 執行）

### 4.2 擴展到模組層級

定義模組層級的特殊需求：
- 模組閉環的輸入 = 該模組內所有方法閉環的產出物
- 模組層級的架構師關注職責劃分、內聚性
- 模組層級的自証師額外驗證方法之間的協作正確性

### 4.3 定義介面橋接閉環

將「介面」從獨立層級改為模組間的橋接驗證：
- 觸發時機：兩個以上的模組閉環完成後
- 驗證重點：API 契約、資料格式、錯誤傳播
- 角色：介面規劃師 + 介面檢核師 + 自証師

## Phase 5：AI Agent 實作

**前提**：Phase 1-3 的定義已完成，Phase 2 已手動驗證可行

### 為每個角色設計 Agent Prompt

每個角色需要：
- **系統 prompt**：定義角色身份、職責範圍、產出格式
- **輸入 template**：接收前一個角色產出的格式
- **產出 template**：符合 Schema 的結構化輸出
- **品質標準**：該角色的通過/不通過條件

### 串接為自動化 Pipeline

```
需求文件 → Agent[架構師] → Agent[程序設計師] → Agent[檢核師]
→ Agent[測試師] → Agent[自証師] → 通過/回退
```

可使用的技術方案：
- SuperClaude 的 `/spawn` 多 Agent 調度
- 外部框架：CrewAI / AutoGen / LangGraph
