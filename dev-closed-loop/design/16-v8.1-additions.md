# 16 · v8.1 補四項：白話、架構與可維護性、模型分級、SSOT

日期：2026-09-03。承接 `15-v8-slim.md`。v8.0 是砍，v8.1 是在砍完的骨架上加回四樣用戶點名要的東西。本文記為什麼這樣加、放在哪、哪裡做不到理想狀態。

## 用戶要什麼

原話（白話轉述）：

1. 跟用戶互動，不管講程式碼還是講做事方式，都要白話、簡單、一眼懂。
2. 改碼和處理事情都要有好架構、好模組化、好維護。
3. 開 workflow 時不要一律用最強模型，依難易度智能分配模型等級。
4. 處理事情要以 SSOT（單一事實來源）原則，「才不會修改後有些內容沒有修改到」。

用戶對我提的三個推薦全數採納：模型分配用靜態表不做動態分類器；架構規則同時寫進模板與 dev-design / dev-review 審查標準；程式碼審查「找問題」可比主對話低一階，設計審查與安全審查不降。

## 加法原則

v8.0 的教訓是「規則要能檢查、要掛在對的時機」。所以四項都照這三條加：

- 掛在既有結構上：白話掛語言設定，重複定義掛 Section 2，架構規則自成一節但同時是 workflow 的審查標準，模型分級掛「可用 workflow」段並沿用 Section 1 的難度尺。
- 寫成能檢查的動作，不寫口號。「要白話」不能檢查，「先結論、術語附一句解釋、改動講三件事」可以。
- 不開新 hook。`impact-analysis-guard.sh` 有動，但只改阻擋訊息裡格式行的來源：從 `${CLAUDE_PROJECT_DIR:-.}/CLAUDE.md` 的「**輸出**」行讀，讀不到才用腳本內 fallback。模板 134 → 164 行。

## 模型分級的具體分派

| workflow | 低 | 中 | 高 |
|----------|----|----|----|
| dev-design | 無 | explore | propose ×3、refute ×3、judge、synthesize |
| dev-prd | 無 | discover ×3、shape ×2 | challenge、synthesize |
| dev-review | synthesis | correctness、maintainability | security、verify ×N |
| dev-verify | enumerate、synthesis | forward、reverse | 無 |

這張表是動工時的快照。逐 agent 分派的唯一出處是各 workflow 腳本本身；模板只定義等級，不列 agent 名，避免第二份真相。模板明講的兩個承諾（dev-review 找問題中階、反駁驗證與 security 高階）由 cross-file Check 6b 鎖。

判斷理由：

- 「高」不指定 model 而是繼承主對話，因為 workflow 腳本不知道主對話用什麼，寫死 opus 在用戶主對話是 fable 時反而降級。「不指定即繼承主對話」的依據是 Claude Code workflow-authoring 參考文件原文：「Default to omitting it — the agent inherits the main-loop model (the resolved session model)」。這是字面證據（A 級），但沒有實跑印出模型確認。
- 「中」用 sonnet 而不是只降 effort，因為找問題的人和驗證的人用不同模型，正好補上 R-2「換來源」目前只有同模型不同 context 的缺口。
- security 放高階，跟我對用戶說的一致（判斷型含安全審查）。用戶同意的「程式碼審查可降一階」只套在 correctness 與 maintainability 兩個 lens。
- 彙整放低階的條件是輸入已結構化、規則已給定。dev-review 與 dev-verify 的 synthesis 符合。dev-prd 與 dev-design 的 synthesize 要做取捨判斷（切 MVP 邊界、吸收 skeptic 缺陷修設計），屬判斷型，兩者都給高。

| 事實 | 層級 | 做法 |

## 沒做到、沒驗證的

- workflow `agent()` 的 `model` 選項用 `haiku` / `sonnet` 這兩個別名，是沿用 Agent 工具的 enum。workflow 執行需付費方案且用戶未要求開 workflow，本輪沒實跑。第一次跑 `/dev-verify` 時若報 model 無效，改成完整 model id 並同步四份 `TIERS`。
- 「不指定 model 即繼承主對話」只有 workflow-authoring 文件的字面證據，沒有實跑印出 high 階 agent 實際用的模型。若實際落到某個預設子 agent 模型而非主對話，「判斷型不降級」會反轉成比中階還低，且不會有任何提示。第一次跑任一 workflow 時，請 high 階 agent 在回報裡附上自己的模型名確認。
- `ARCH_RULES` 讓 agent 用 Read 讀專案 CLAUDE.md，靠 `<!-- arch-rules -->` 錨點定位。若 Claude Code 讀 CLAUDE.md 時過濾 HTML 註解，只影響主對話看不到錨點，不影響 agent 用 Read 工具讀檔。未驗證過濾行為。
- 四項對正確性的增益沒有量化。加它們的依據是成本低、可檢查、對人可見，跟 v8.0 保留項目的依據相同。
- 模型分級省多少 token 沒量過。
