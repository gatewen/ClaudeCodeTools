## 升級摘要

從 Karpathy 4 原則（Think Before Coding / Simplicity First / Surgical Changes / Goal-Driven Execution）萃取本專案缺失的價值維度，分 4 個 milestone 漸進式整合。**v6.0.0 只做核心結構與哲學改動**，細節項分到後續 minor 版本。

**核心問題識別**：本專案閉環把 Karpathy 4 原則**切片**到 Phase 中（Phase 1=Think 部分、Phase 2=Surgical 部分…），但 4 原則本應是 **cross-cutting concerns**（每次代碼接觸都成立）。切片導致：Phase 2 不再被要求 Think、Phase 3 不再被要求 Push back——精神在切片過程被「假設已完成」吃掉。

**v6.0.0 要做的**：補上 cross-cutting 自檢層 + 補上「主動反對用戶」的行為文化。

---

## 為什麼是 Major Bump

15 條優化中真正 major 的只有 3 條（其餘 12 條是 minor/patch）：

| 條目 | 為什麼算 major | Breaking 影響 |
|------|--------------|--------------|
| **K-01** 4 原則 cross-cutting 自檢層 | 新增 Section 0 改變 CLAUDE_TEMPLATE 的根結構 | 已部署專案需 migration（K-17 處理） |
| **K-04** Push back 義務（Section 12.5） | 新增「主動反對用戶」的行為文化，AI ↔ 用戶關係改變 | 行為哲學維度新增，使用體感改變 |
| **K-13** Karpathy 自循環模式（v6.3.0 才做） | implementer/tester 失敗處理流程改變 | 跟現有斷點 B 機制有交互 |

叫 v6.0.0 的條件：必須包含 **K-01 + K-04**（v6.0.0 已含），不然名實不符。

## Migration 策略（K-17 是 enabler）

### 偵測機制

`skill/init-claude.md` 的 `upgrade` mode 加入 v6.0.0 偵測 logic：

```
讀取目標專案的 CLAUDE.md
1. 偵測版本：Grep 末尾 `closed-loop v6.0.0` 字串
2. 若已是 v6.0.0+ → 跳過 migration
3. 若是 v5.x（無 Section 0）→ 進入 migration flow
```

### Migration Flow

1. 顯示「v5.x → v6.0.0 升級摘要」（從 K-17 機制讀 CLAUDE_TEMPLATE 末尾的 migration notes）
2. AskUserQuestion 確認用戶是否升級
3. 用戶選是 → 三種策略：
   - **A. 全替換**：直接覆蓋為新 CLAUDE_TEMPLATE（用戶的客製化會丟）
   - **B. 智能合併**：保留用戶客製化，僅在指定錨點注入 Section 0 / 12.5（推薦）
   - **C. 手動**：印出 diff，用戶自己貼

策略 B 的錨點：
- Section 0 注入點：`## ⚠️ 執行約束（最高優先級）` 之前
- Section 12.5 注入點：Section 12 結尾、Section 13 之前

### Migration Notes 格式（K-17）

`CLAUDE_TEMPLATE.md` 末尾新增區塊：

```markdown
<!--
migration-notes (read by /dev:init-claude upgrade)

from-version: v5.x
to-version: v6.0.0
breaking-changes:
  - 新增 Section 0「四原則 cross-cutting 自檢層」
  - 新增 Section 12.5「Push back 義務」
required-actions:
  - 部署新 Section 0 / 12.5
  - 確認所有 placeholder 仍正確替換
recommended-actions:
  - 重新閱讀 .claudedocs/concepts/閉環核心理念.md
-->
```
