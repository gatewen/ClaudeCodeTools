## K-07 條目規格

### 5 個 anti-pattern 對照檔案

每個檔案結構統一為：
1. **場景**：典型開發情境
2. **錯誤示範**：違反 Karpathy 4 原則 / 閉環機制的具體做法
3. **原則診斷**：對應 Karpathy Q1-Q4 / 閉環機制的哪一條
4. **修正版本**：正確做法的具體實作
5. **關鍵限制**：什麼情況可以例外、什麼情況不適用

**檔案清單**：

| 編號 | 檔名 | 違反原則 | 場景示例 |
|-----|------|---------|---------|
| 01 | `01-think-before-coding.md` | Q1 Think | 用戶說「修一下這個 API」（含糊）→ 默默選一種解讀直接動 |
| 02 | `02-simplicity-first.md` | Q2 Simplicity | 用戶要計算「打折價」→ 用 Strategy pattern 處理單一計算 |
| 03 | `03-surgical-changes.md` | Q3 Surgical | 修 typo bug → 順手 reformat 引號 / 加 type hints |
| 04 | `04-goal-driven-execution.md` | Q4 Goal | 用戶報「測試失敗」→「我先 review 整個檔案再改善」 |
| 05 | `05-cross-artifact-mismatch.md` | 閉環特色（Q4 Goal 延伸） | 設計 5 種錯誤 → 實作 3 種 → 測試 2 種，傳統 Review 抓不到 |

**檔案位置**：`.claudedocs/examples/0X-{slug}.md`

**行數規範**：每個檔案 80-120 行（含 heading + 5 個結構性段落 + 程式碼範例）

**不加 examples/README.md 索引**：5 個檔案內容夠完整，不需要額外索引；reviewer 想找哪個 anti-pattern 直接看檔名 + 開頭場景描述即可。

## K-13 緩議說明

**為什麼 v6.3.0 不做 K-13**：

design/08 RISK-6 標：「K-13 自循環跟斷點 B 衝突（v6.3.0）」中等風險，緩解策略：「先用 brainstorming skill 釐清狀態機」。

K-07 完成後啟動獨立 brainstorming session 處理 K-13，可能結果：

1. **可整合 → v6.4.0 做 K-13**（單條 K-x 一個 milestone）
2. **整合複雜度高 → 推 v7 重評**（跟 K-11 KPI 觀察期資料一起評估）
3. **不適合本方法論 → 移除**（K-13 跟閉環既有斷點機制重疊）

K-13 brainstorming 的核心問題：
- 「3 輪自修正」是新機制還是擴充既有斷點 B（implementer/tester 失敗回退）？
- 自修正的終止條件（避免無限循環）跟斷點熔斷（≥ 3 次觸發 → AskUserQuestion）的關係？
- 自修正過程中是否走完整 5-Phase 還是只跑 P2 / P4？
- 用戶介入時機（總是介入 vs 自修正失敗才介入）？

這些問題在 brainstorm 完前無法寫具體規格，所以 v6.3.0 暫緩。
