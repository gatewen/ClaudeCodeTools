# dev-closed-loop 完整分析報告

## 一、總體評價

**這是一套有真實創新價值的方法論。** 在 AI 輔助開發工具大量湧現的時代，大多數人專注於「讓 AI 寫更多程式碼」，而本方法論專注於「讓 AI 寫的程式碼可以被信任」。這個方向選擇本身就值得肯定。

核心創新——Phase 5 自証師的「跨產出物一致性驗證」——填補了傳統開發流程的一個真實盲區。Code Review 看程式碼品質、單元測試驗證功能正確性、CI/CD 驗證建置和測試通過，但**沒有人去比對設計規格、程式碼、檢核報告和測試報告之間有沒有矛盾**。自証機制就是做這件事。

整體完成度相當高：方法論定義清晰、工具鏈可運作、文檔品質優秀。但也存在若干設計層面的深層問題和具體的不一致之處。以下分四個維度展開。

## 二、方法論設計品質分析

### 2.1 設計亮點

**ID 追溯系統是整套方法論的骨幹。** BC-x / EH-x / R-x / MC-x / EP-x / MD-x 六種前綴覆蓋了從函式到框架的所有層級，每個 ID 從定義到引用有清晰的生命週期。沒有這套 ID 系統，Phase 5 的自証就只能是籠統的「看看有沒有問題」，而不是精確的「BC-1 有設計、有實作、有測試」。

**斷點機制的位置選擇精準。** 斷點 A 放在 Phase 3→4 之間（high issue 攔截），斷點 B 放在 Phase 4→5 之間（test failure 攔截）。這兩個位置恰好是成本曲線的拐點——越晚發現問題，修復成本越高。在 Phase 3 就攔截嚴重問題，避免為有根本缺陷的程式碼寫測試。

**code-simplifier 強制步驟的設計動機正確。** 用獨立 Task agent 而非同一個對話內的 Skill，目的是避免「自己審自己」的認知偏見。Agent 使用指南中對此有很好的解釋。這個設計決策顯示了對 LLM 行為模式的深刻理解。

**層級擴展的遞進結構完整。** 函式→模組→框架三層，每層增加新的 ID 前綴（MC-x/EP-x → MD-x），低層級的產出物作為高層級的輸入，且不需要攜帶中間產出物（只帶設計規格和自証結果）。這個設計很節制——沒有讓信息量隨層級爆炸。

### 2.2 設計疑慮

#### 2.2.1 Phase 5 三步走可能冗餘

Phase 5 要求依序執行：(1) 自証檢查表 6 步 → (2) `sc:reflect --type completion` → (3) `superpowers:verification-before-completion`。

**我的看法**：自証檢查表 6 步本身已經是完整的自証流程——建立基準清單、逐一比對、輸出結果。後面兩個 Skill 的預設行為分別是「任務反思」和「跑測試確認完成」，**它們的核心能力與自証的目標並不對齊**。Agent 使用指南自己也承認了這一點：「`sc:reflect` 和 `superpowers:verification-before-completion` 的預設行為…都不是跨產出物一致性比對。光靠 CLAUDE.md 的約束文字不一定能覆蓋它們的預設行為。」

既然知道這些 Skill 的預設行為不對、約束文字也不一定能覆蓋，為什麼還要調用它們？這看起來像是「多做一步不會錯」的保守策略，但實際上增加了 token 消耗和時間，而且引入了不必要的行為不確定性。

**建議**：Phase 5 以自証檢查表 6 步為唯一核心。`sc:reflect` 和 `superpowers:verification` 改為可選的補充步驟，且明確說明它們的預期貢獻（完成度評估 / 最終驗證）而非自証本身。

#### 2.2.2 對 LLM 上下文窗口的隱性依賴

整個閉環設計假設在**單一對話**中執行。Phase 5 需要回溯 Phase 1-4 的所有產出物做比對。對於一個有 5 個 BC、3 個 EH 的中等複雜度函式，Phase 1-4 的產出物加上中間的討論和 Agent 輸出，token 消耗可能達到 50K-100K。如果是模組層級（多個函式 + 整合），消耗更大。

**風險**：當對話接近上下文窗口限制時，系統會壓縮早期訊息。Phase 1 的設計規格可能被壓縮或丟失，導致 Phase 5 的自証基於不完整的資訊。

**方法論中沒有任何機制來處理這種情況。** 沒有「將產出物寫入檔案以持久化」的建議（Agent 使用指南提到了「檔案傳遞」用於跨 session，但沒有要求在單一 session 內也做這件事），也沒有「當上下文接近滿載時如何處理」的指引。

**建議**：在閉環調度規則中加入一條規則：每個 Phase 完成後，將產出物（設計規格、檢核報告、測試報告）寫入專案的暫存目錄（如 `.claude-loop/`），Phase 5 自証時從檔案讀取而非依賴對話記憶。這同時也解決了「對話斷掉後無法恢復」的問題。

#### 2.2.3 斷點 B 的回退策略可能過度

斷點 B 的規則是：測試失敗 → 回到 Phase 2 修正 → **重跑 Phase 3 和 Phase 4**。

**問題**：如果測試失敗的原因是 Phase 4 的測試本身寫錯（例如斷言寫反、測試數據不對），不應該回到 Phase 2，也不需要重跑 Phase 3。正確的做法是在 Phase 4 內修正測試再重跑。

當前的規則把所有測試失敗都歸因於 Phase 2（實作問題），但實際上失敗原因可能是：
- Phase 2 的實作有 bug（需要回 P2）
- Phase 4 的測試寫錯（只需在 P4 修正）
- Phase 1 的設計規格有問題，導致實作和測試不一致（需要回 P1）

**建議**：斷點 B 觸發時，先做一步根因分析（可調用 `root-cause-analyst`），根據原因決定回退目標，而不是一律回到 Phase 2。

#### 2.2.4 觸發條件的邊界模糊

觸發閉環的條件是：「新增函式/類別/模組、重構 >= 3 個函式、安全相關程式碼」。跳過的條件是：「1-3 行 bug 修正」。

**灰色地帶**：
- 修改 2 個函式的核心邏輯（不到 3 個，但影響很大）→ 走不走？
- 新增一個 2 行的 helper 函式 → 算新增函式嗎？
- 修改一個函式的 10 行，但邏輯沒變（只是重構內部實作）→ 走不走？

方法論有提供用戶覆蓋機制（「完整閉環」/「快速修改」），但 Claude 自己判斷的預設行為在灰色地帶可能不一致。

**建議**：加一個「判斷不確定時」的預設行為，例如：「不確定時用 AskUserQuestion 詢問用戶」或「不確定時預設走閉環」。

#### 2.2.5 缺少「快速閉環」的中間模式

目前只有兩個極端：走完整五階段閉環 vs 完全跳過。

但很多變更（例如修一個邏輯 bug，涉及 5-10 行程式碼）不值得走完整閉環，但也不是微小到可以完全跳過。一個只包含「修改→測試→快速確認」的簡化閉環（跳過正式的設計規格和檢核報告）可能更務實。

## 三、工具鏈與部署機制分析

### 3.1 雙層架構的設計合理

安裝層（`setup.sh`）和使用層（`/dev:init-claude` Skill）的分離是正確的。安裝腳本做一次性的路徑替換和驗證，Skill 做每次部署時的專案偵測和互動。兩者職責清晰不重疊。

### 3.2 具體問題

#### 3.2.1 跨平台問題（嚴重）

- **`setup.sh`**：純 bash 腳本，使用 `sed`、`grep`、`ls`、`cp`。在 Windows 上需要 WSL、Git Bash 或 MSYS2。
- **`init-claude.md` 第 197 行**：`cp -r "{{REPO_PATH}}/dev-closed-loop/.claudedocs/" "./.claudedocs/"`。這是 Unix 指令。在 Windows 的 Claude Code 環境中，如果 shell 不支援 `cp -r`，部署會失敗。
- **當前 repo 在 Windows 上**（`platform: win32`），說明作者自己就在 Windows 上開發。

**建議**：
- Skill 中的檔案操作改用 Claude Code 的內建工具（Read + Write），而不依賴 shell 指令。
- `setup.sh` 考慮提供 PowerShell 版本，或在腳本開頭檢測平台。

#### 3.2.2 缺少版本管理

`setup.sh` 沒有：
- 版本號（不知道裝的是哪個版本）
- 升級檢查（不知道是否需要重裝）
- 卸載功能（只能手動刪除 `~/.claude/commands/dev/init-claude.md`）
- 備份機制（重裝時會覆蓋已有的 Skill）

### 3.3 Skill 偵測邏輯的健壯性

`init-claude.md` 的專案偵測邏輯（Step 2）覆蓋了主流語言和框架，兩階段掃描策略（先根目錄、再一層子目錄）合理。Step 2.5 的「全部未偵測到」攔截也是好的防禦設計。

但偵測邏輯有一個假設：專案只使用一種語言。Monorepo（前端 TypeScript + 後端 Go）或多語言專案（Python + JavaScript）會只偵測到第一個匹配的語言。

## 四、文檔品質與一致性分析

### 4.1 文檔品質（優秀）

- **寫作風格一致**：所有文檔都用白話文，避免術語堆砌。「用白話說」的設計特別好。
- **結構清晰**：每份文檔有明確的定位說明（「這份文件是幹嘛的」）。
- **權威性聲明正確**：`產出物格式.md` 開頭就說「CLAUDE.md 中的格式定義為執行權威…如有出入，以 CLAUDE.md 為準」。
- **日期維護**：所有文檔的「最後修訂」日期一致（2026-02-12），說明是同步更新的。

### 4.2 發現的具體不一致

#### BUG-1：幽靈 Agent —— `code-review-optimizer`（中等嚴重）

**位置**：`CLAUDE_TEMPLATE.md:166`
```
- 程式碼品質 → 額外調用 Task agent `code-review-optimizer`
```

**問題**：`code-review-optimizer` 不是 Claude Code 的內建 Task agent。Claude Code 內建的 Task agent 列表中沒有這個名稱（有 `code-simplifier`、`superpowers:code-reviewer` 等，但沒有 `code-review-optimizer`）。

**影響**：Claude 執行到 Phase 3 時如果選擇調用 `code-review-optimizer`，Task 調用會失敗或產生非預期行為。

**Agent 使用指南中也沒有提到這個 agent**——Phase 3 的推薦組合是 `superpowers:code-reviewer` + `security-engineer`。

#### BUG-2：補充文檔數量不一致（低嚴重）

三處提到 .claudedocs 檔案數量，說法不同：

| 位置 | 說法 | 實際 |
|------|------|------|
| `setup.sh:144` | "✅ .claudedocs 完整（8/8）" | 正確，8 個檔案 |
| `init-claude.md:230` | "7 份補充文檔，給人類閱讀" | 錯誤，應為 8 份（或 7 份 + README.md） |
| `CLAUDE_TEMPLATE.md:438-446` | 表格列 7 項（不含 README.md） | 一致但不完整 |

**根因**：README.md 是 .claudedocs 的一部分但不是「補充文檔」（它是目錄索引）。應該統一說法——「8 個檔案」或「7 份補充文檔 + 1 份 README」。

#### BUG-3：跨平台指令問題（中等嚴重）

**位置**：`init-claude.md:197` 和 `:252`
```bash
cp -r "{{REPO_PATH}}/dev-closed-loop/.claudedocs/" "./.claudedocs/"
```

`cp -r` 是 Unix 指令，在 Windows 原生環境中不可用。考慮到 Claude Code 在 Windows 上可能使用 PowerShell 或 cmd，這個指令可能失敗。

### 4.3 CLAUDE_TEMPLATE.md 與 .claudedocs 的一致性

逐一比對兩邊的內容：

| 主題 | CLAUDE_TEMPLATE.md | .claudedocs 對應檔案 | 一致性 |
|------|-------------------|---------------------|--------|
| 五階段流程 | 完整定義，含 Agent 調用方式和約束 | 五階段閉環流程.md — 白話文描述，無 Agent 細節 | ✅ 一致（詳略不同但不矛盾） |
| 產出物格式 | 完整定義，含所有模板 | 產出物格式.md — 相同模板 | ✅ 一致 |
| ID 系統 | 6 種前綴，含使用階段 | 層級擴展.md — 同樣 6 種前綴，含定義/引用層級 | ✅ 一致 |
| Agent 調用 | Phase 1-5 各列出具體 Agent 和優先順序 | Agent使用指南.md — 補充選擇邏輯和常見錯誤 | ⚠️ 基本一致，但 `code-review-optimizer` 只出現在模板中 |
| 斷點機制 | 斷點 A（P3→P2）、斷點 B（P4→P2，重跑P3+P4） | 五階段閉環流程.md — 一致 | ✅ 一致 |
| Git 規範 | 5 條簡要規則 | Git工作流.md — 詳細展開，含 commit message 格式 | ✅ 一致 |

**總結**：CLAUDE_TEMPLATE.md 和 .claudedocs 之間的一致性很好，唯一問題是 BUG-1 的幽靈 Agent。

## 六、我的深層觀點

### 6.1 這套方法論最大的價值不是「品質保證」

表面上看，這是一套品質保證方法論。但我認為它更深層的價值是**馴化 LLM 的行為模式**。

LLM（包括 Claude）有幾個已知的行為傾向：
1. **討好式回應**——傾向於告訴你「一切都好」而不是指出問題
2. **認知偏差**——自己寫的程式碼自己 review 時會傾向於認為沒問題
3. **上下文遺忘**——長對話後面的步驟可能忘記前面的約束
4. **偷懶傾向**——如果不強制要求格式和步驟，會傾向於跳過或簡化

閉環方法論用**結構化的指令**（不是建議，是指令）來對抗這些傾向：
- ID 編號系統讓 LLM 不能籠統地說「都檢查了」，必須逐一列舉
- 固定格式讓產出物可追溯、可比對
- code-simplifier 用獨立 Agent 來避免自己審自己
- 斷點機制強制停下來，不讓 LLM 一路衝到底

**這是一套「LLM 行為工程」，偽裝成品質方法論。** 這個洞察很有價值。

### 6.2 潛在的反效果

但也正因為如此，這套方法論有一個根本性的張力：**它用 LLM 來約束 LLM**。

Phase 3 的檢核師、Phase 5 的自証師，都是由同一個 Claude 實例在同一個對話中扮演的。即使有 Agent 切換和角色提示，底層仍然是同一個模型、同一段對話歷史。要 Claude 真正客觀地「找碴」自己前面寫的程式碼，與它的討好傾向是矛盾的。

**code-simplifier 用 Task agent（獨立子程序）解決了 Phase 2→3 的自我偏見問題，但 Phase 3 的檢核和 Phase 5 的自証沒有這個隔離。** 如果要徹底解決，Phase 3 的 code review 也應該盡量用 Task agent，而不是同一對話中的 Skill。Agent 使用指南中已經建議了這個做法（Phase 3 推薦用 Task agent 做平行 review），但 CLAUDE_TEMPLATE.md 中的「調用方式（擇一）」把 `sc:analyze` 列為首選，這與「避免自己審自己」的原則有衝突。

### 6.3 實際效果的不確定性

方法論的設計很精密，但有一個根本問題無法在文檔層面解決：**Claude 會不會真的照做？**

CLAUDE.md 是 Claude Code 的指令來源，Claude 確實會嘗試遵循。但：
- 455 行的指令中，Claude 的遵循程度可能不均勻——顯眼的規則（如 Phase 進出標記）更容易被遵循，微妙的約束（如「不能自行增加功能」）可能被忽略
- 隨著對話加長，早期的指令可能被壓縮，遵循度下降
- 不同版本的 Claude 模型對同一份 CLAUDE.md 的遵循行為可能不同

**建議**：在 .claudedocs/records/ 中維護一份「合規性觀察」文檔，記錄實際使用中 Claude 在哪些步驟容易跳過或敷衍，逐步優化指令措辭。

### 6.4 最被低估的設計：閉環可見性規則

`CLAUDE_TEMPLATE.md` 中「閉環可見性規則」段落（第 46-111 行）是整份模板中我認為**被低估但最實用**的部分。

它要求：
1. 用 TaskCreate 建立 5 個任務追蹤進度
2. 每個 Phase 進出時輸出分隔線標記
3. 每次 Agent 調用時輸出宣告和結果摘要

這些看起來只是「格式化輸出」，但實際效果是：
- **讓用戶知道閉環在哪裡**——不會在漫長的 AI 輸出中迷路
- **讓用戶可以介入**——看到 Phase 標記就知道什麼時候可以打斷或修正
- **產生可審計的記錄**——事後可以回溯哪個 Phase 做了什麼

這種「可觀察性優先」的設計原則在 DevOps 領域很成熟，但在 AI 輔助開發工具中很少見。

## 八、結論

**最有價值的潛力**是將這套「LLM 行為工程」的思路推廣——不只用在品質保證，還可以用在其他需要「約束 LLM 行為」的場景，例如安全合規、文檔一致性、多人協作等。
