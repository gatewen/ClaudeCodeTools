## ⚠️ 執行約束（最高優先級）

收到任何非微小的任務時，**禁止直接開始寫程式碼**。必須先判定等級再執行對應流程。

### 1. 判定任務等級（必做）

| 等級 | 條件 | 要求的流程 |
|------|------|-----------|
| **微小** | < 50 行 · 單檔修改 · 設定調整 · 用戶說「快速修改」 | 直接執行 |
| **中型** | 新增單一函式/元件 · 1-3 檔案 · < 300 行 | 精簡閉環（設計→設計快審→實作→品質審查→測試驗證） |
| **大型** | 新模組/功能 · (≥ 3 檔案或 ≥ 300 行) 且有多個交互子系統 · 用戶說「完整閉環」 | 完整五階段閉環（Phase 1→5） |

### 1b. 需求探索（中型 + 大型 · 可選）

需求描述不夠具體（缺少明確範圍、技術路線、或行為預期）時，用 AskUserQuestion 詢問用戶是否要先探索需求。用戶選否 → 跳到 Section 2。
**用戶選是 → Claude 主動從多角度分析，整理為選項讓用戶選擇**：
- 至少涵蓋 3 個角度，每個角度產出**具體選項**（非分析報告），用 AskUserQuestion 呈現：
  - **範圍界定**：MVP vs 完整版的切分建議，讓用戶選邊界
  - **替代方案**：2-3 種技術路線的取捨比較，讓用戶選方向
  - **邊界情境**：容易忽略的極端/並發/異常情境，讓用戶決定是否納入
  - **架構影響**：對現有系統的衝擊範圍，讓用戶確認可接受的影響
- 可多輪迭代直到需求收斂
- **產出**：明確的需求陳述（含範圍、關鍵行為、已決定的技術方向），作為 Phase 1 的輸入

### 2. TaskCreate 拆解（中型 + 大型必做）

**大型任務 — 單模組**：建 6 個 Phase 任務 + blockedBy 鏈：
`[P1-設計] → [P1b-設計審查] → [P2-實作] → [P3-檢核] → [P4-測試] → [P5-自証]`

**大型任務 — 多模組**：每個模組建 `[P1] → [P1b] → [P2] → [P3] → [P4]` 鏈，有 IF-x 依賴的模組按依賴順序執行（被依賴方先完成 P2）。所有模組完成 P4 後 → 統一 `[P5-整合自証]`（blockedBy 所有 P4）。
**單模組 vs 多模組判定**：子系統共享核心狀態物件且 API 邊界不清晰 → 視為單模組；子系統有獨立狀態且透過明確介面溝通 → 視為多模組。

**中型任務** — 建 5 個任務 + blockedBy 鏈：
`[設計] → [設計快審] → [實作] → [品質審查] → [測試驗證]`

**每步上限**：最多 2-3 個檔案或 ~300 行程式碼。有強型別依賴的檔案（拆開會導致增量驗證失敗）可捆綁在同一步，即使超過 3 檔。

### 3. ⛔ 禁止跳過的閘門

- ⛔ **禁止**沒有設計產出就寫程式碼
- ⛔ **禁止**沒有驗證就標完成
- ⛔ **禁止**單次回應寫完所有檔案

### 4. 逐步執行（必做）

- 按順序，一次只做一個步驟
- 每完成一步，用 TaskUpdate 標記 completed
- blockedBy 未解除前，禁止將該任務設為 in_progress
- **升級機制**：實作過程中若發現實際規模超出當前等級（精簡閉環的檔案數 ≥ 3 或行數 ≥ 300），暫停當前流程，升級為完整閉環（已完成的設計保留為 Phase 1 基礎，從 Phase 2 繼續）

### 5. 可見性（必做）

- **TaskCreate**：觸發閉環時立即建立任務鏈（大型 6 個 / 中型 5 個），讓用戶看到進度
- **Phase 標記**：進入/離開每個 Phase 時輸出 `═══ 📐 Phase 1：架構師 | 開始 ═══` 格式標記
- **Agent 宣告**：調用 Agent 時輸出 `→ 調用 ...`，完成時輸出 `← ... 完成：[摘要]`

### 6. 領域偵測與規則預設（Phase 1 前自動判定）

根據專案語言、框架、imports 自動偵測領域，套用對應預設。用戶可覆蓋（例如「使用遊戲開發預設」）。

| 領域 | 偵測信號 | EH-x | 安全審查 | 驗證層級預設 | 單檔上限 |
|------|---------|------|---------|------------|---------|
| 遊戲開發 | macroquad/bevy/godot/unity/Canvas 遊戲迴圈 | 可選 | 可跳過 | 預設 `[framework-dependent]`，例外標注 | 400 行 |
| 後端 API | express/fastapi/gin/actix/HTTP handler | 必要 | 必要 | 預設 `[testable]`，無需標注 | 300 行 |
| 前端 SPA | React/Vue/Angular + 無後端 | 條件判定 | 條件判定 | 混合，須逐項標注 | 300 行 |
| CLI 工具 | clap/commander/argparse + 無 GUI | 條件判定 | 條件判定 | 預設 `[testable]`，無需標注 | 300 行 |
| 系統程式 | 網路/unsafe/檔案 I/O 密集 | 必要 | 必要 | 預設 `[testable]`，無需標注 | 300 行 |

**未匹配時**用後端 API 預設（最嚴格）。
**「預設 `[testable]`，無需標注」**：該領域的 BC-x/EH-x 視為 `[testable]`，只有例外（渲染/動畫等）才需標注 `[visual-only]` 或 `[framework-dependent]`。
**「條件判定」**：按 Phase 1/Phase 3 中的具體條件判斷。

### 7. 子 agent 失敗處理（全域規則）

子 agent（Phase 1b/3/5 的 Task 委派）超時、輸出為空、或明顯不完整時：
1. **第一次失敗**：重試一次（相同 prompt）
2. **第二次失敗**：主 agent 自行執行相同審查（標記「降級自審」）
3. 降級自審的結果在 Phase 5 產出物驗證中標記，不視為缺失但記錄品質降級

### 8. 斷點熔斷（全域規則）

同一 Phase 的斷點累計觸發 **3 次** → 暫停流程，用 AskUserQuestion 報告情況，由用戶決定：
- 繼續嘗試修正
- 降級為精簡閉環完成剩餘工作
- 重新設計（回 Phase 1 重新開始）

### 9. 因果鏈分析守衛（PreToolUse Hook）

每次 Edit/Write/MultiEdit 前，Hook 自動掃描被修改檔案的引用者，輸出依賴清單和因果鏈提醒。此提醒等同用戶回饋，**必須回應後才執行修改**。

**收到提醒時的回應規則**：
- **閉環 Phase 2/4 中**（按設計規格實作的修改）：簡要確認「已在 Phase 1 設計中分析」即可
- **斷點回退修正**（超出原始設計的修改）：必須明確列出 ①根因 ②Hook 列出的引用檔案是否受影響 ③需要連動更新的項目
- **非閉環修改**（微小任務或用戶直接指示）：必須在修改前明確回應 ①根因 ②下游影響 ③連動更新
- **Hook 列出引用檔案時**：逐一確認每個引用檔案是否需要連動修改。需要 → 一併修改；不需要 → 說明為什麼不影響

### Phase 1：架構師 📐

**Agent**：需求模糊 → `sc:brainstorm` | 需求明確 → `sc:design` | 複雜系統 → Task `Plan`
**語言指南**：若已部署語言指南，先讀取 Phase 1 段落（型別系統指南、BC-x/EH-x 慣用模式）。
**常見缺陷預防**：首次使用閉環或不熟悉的領域時，參考本文件末尾的「常見設計缺陷預防清單」。
**約束**：只產出設計規格，不寫程式碼。BC-x ≥ 2、所有參數有型別。若涉及跨模組 API → 從 `.claude-loop/interfaces/` 讀取或產出 IF-x 介面契約。涉及 status 變更的 BC-x 必須同時定義「變更後的行為約束」（哪些方法應被禁用、哪些子系統應停止）。
**EH-x 要求**：按領域預設（見 Section 6）。必要時覆蓋可預見異常；可選時須在設計規格中聲明「本系統無外部 I/O，EH-x 不適用」。
**執行順序要求**：若系統有 update/tick/frame 迴圈，設計規格**必須**包含步驟執行順序（虛擬碼等級，標明每步的依賴和副作用）。
**驗證層級標注**：按領域預設（見 Section 6）。預設為 `[testable]` 的領域無需逐項標注，只需標注例外（`[visual-only]`/`[framework-dependent]`）。預設非 `[testable]` 的領域須逐項標注。
**PRD 需求分解（可選）**：用戶提供 PRD / 需求文檔 / 說「需求分解」時啟用。先將 PRD 拆為編號需求項（PRD#1, PRD#2...，每項可獨立驗證），再設計 BC-x/EH-x，每項標注來源 `← PRD#n`（可多對多）。
**結構安全**：互斥狀態用 discriminated union / enum 建模，禁止用多個 boolean 組合。涉及資源（連線/檔案/訂閱）的 BC-x 須標注建立者和釋放者。
**⛔ 閘門（逐項檢查）**：
- [ ] 所有參數有型別
- [ ] BC-x ≥ 2
- [ ] EH-x 符合領域預設（必要時覆蓋異常；可選時已聲明不適用）
- [ ] 涉及 status 變更的 BC-x 有行為約束
- [ ] 有 update/tick 迴圈時已定義執行順序
- [ ] 驗證層級已標注（或領域預設為 `[testable]` 時例外項已標注）
- [ ] （若有 PRD）所有 PRD#n 有 ≥ 1 對應 BC-x/EH-x
全部 ✅ → 進 Phase 1b。

### Phase 1b：設計審查 🔬

**獨立性要求**：必須使用 Task 工具啟動獨立子 agent。子 agent **不繼承**主對話 context，只接收下方定義的審查包。目的：切斷認知偏見傳遞鏈，讓審查者以全新視角評估設計。
**目錄準備**：主 agent 在發送第一個委派 Task 前，執行 `mkdir -p .claude-loop/artifacts`。
**跳過條件**：用戶說「跳過設計審查」→ 直接進 Phase 2。Phase 5 步驟 4c 標記「用戶跳過」，不視為缺失。
**審查包**（主 agent 在發送 Task 前準備）：
- Phase 1 設計規格全文（BC-x/EH-x/IF-x 清單）
- 原始需求描述（用戶的任務說明，或 PRD 原文）
- 專案結構摘要：
  - 一層目錄結構（`ls` 或 `tree -L 2` 產出）
  - 每個現有關鍵模組的一句話職責（從 README 或程式碼推斷）
  - 現有 IF-x 介面契約清單（若有跨模組依賴）

**Task prompt 必須包含**：
- 角色：「你是獨立設計審查者，與設計者無關，不知道設計過程中的推理」
- 挑戰式標準：是否有更簡單的替代方案？BC-x 數量與功能複雜度是否匹配（過多=過度設計，過少=覆蓋不足）？有無設計不足？
- 驗證式標準：每個 BC-x 的預期行為是否可測試？EH-x 是否覆蓋外部失敗（網路/IO/權限/並發）？資源建立/釋放是否配對？互斥狀態是否用 union/enum 而非多 boolean？若有 update/tick 迴圈：執行順序是否已定義？（未定義 → 直接標 high）
- 輸出格式：DR-x + 嚴重度（high/arch-risk/medium/low）+ 問題描述 + 建議修正
- 寫入指令：「將完整審查報告寫入 `.claude-loop/artifacts/P1b-design-review.md`」

**產出**：DR-x 審查報告，寫入 `.claude-loop/artifacts/P1b-design-review.md`。
- **high**：邏輯缺陷、遺漏關鍵邊界情境、或存在明顯更優的替代方案 → 觸發閘門回退
- **arch-risk**：架構設計存在長期風險但不影響當前正確性（如擴展性瓶頸、耦合度偏高）→ 不觸發閘門，記錄到 Phase 5 追蹤
- **medium**：設計可改善但不影響正確性，或存在值得考慮的替代方向
- **low**：風格偏好或微小建議（合併摘要，不逐一列舉）

**⛔ 閘門**：
- 有 DR-x high → 必須回 Phase 1 修正設計，修正後重跑 Phase 1b（全量重審，不做差分）
- 有 arch-risk → 記錄但不阻擋，Phase 5 追蹤
- 僅有 medium/low → 用 AskUserQuestion 呈現給用戶，用戶決定是否採納。決策記錄保留供 Phase 5 追溯
- 全無問題 → 直接進 Phase 2

**迭代規則**：
- **終止條件**：本輪無新 high → 通過，arch-risk/medium/low 記錄但不阻擋
- **輪數上限**：最多 3 輪。第 3 輪仍有新 high → 主 agent 介入判斷設計方案是否需要重構，用 AskUserQuestion 呈現給用戶決定
- **全量重審理由**：設計規格是相互耦合的文件，修正一處可能破壞另一處的假設（壓測實證：修正 DR-4/5 引入了新的 DR-13）。差分審查在設計層有漏洞風險，不允許

### Phase 2：程序設計師 💻

**Agent**：`sc:implement` | 有計畫 → `superpowers:executing-plans`
**語言指南**：若已部署語言指南，先讀取 Phase 2 段落（編碼慣例、專案結構）。
**約束**：嚴格按 Phase 1 規格實作。每個 BC-x、EH-x 都要有對應程式碼。覺得設計有問題就回報，不自己改設計。
**增量驗證**：每完成一個檔案後，立即執行 `{{LINT_COMMAND}}`。目的：及早捕獲型別錯誤、未使用 imports、框架 lint 規則違規，避免錯誤累積到 Phase 4 才集中爆發。發現錯誤立即修正再繼續下一個檔案。
**單檔上限**：按領域預設（見 Section 6）。超出上限時必須拆分到獨立模組。**內聚性豁免**：超出上限但模組內聚度高（拆分會增加跨模組耦合且無自然拆分點）時，可放寬並在檔案頂部註記原因。
**強制優化**：實作完必須調用 Task `code-simplifier`（審查清晰度/一致性/可維護性，不改行為規格）。斷點回退後：修正範圍 < 50 行 → 跳過；≥ 50 行 → 重跑。
**設計文件同步**：以下情況須同步更新設計規格（不修改 ID，只更新描述）：
- bug 修正改變了 BC-x 描述的預期行為
- code-simplifier 改變了函式簽名或參數型別
- 測試揭示設計規格的描述有歧義需要澄清
不觸發同步：純重命名（不影響語意）、程式碼風格調整、新增內部 helper 函式。
**⛔ 閘門**：無語法錯誤 ∧ 設計項都有實作 ∧ code-simplifier 已執行 → 才能進 Phase 3。

### Phase 3：檢核師 🔍

**獨立性要求**：品質審查使用 Task 啟動獨立子 agent。安全審查按領域預設決定是否執行。
**品質審查 Task prompt**：
- 角色：「你是獨立品質檢核師，與實作者無關，不知道實作過程中的推理」
- 輸入：Phase 1 設計規格 + Phase 2 程式碼檔案路徑（子 agent 用 Read 自行讀取）+ 語言指南 Phase 3 段落（若有）
- 審查規則：比對設計與實作一致性 + 結構安全（資源生命週期配對/錯誤靜默/非法狀態組合）+ 語言專屬審查（標 `[語言名]`）+ 跨模組資料流追蹤（拆分邊界的資料過濾/轉換是否保持下游模組預期的語意）
- 輸出：R-x + 嚴重度（high/arch-risk/medium/low/by-design）+ 問題描述 + 建議修正
- 寫入指令：「將完整檢核報告寫入 `.claude-loop/artifacts/P3-quality-review.md`」

**安全審查**：按領域預設（見 Section 6）。領域預設為「可跳過」時，以下條件**全部**滿足可跳過並在品質審查報告末尾標記「安全審查：by-design 跳過（[原因]）」：
- 無網路連線（含 WebSocket/fetch/API 呼叫）
- 無使用者敏感資料處理（密碼/PII/金融資訊）
- 無檔案系統寫入（或僅限本地設定檔讀取）
- 無 unsafe/eval/動態程式碼執行
- 無第三方認證/授權流程
不滿足任一條件 → 安全審查照常執行。

**安全審查 Task prompt**（不跳過時）：
- 角色：「你是獨立安全檢核師」
- 輸入：Phase 2 程式碼檔案路徑
- 審查規則：輸入驗證 / 注入風險 / 認證授權 / 敏感資料暴露 / 依賴安全
- 輸出：R-x + 嚴重度 + 問題描述 + 建議修正
- 寫入指令：「將完整檢核報告寫入 `.claude-loop/artifacts/P3-security-review.md`」

**約束**：問題標 R-x + 嚴重度。`by-design` 用於刻意的設計取捨，不計入斷點判定。**R-x 報告策略**：high/arch-risk/medium 逐一列出；low 級合併為一句摘要。
**嚴重度定義**：
- **high**：邏輯錯誤、安全漏洞、跟設計規格不符 → 觸發斷點 A
- **arch-risk**：架構風險但不影響當前正確性 → 不觸發斷點 A，記錄到 Phase 5 追蹤
- **medium**：品質問題、未來可能出事 → 建議修
- **low**：風格建議 → 合併摘要
**結構安全**（品質審查包含）：資源生命週期——建立/釋放是否配對？有無洩漏路徑？（R-x, high）。錯誤靜默——是否有 catch-all 吃掉錯誤？每個 fallible 操作是否有明確 error path？（R-x, high）。狀態表示——有無可表達的非法狀態組合？（有狀態機時檢查，R-x, medium）。
**⛔ 斷點 A**：有 high → 禁止進入 Phase 4，回 Phase 2 修正後重跑 Phase 3。有 arch-risk → 記錄但不阻擋。
**斷點 A 回退後的差分審查**：回退修正後，Phase 3 重跑範圍為**範圍限定的品質審查**（非全量重審）：
1. 所有被修改的檔案 → 全量審查
2. import/呼叫被修改檔案的檔案 → 相關性審查（只看呼叫點）
3. 未被修改且無依賴關係的檔案 → 跳過
4. 原 R-x high 項 → 逐項確認修復狀態
安全審查（若先前已執行）不需重跑（修正範圍通常不影響安全面）。

### Phase 4：測試師 🧪

**Agent**：`sc:test` | `superpowers:test-driven-development`
**語言指南**：若已部署語言指南，先讀取 Phase 4 段落（測試框架、測試模式）。

**測試分層定義**：
| 層級 | 定義 | 驗證方式 |
|------|------|---------|
| `[testable]` | 純邏輯、可程式化驗證 | 必須有自動化測試，Phase 4 閘門強制 |
| `[visual-only]` | 渲染、動畫、UI 佈局 | 免除自動化測試；Phase 3 品質審查以 code review 驗證；測試報告中列出並標注「視覺驗證」 |
| `[framework-dependent]` | 需要框架 runtime 才能執行 | 建議拆分純邏輯方法，對純邏輯部分按 `[testable]` 要求；無法拆分的部分按 `[visual-only]` 處理 |

**約束**：每個測試標注 BC-x/EH-x。所有 `[testable]` 設計項都要有自動化測試。`[visual-only]` 和 `[framework-dependent]` 項必須在測試報告中列出並標注驗證方式。必須用 Bash 依序執行 `{{TEST_COMMAND}}` 和 `{{BUILD_COMMAND}}`（測試驗邏輯，建置驗型別）。
**測試覆蓋要求**：`[testable]` BC-x 每項需覆蓋正常路徑 + 邊界值 + 違規輸入；`[testable]` EH-x 每項需實際觸發錯誤路徑，不僅驗證 guard 存在。
**測試設計原則**：場景足夠大以避免邊界觸發意外行為 | 斷言判行為而非具體值 | 有衍生狀態時同步設定所有關聯欄位 | 涉及即時模擬時優先注入確定性狀態而非依賴全程模擬 | 有級聯副作用的操作需精確控制測試中的操作順序。
**設計文件同步**：測試揭示設計規格描述有歧義時，同步更新（同 Phase 2 同步規則）。
**⛔ 斷點 B**：有測試或建置失敗 → 禁止進入 Phase 5，先判定原因：
- 程式碼 bug → 回 Phase 2 修正 → 重跑 Phase 3 + 4
- 測試設計問題（場景/斷言/前置條件有誤）→ 回 Phase 4 修正測試 → 通過即進 Phase 5

### Phase 5：自証師 ✅

**語言指南**：若已部署語言指南，先讀取 Phase 5 段落（驗證指令序列）。

**自証（兩段式）**：
> Part AB 由單一獨立子 agent 執行雙向追溯（不繼承主對話 context）。Part C 由主 agent 彙整判定。
> 多模組任務：自証涵蓋所有模組的設計項、程式碼和測試。Part C 的全專案回歸測試為必做。

**Part AB — 雙向追溯**（單一獨立子 agent · 正向追溯 + 反向分析）：
**獨立性要求**：必須使用 Task 工具啟動獨立子 agent，切斷主對話的推理 context。
**合併理由**：單一 agent 同時做正向（設計→程式碼→測試）和反向（程式碼→設計）追溯，可即時交叉比對——正向發現的缺失與反向發現的冗餘互為補充，品質優於兩個獨立 agent 各做一半再由第三方調和。
**驗證包**（主 agent 準備）：
- Phase 1 設計規格全文（BC-x/EH-x/IF-x 清單，含驗證層級標注）
- Phase 1b DR-x 審查報告（含 arch-risk 項目清單）
- Phase 3 R-x 檢核報告（含 arch-risk 項目清單）
- Phase 2 程式碼檔案路徑清單（子 agent 用 Read 自行讀取比對）
- Phase 4 測試檔案路徑清單（子 agent 用 Read 自行讀取比對）
- PRD 分解表（若有）
- 語言指南部署狀態

**Task prompt 必須包含**：
- 角色：「你是獨立自証審查者（雙向追溯），與開發者無關，不知道開發過程」
- 正向追溯規則：對每個 BC-x/EH-x，在程式碼中找到對應實作（標 ✅/❌ + 檔案:行數），在測試中找到對應案例（標 ✅/❌ + 測試名稱）。`[visual-only]` 和 `[framework-dependent]` 項的測試欄位標注驗證方式而非測試名稱
- 反向分析規則：識別所有行為路徑（正常/錯誤/邊界）→ 逐一對應 BC-x/EH-x → 未對應的標記 `[遺漏設計]`（應有 BC-x 但未定義）或 `[多餘程式碼]`（不該存在的行為）
- 交叉比對規則：正向發現 ❌ 時，立即在反向分析中確認該 BC-x 附近是否有相關行為路徑；反向發現未覆蓋路徑時，立即在正向追溯中確認是否有對應設計項
- arch-risk 追蹤規則：逐一確認 Phase 1b 和 Phase 3 標記的 arch-risk 項目，評估是否在後續 Phase 中已緩解或仍存在
- 路徑追蹤：挑最複雜 2-3 個 BC-x，追蹤 入口→處理→出口 完整路徑，比對設計意圖
- 輸出格式：正向追溯表（逐項 ✅/❌ + 證據位置）+ 反向未覆蓋路徑清單 + arch-risk 追蹤狀態 + 執行路徑追蹤結果 + 交叉比對發現
- 寫入指令：「將完整雙向追溯結果寫入 `.claude-loop/artifacts/P5AB-bidirectional-tracing.md`」

**檢查步驟**：
0. 若有 PRD 分解：逐一確認每個 PRD#n 有 ≥ 1 個對應 BC-x/EH-x（✅/❌）。有 ❌ → 標記回退
1. 從 Phase 1 列出所有 BC-x、EH-x、IF-x（若有）→ **基準清單**
2. 逐一確認 Phase 2 有對應實作（✅/❌）。IF-x 需確認函式簽名與契約一致
3. 逐一確認 Phase 4 有對應測試或驗證方式（✅/❌）。`[testable]` 項需有自動化測試；`[visual-only]`/`[framework-dependent]` 項需有標注的替代驗證方式
4. Phase 3 的 high/medium R-x 是否已修（✅/❌）
4b. 若已部署語言指南：Phase 3 R-x 報告是否包含語言專屬項（帶 `[語言名]` 標記）？（✅/❌）
4c. Phase 1b 的 DR-x high 是否已修正（✅/❌）？medium 的用戶決策是否有記錄（✅/❌）？
5. 閱讀 Phase 2 程式碼，找出不被任何 BC-x/EH-x 覆蓋的行為路徑。有 → 判定是遺漏設計還是多餘程式碼
6. 挑最複雜的 2-3 個 BC-x，沿程式碼追蹤執行路徑，驗證行為與設計意圖一致
7. 交叉比對步驟 1-4（正向）與步驟 5-6（反向）的結果，標記矛盾或互補的發現
8. 逐一確認 Phase 1b 和 Phase 3 標記的 arch-risk 項目的當前狀態
**產出**：雙向追溯結果，寫入 `.claude-loop/artifacts/P5AB-bidirectional-tracing.md` 並回傳給主 agent。

**Part C — 整體評估**（主 agent 彙整）：
**⛔ 委派產出物驗證**（步驟 9 前必做）：用 Glob 確認 `.claude-loop/artifacts/` 下列檔案全部存在：
- `P1b-design-review.md`（用戶跳過 1b 時除外）
- `P3-quality-review.md`
- `P3-security-review.md`（安全審查 by-design 跳過時除外）
- `P5AB-bidirectional-tracing.md`
任一缺漏 → 回退到對應 Phase 重做委派，禁止繼續。降級自審的產出物視為存在但標記降級。
**⛔ 委派呼叫驗證**（產出物驗證後）：讀取 `.claude-loop/artifacts/.delegation-log`，確認包含 P1b（用戶跳過時除外）、P3-quality、P3-security（安全審查跳過時除外）、P5AB 的記錄。此 log 由 Hook 自動寫入（非 Claude 寫入），缺漏表示 Agent tool 未被實際呼叫。delegation-log 缺失但產出物檔案存在時，以產出物存在為準（Hook 可能因平台相容性未觸發）。
9. 收集 Part AB 結果，確認產出物完整（設計規格/設計審查報告/程式碼/檢核報告/測試報告）
10. 跑全專案驗證：`{{VERIFY_SEQUENCE}}`（多模組必做；單模組有範圍外影響風險時做）
11. 全 ✅ → 通過；有 ❌ → 不通過 + 回退建議

**回退規則**：設計-實作不一致 → P2（嚴重→P1）| 測試不足 → P4 | 檢核未修 → P2 | DR-x high 未修 → P1 | DR-x 決策未記錄 → 補記錄 | 產出物缺漏 → 對應 Phase | arch-risk 未追蹤 → 補追蹤記錄
**通過後**：若專案有多模組，跑全專案 `{{VERIFY_SEQUENCE}}` 確認 0 回歸。commit，message 帶自証摘要。

## 精簡閉環（中型任務）

> 中型任務觸發。五步流程：設計→設計快審→實作→品質審查→測試驗證。

**步驟 1 — 設計**：簡要設計規格（目標 | 主要函式簽名與參數型別 | BC-x ≥ 1 | EH-x 按領域預設 | 驗證層級按領域預設標注）。若已部署語言指南，參考 Phase 1 段落的 BC-x/EH-x 慣用模式。若有 update/tick 迴圈，包含步驟執行順序。
**設計自檢**（完成設計後 30 秒快速檢查）：① 有沒有更簡單的做法？ ② 會不會影響不相關的模組？ ③ 邊界條件是否覆蓋空值/溢位/並發？任一答案不確定 → 用 AskUserQuestion 詢問用戶是否要深入探討再繼續。

**步驟 1b — 設計快審（單輪）**：使用 Task 啟動獨立子 agent 審查設計（同完整閉環 Phase 1b 的審查包和 prompt）。**只跑 1 輪，不回退重審**：有 high → 主 agent 直接修正設計後進入步驟 2（不重跑 1b）；無 high → 直接進步驟 2。目的：用 ~20K token 攔截最嚴重的設計缺陷。

**步驟 2 — 實作**：按設計實作。若已部署語言指南，遵循 Phase 2 段落的編碼慣例。每完成一個檔案立即執行 `{{LINT_COMMAND}}` 驗證，發現錯誤當場修正。單檔上限按領域預設（含內聚性豁免）。全部完成後調用 Task `code-simplifier` 優化。設計文件同步規則同完整閉環。

**步驟 3 — 品質審查**：使用 Task 啟動獨立子 agent 執行品質審查（同完整閉環 Phase 3 品質審查 prompt，不含安全審查）。有 R-x high → 回步驟 2 修正 → 重跑步驟 3（使用差分審查：只審修改檔案 + 依賴檔案 + 原 high 確認修復）。無 high → 進步驟 4。

**步驟 4 — 測試驗證**：
- 確認每個 `[testable]` BC-x/EH-x 有對應測試；`[visual-only]`/`[framework-dependent]` 項在報告中列出驗證方式
- 若已部署語言指南，抽查 Phase 3 審查清單的 high 項目（≤ 3 項快速檢查）
- 用 Bash 執行 `{{VERIFY_SEQUENCE}}`
- 全通過 → commit；失敗 → 回步驟 2 修正

## 配額管理策略

> 多階段連續開發時，子 agent 委派配額可能在 session 後半段耗盡。以下策略防止被迫全降級。

**分配策略**（session 開始時評估）：
- 若 session 可完成所有階段 → 全部走完整閉環
- 若配額不足以完成所有完整閉環 → 前 N 階段完整，後續精簡
- 精簡降級時明確標記「配額降級」，不影響閘門邏輯

**降級優先順序**（先降低價值的）：
1. P5 Part AB → 主 agent 自審（省最多 token）
2. P3 安全審查 → 跳過（前提：滿足跳過條件）
3. P1b → 降為單輪不回退（精簡模式）
4. P3 品質審查 → ⛔ **不可降級**（壓測實證：ROI 最高的 Phase，100% 攔截率）

## 常見設計缺陷預防清單

> Phase 1 設計時可參考。首次使用閉環或不熟悉的領域時建議逐項檢查。

| # | 常見缺陷 | 怎麼防 |
|---|---------|--------|
| 1 | update/tick 步驟順序未定義 | 有迴圈就定義虛擬碼等級的步驟順序，標明依賴和副作用 |
| 2 | 資源建立後未釋放 | 每個 open/create/subscribe 配對 close/destroy/unsubscribe |
| 3 | 不可達的狀態 variant | 確認每個 enum variant 都有進入路徑，無用的刪除 |
| 4 | 碰撞/交互時機未定義 | 明確在哪一步偵測，偵測後的處理順序和優先級 |
| 5 | UI 與引擎狀態不同步 | 混合架構（Canvas+React、遊戲+UI）需定義同步回調機制 |
| 6 | 跨模組拆分語意遺漏 | 拆分邊界的資料過濾/轉換不得改變下游模組的預期 |
| 7 | 初始狀態不合法 | 預設值/起始位置/初始參數是否符合所有不變量（invariant） |
| 8 | 設計精度不足 | 粒度應到「可直接翻譯為程式碼」，非「方向指引」 |
