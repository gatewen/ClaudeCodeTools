# 層級擴展

## 三個層級

閉環不只能用在單一函式上。同樣的五階段流程可以套在不同大小的範圍：

| 層級 | 範圍 | 白話說明 |
|------|------|---------|
| 方法（Function） | 一個函式 | 確認這個函式本身沒問題 |
| 模組（Module） | 一組相關的函式或類別 | 確認這群函式合作起來沒問題 |
| 框架（Framework） | 整個系統架構 | 確認整體設計沒問題 |

## 層級怎麼串起來

```
函式 A 閉環通過 ──┐
函式 B 閉環通過 ──┤→ 模組閉環 → 模組通過 ──┐
函式 C 閉環通過 ──┘                          ├→ 框架閉環 → 系統通過
                                              │
模組 X 閉環通過 ──┐                          │
模組 Y 閉環通過 ──┤→ ─────────────────────────┘
```

**低層級的產出物就是高層級的輸入。**

模組閉環的架構師不用從零開始設計，而是拿著底下所有函式的設計規格和自証結果來工作。

## 什麼時候觸發哪個層級

- **方法層級**：每寫一個新函式或大幅修改一個函式就觸發（這是預設）
- **模組層級**：一個模組裡的所有函式閉環都通過後自動觸發
- **框架層級**：涉及系統架構變更時才觸發（例如：換框架、改整體設計模式）

大部分的日常開發只會用到方法層級。模組層級在做完一個完整功能後才需要。框架層級很少用到。

## 模組層級

### 跟方法層級的關係

模組閉環**不是重跑一次方法閉環**，而是站在更高的視角，看底下這群函式合在一起有沒有問題。

**前提**：模組裡每個函式的方法層級閉環都已經通過。

**輸入**：所有函式的設計規格 + 自証結果。

**額外要查的事情**：

| 檢查項 | 在確認什麼 | 怎樣算有問題 |
|--------|-----------|-------------|
| 職責劃分 | 每個函式的責任有沒有清楚劃分 | 一個函式什麼都做、兩個函式做重複的事 |
| 協作正確性 | 函式 A 的輸出餵給函式 B，格式和語意對得上嗎 | A 回傳 string 但 B 期待 number |
| 內聚性 | 這些函式放在一起合理嗎 | 有不相關的函式混在裡面 |
| 錯誤傳播 | 函式 A 出錯時，函式 B 和 C 會怎麼反應 | A 拋出錯誤但 B 沒有 catch |

### 模組層級的 ID 系統

方法層級用 BC-x、EH-x。模組層級多兩種：

| 前綴 | 含義 | 說明 |
|------|------|------|
| MC-1, MC-2... | 模組協作（Module Collaboration） | 函式之間的協作契約 |
| EP-1, EP-2... | 錯誤傳播（Error Propagation） | 跨函式的錯誤流轉路徑 |

方法層級的 BC-x 和 EH-x 在模組層級仍然有效，不需要重新編號。MC-x 和 EP-x 是模組層級新增的。

### 模組設計規格（Phase 1 產出）

```markdown
## 📐 模組設計規格

### 模組目標
[一句話說明這個模組要解決什麼問題]

### 包含的函式

| 函式名 | 職責 | 方法閉環狀態 |
|--------|------|-------------|
| funcA | [這個函式負責什麼] | ✅ 通過 |
| funcB | [這個函式負責什麼] | ✅ 通過 |
| funcC | [這個函式負責什麼] | ✅ 通過 |

### 公開 API

| 名稱 | 參數 | 回傳 | 說明 |
|------|------|------|------|
| [對外暴露的函式/方法] | [型別] | [型別] | [用途] |

### 函式協作（內部資料流）

```
用戶輸入
  ↓
funcA（驗證輸入）
  ↓ 回傳 ValidatedInput
funcB（處理邏輯）
  ↓ 回傳 Result
funcC（格式化輸出）
  ↓ 回傳 FormattedResult
```

### 模組協作契約

| ID | 上游函式 | 下游函式 | 傳遞的資料 | 契約說明 |
|----|---------|---------|-----------|---------|
| MC-1 | funcA | funcB | ValidatedInput | [funcA 保證回傳非 null，funcB 依賴此保證] |
| MC-2 | funcB | funcC | Result | [funcB 回傳的 Result 一定有 status 欄位] |

### 錯誤傳播路徑

| ID | 起源函式 | 錯誤類型 | 傳播路徑 | 最終處理 |
|----|---------|---------|---------|---------|
| EP-1 | funcA | ValidationError | funcA → 直接拋出 | 呼叫端 catch |
| EP-2 | funcB | NetworkError | funcB → funcC 收到 null → 回傳預設值 | 靜默降級 |

### 設計決策
[為什麼這樣劃分職責，排除了什麼替代方案]
```

### 模組檢核報告（Phase 3 產出）

跟方法層級的檢核報告格式相同（用 R-x 編號），但多檢查以下面向：

```markdown
## 🔍 模組檢核報告

- 檢核對象：[模組名稱]
- 檢核時間：[YYYY-MM-DD HH:MM]
- 檢核範圍：模組層級（方法層級已各自通過）

### 模組專屬檢查

| ID | 嚴重度 | 檢查面向 | 問題描述 | 建議修正 | 狀態 |
|----|--------|---------|---------|---------|------|
| R-1 | high | 協作正確性 | [例：funcA 回傳 string 但 funcB 期待 number] | [加型別轉換] | open |
| R-2 | medium | 職責劃分 | [例：funcB 同時做驗證和處理，應拆分] | [提取驗證到 funcA] | open |
| R-3 | medium | 錯誤傳播 | [例：funcB 的 NetworkError 沒被 funcC 處理] | [funcC 加 try-catch] | open |
| R-4 | low | 內聚性 | [例：helperX 跟這個模組的職責無關] | [移到 utils 模組] | open |
```

### 模組測試報告（Phase 4 產出）

方法層級測試的是單一函式。模組層級測試的是**函式之間的協作**（整合測試）。

```markdown
## 🧪 模組測試報告

- 測試對象：[模組名稱]
- 測試時間：[YYYY-MM-DD HH:MM]
- 模組協作覆蓋：X / Y
- 錯誤傳播覆蓋：X / Y

| 測試名稱 | 對應規格 ID | 結果 | 說明 |
|---------|------------|------|------|
| [test_a_to_b_data_flow] | MC-1 | pass/fail | [funcA → funcB 的資料傳遞] |
| [test_b_to_c_contract] | MC-2 | pass/fail | [funcB → funcC 的契約驗證] |
| [test_validation_error_propagation] | EP-1 | pass/fail | [ValidationError 正確拋出] |
| [test_network_error_degradation] | EP-2 | pass/fail | [NetworkError 靜默降級] |
| [test_full_happy_path] | — | pass/fail | [完整正常路徑] |
| [test_full_error_path] | — | pass/fail | [完整錯誤路徑] |
```

注意：方法層級的單元測試仍然有效，不需要重跑。模組層級只加**整合測試**。

### 模組自証結果（Phase 5 產出）

方法層級的 4 個維度保留，再加 2 個模組專屬維度：

```markdown
## ✅ 模組自証結果

- 自証對象：[模組名稱]
- 自証時間：[YYYY-MM-DD HH:MM]
- **判定：通過 / 不通過**

### 方法層級前提
| 函式 | 方法閉環 |
|------|---------|
| funcA | ✅ 通過 |
| funcB | ✅ 通過 |
| funcC | ✅ 通過 |

### 模組層級驗證

| 維度 | 狀態 | 證據 | 缺口描述 |
|------|------|------|---------|
| 設計-實作一致性 | ✅/❌ | [MC-1, MC-2, EP-1, EP-2 均有對應實作] | |
| 實作-測試覆蓋 | ✅/❌ | [模組協作 2/2、錯誤傳播 2/2] | |
| 檢核-修正閉合 | ✅/❌ | [R-1(high) 已修正] | |
| 產出物完整性 | ✅/❌ | [模組設計規格 ✅ 整合測試 ✅ 模組檢核 ✅ 模組測試報告 ✅] | |
| **協作正確性** | ✅/❌ | [所有 MC-x 契約在整合測試中驗證通過] | |
| **錯誤傳播完整性** | ✅/❌ | [所有 EP-x 路徑在整合測試中驗證通過] | |

（若不通過）
### 回退建議
- 回退目標：[具體函式的方法閉環 / 模組 Phase X]

- 修正方向：[建議怎麼修]
```

## 框架層級

### 跟模組層級的關係

框架閉環看的是**模組之間**的合作，就像模組閉環看的是函式之間的合作。

**前提**：所有模組的模組層級閉環都已經通過。

**輸入**：所有模組的設計規格 + 自証結果。

**額外要查的事情**：

| 檢查項 | 在確認什麼 | 怎樣算有問題 |
|--------|-----------|-------------|
| 設計模式適用性 | 用的設計模式合不合適 | 過度設計、模式用錯場景 |
| 可擴展性 | 未來加新功能容不容易 | 加一個小功能要改 10 個地方 |
| 跨模組一致性 | 不同模組的風格統一嗎 | 模組 A 用 camelCase、模組 B 用 snake_case |
| 依賴關係 | 模組之間的依賴合不合理 | 循環依賴、過度耦合 |

### 框架層級的 ID 系統

模組層級的 MC-x、EP-x 仍然有效。框架層級多一種：

| 前綴 | 含義 | 說明 |
|------|------|------|
| MD-1, MD-2... | 模組依賴（Module Dependency） | 跨模組的依賴契約和介面約定 |

### 框架設計規格（Phase 1 產出）

```markdown
## 📐 框架設計規格

### 系統目標
[一句話說明整個系統要解決什麼問題]

### 模組組成

| 模組名 | 職責 | 模組閉環狀態 |
|--------|------|-------------|
| 模組 X | [負責什麼] | ✅ 通過 |
| 模組 Y | [負責什麼] | ✅ 通過 |

### 模組依賴關係

```
模組 X ──呼叫──→ 模組 Y
模組 Y ──呼叫──→ 模組 Z
模組 X ──不依賴──→ 模組 Z（確保隔離）
```

### 模組依賴契約

| ID | 上游模組 | 下游模組 | 介面 | 契約說明 |
|----|---------|---------|------|---------|
| MD-1 | 模組 X | 模組 Y | Y.process(data) | [X 傳入的 data 格式、Y 保證的回傳] |
| MD-2 | 模組 Y | 模組 Z | Z.store(result) | [Y 傳入的 result 格式、Z 的失敗處理] |

### 架構決策

| 決策 | 選擇 | 排除的替代方案 | 原因 |
|------|------|--------------|------|
| [例：狀態管理] | [例：事件驅動] | [例：共享狀態] | [例：避免耦合] |
| [例：錯誤處理策略] | [例：統一錯誤邊界] | [例：各模組自行處理] | [例：一致性] |
```

模組層級的 6 個維度保留，再加 2 個框架專屬維度：

- 自証時間：[YYYY-MM-DD HH:MM]

### 模組層級前提
| 模組 | 模組閉環 |

| 模組 Y | ✅ 通過 |

### 框架層級驗證

| 維度 | 狀態 | 證據 | 缺口描述 |
|------|------|------|---------|
| 設計-實作一致性 | ✅/❌ | [所有 MD-x 均有對應實作] | |
| 實作-測試覆蓋 | ✅/❌ | [模組依賴 2/2、E2E 路徑覆蓋] | |
| 檢核-修正閉合 | ✅/❌ | [框架層級 R-x 均已處理] | |
| 產出物完整性 | ✅/❌ | [框架設計規格 ✅ E2E 測試 ✅ 框架檢核 ✅ 框架測試報告 ✅] | |

| 錯誤傳播完整性 | ✅/❌ | [繼承模組層級，所有 EP-x 通過] | |
| **跨模組一致性** | ✅/❌ | [命名風格、錯誤處理策略、介面慣例統一] | |
| **依賴合理性** | ✅/❌ | [無循環依賴、所有 MD-x 契約在 E2E 測試中驗證] | |

## 層級之間的產出物怎麼彙整

| 從哪來 | 到哪去 | 帶什麼過去 |
|--------|--------|-----------|
| 方法閉環 → 模組閉環 | Phase 1 輸入 | 每個函式的設計規格 + 自証結果 |
| 模組閉環 → 框架閉環 | Phase 1 輸入 | 每個模組的設計規格 + 自証結果 |

**不需要帶的東西**：
- 方法層級的檢核報告和測試報告不用帶到模組層級（已經在方法自証時驗證過了）
- 模組層級的檢核報告和測試報告不用帶到框架層級（同理）

**需要帶的東西**：
- 設計規格（告訴上層「底下有什麼」）
- 自証結果（告訴上層「底下的品質狀態」）

如果底下某個閉環的自証結果是「有條件通過」（例如有 low 問題未處理），上層閉環的架構師要判斷這些遺留問題在上層視角是否可接受。

## ID 系統總覽

| 前綴 | 含義 | 定義層級 | 引用層級 |
|------|------|---------|---------|
| BC-x | 邊界條件 | 方法 | 方法、模組、框架 |
| EH-x | 錯誤處理 | 方法 | 方法、模組、框架 |
| R-x | 檢核問題 | 所有層級 | 同層級的 Phase 5 |
| MC-x | 模組協作 | 模組 | 模組、框架 |
| EP-x | 錯誤傳播 | 模組 | 模組、框架 |
| MD-x | 模組依賴 | 框架 | 框架 |
