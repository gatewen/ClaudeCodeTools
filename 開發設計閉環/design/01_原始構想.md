# 原始構想：開發的工作閉環

## 核心理念

- **閉環原則**：每個粒度層級都必須形成獨立的完整閉環
- **自証機制**：閉環的最後一步，由「自証師」驗證該層級的所有產出是否一致、完整、可運行
- **逐層擴展**：從最小的方法層級開始，逐步往上擴展到框架層級

## 閉環層級定義

| 層級 | 範圍 | 說明 |
|------|------|------|
| **方法（Function）** | 單一函式 | 最小可驗證單元，確保輸入/輸出/邊界正確 |
| **模組（Module）** | 一組相關函式/類別 | 確保內部邏輯一致，職責單一 |
| **介面（Interface）** | 模組與模組之間的溝通契約 | 確保模組間的協作正確、契約穩定 |
| **框架（Framework）** | 整體架構與設計模式 | 確保系統層級的一致性、可擴展性 |

## 基礎角色（適用於所有層級）

| 順序 | 角色 | 職責 | 產出物 |
|------|------|------|--------|
| 1 | 架構師 | 定義該層級的結構與設計 | 設計文件/規格 |
| 2 | 程序設計師 | 根據設計進行實作 | 程式碼 |
| 3 | 程序檢核師 | 檢查程式碼品質與邏輯正確性 | 檢核報告 |
| 4 | 安全檢核師 | 檢查安全漏洞與風險 | 安全報告 |
| 5 | 測項規劃師 | 規劃測試案例與覆蓋範圍 | 測試計畫 |
| 6 | 單元測試設計師 | 撰寫自動化測試程式 | 測試程式碼 |
| 7 | 測試師 | 執行測試並回報結果 | 測試報告 |
| 8 | 效能評估師 | 評估效能瓶頸與優化建議 | 效能報告 |
| 9 | **自証師** | 綜合驗證所有產出的一致性與完整性 | 自証結果（通過/不通過） |

## 追加角色

### 介面層級

| 角色 | 職責 | 產出物 |
|------|------|--------|
| 介面規劃師 | 定義模組間的溝通契約（API/協議） | 介面規格文件 |
| 介面程序設計師 | 實作介面層程式碼 | 介面程式碼 |
| 介面檢核師 | 驗證介面實作與規格的一致性 | 介面檢核報告 |

### 框架層級

| 角色 | 職責 | 產出物 |
|------|------|--------|
| 設計模式專家 | 選擇並套用合適的設計模式 | 設計模式建議書 |
| 設計模式評估專家 | 評估設計模式的適用性與風險 | 評估報告 |

## 閉環流程（方法層級）

```
架構師 → 程序設計師 → 程序檢核師 → 安全檢核師
→ 測項規劃師 → 單元測試設計師 → 測試師
→ 效能評估師 → 自証師
                  ↓
           通過 → 完成
           不通過 → 回到對應角色修正
```

## 原始文件中的自我觀察

### 已識別的問題

1. **介面定位模糊**：同時被當作層級和溝通機制，建議改為三層 + 橋接閉環
2. **角色數量過多**：9 個基礎角色可能造成流程冗長，建議先精簡為 5 個
3. **自証定義不清**：缺少具體的輸入、標準、回饋路徑
4. **缺少需求起點**：架構師的設計依據不明確
5. **回饋機制不足**：線性流程缺少中間回退路徑
6. **可參考框架**：V-Model、Code Review Pipeline、AI Agent Workflow
